AI ツール活用ガイド（Claude Code）

本リポジトリの標準 AI ツールである Claude Code の常設リファレンスです。
STEP-02 で全体に目を通し、以降の課題では必要な節を随時参照してください。ここでの目標は、Claude Code の特性を理解して状況に応じて意図的に使い分けられるようになることです。

実践的なテクニック（検証の与え方、コンテキスト管理、よくある失敗パターン）は Claude Code ベストプラクティス、AI-DLC を使わずに課題を進める手順は AI-DLC を使わない開発フロー を参照してください。

Claude Code とは​

Claude Code は、ターミナル上で動作するコーディングエージェントです。
エディタのインライン補完と異なり、リポジトリ全体を読み取りながら対話形式でタスクを進められるのが特徴です。

得意な場面

場面例
広いコンテキストが必要な質問「予約申請から承認までの処理がどのファイルを通るか説明して」
複数ファイル横断の変更「Resource に description フィールドを追加して。Entity・DTO・画面まで一式」
影響範囲の安全確認「このメソッドのシグネチャを変えたら、呼び出し元はどこが壊れる？」
テスト・ドキュメント生成「この Service のユニットテストを既存テストの書き方に合わせて作成して」
エラー原因の調査エラーメッセージを貼り付けて「原因を調査して」

セットアップ​

Claude Code は DevContainer に組み込み済みです。学習者が追加でインストールする必要はありません。

構成要素内容
CLIdevcontainer feature（anthropics/devcontainer-features/claude-code）で自動インストール
VS Code 拡張Anthropic.claude-code が自動インストール
認証情報.claude（.credentials.json を含む）はコンテナ専用の named volume に隔離。ホストとは共有しない

初回の認証​

DevContainer 内のターミナルで起動します。

claude --version   # インストール確認
claude             # 対話セッションを開始

初回起動時はログイン（ブラウザ認証）を求められます。画面の指示に従って認証してください。
認証情報はコンテナ専用の named volume に保存されるため、コンテナを再作成してもログインし直す必要はありません（volume 自体を削除した場合を除く）。

ホストで Claude Code を使ったことがある場合でも、コンテナ内では初回ログインが必要

.claude ディレクトリはホストと共有せずコンテナ専用の named volume に隔離しているため、ホスト側の認証情報は引き継がれません。コンテナ内のターミナルで一度だけ claude にログインしてください。

コンテナ起動が .claude.json 関連で失敗する場合

マウント元の ~/.claude.json はコンテナ初回起動時に自動生成されます（devcontainer.json の initializeCommand）。
起動に失敗する場合は AI ツール関連のトラブルシューティング を参照してください。

基本的な使い方​

対話の始め方​

リポジトリルート（/workspace）で claude を起動し、日本語でそのまま依頼します。

> 予約のステータス遷移がどこで実装されているか教えて

VS Code 拡張機能としての利用​

ターミナルの claude コマンドに加えて、VS Code 拡張機能（Anthropic.claude-code、セットアップ時に自動インストール済み）からもグラフィカルパネルで同じ Claude Code を使えます。
エディタ右上のアイコン、またはコマンドパレットで「Claude Code」と入力して開きます。

拡張機能ならではの利点：

機能内容
差分レビューClaude が提案する変更を、受け入れる前にエディタ上の差分表示で確認・編集できる
@ メンションファイル名の一部やコード選択範囲を @ で直接参照させられる
複数会話別のタブやウィンドウで複数の会話を並行して開ける

ターミナルとパネルは会話履歴を共有しているため、claude --resume でパネル側の会話をターミナルから再開することもできます。

CLAUDE.md 連携​

Claude Code は起動時にリポジトリルートの CLAUDE.md を自動で読み込みます。
本リポジトリの CLAUDE.md には技術スタック、ディレクトリ構成、よく使うコマンド、コーディング規約が記載済みのため、毎回これらを説明しなくても前提を踏まえた回答が得られます。

CLAUDE.md は「AI への申し送り事項」

プロジェクト固有の約束事（規約、コマンド、設計方針）を CLAUDE.md に書いておくと、すべてのセッションで一貫して反映されます。

よく使う操作​

キー操作

操作内容
shift+tabモード切替。既定の Manual モードから、Accept edits・Plan・Auto など複数のモードを順に切り替えられる（詳細は権限モードの種類と切り替えを参照）
esc実行中の応答を中断する（それまでの作業結果は残る）。ダイアログ表示中は中断ではなくダイアログを閉じる
ctrl+c実行中の操作を中断する。何も実行していないときは 1 回目の押下で入力中のプロンプトをクリアし、2 回目で Claude Code を終了する
ctrl+v（効かない場合は alt+v）クリップボードの画像を貼り付ける。[Image #N] という形で挿入され、あとから位置を参照できる
alt+p入力中のプロンプトを消さずにモデルを切り替える（/model を打たずに済む）

プロンプト冒頭の記号・スラッシュコマンド

操作内容
@ファイルパスの補完を呼び出す。参照したいファイルをその場で指定できる
! + コマンドシェルモードに切り替えてコマンドをそのまま実行する（例: !curl http://localhost:8080/actuator/health）。出力はコンテキストに読み込まれ Claude が応答するため、通常のプロンプト 1 回分のコストがかかる
/clear会話履歴をリセットする（別のタスクに移るとき）
/compact長くなった会話を要約して続行する
/contextいまコンテキストを何が占めているかを表示する
/rewind会話とコードを直前のチェックポイントに戻す（esc の 2 回連打でも開ける）
/usage使用量と上限を確認する。表示内容は使用量と上限を確認するで詳しく説明する
/helpヘルプを表示する

権限モードの種類と切り替え​

Claude Code は、ツール実行やファイル編集をどこまで確認なしに進めてよいかを「モード」で切り替えます。shift+tab を押すたびに次のモードへ順に切り替わり、画面下部のステータス表示で今どのモードかが分かります。

モードステータス表示挙動向いている場面
Manual（既定）⏸ manual mode onファイルの読み取りのみ自動承認し、編集やコマンド実行は都度確認を求める通常の作業。挙動を逐一確認したいとき
Accept edits（自動承認）⏵⏵ accept edits onファイル編集や一般的なファイル操作コマンドを自動承認するあとで差分をまとめて確認する前提で、細かい確認を省きたいとき
Plan（プランモード）⏸ plan mode onコードの変更を一切行わず、調査と計画提示だけを行う。計画に納得して抜けるまで実装には進まない探索→計画→実装→コミット の計画フェーズ。影響範囲が広い変更、進め方に確信が持てないとき
Auto（自動モード）⏵⏵ auto mode on実行内容を都度判定し、問題ないと判断したものは自動承認する。判定に迷う操作は通常どおり確認を求める確認の手間を減らしたいとき。判定基準は挙動として固定されていないため、想定外の操作がないか差分は確認する

利用できるモードの組み合わせや切り替え順は、アカウント種別や設定によって変わることがあります。表示されるモード名が上記と異なる場合は、ステータス表示の文言を優先してください。

Bypass permissions モードは研修課題では使わない

--dangerously-skip-permissions フラグ、または設定で明示的に有効化した場合にのみ現れる、全ての確認をスキップするモードです（ステータス表示: ⏵⏵ bypass permissions on）。root/sudo 権限下では起動できない安全策が入っていますが、それ以外の環境では実行内容の妥当性チェックが一切効かなくなります。研修課題では使わないでください。

VS Code 拡張でも同じモードを切り替えられる

CLI の shift+tab に相当する操作は、VS Code 拡張ではステータスバー下部のモード表示をクリックすることで行えます。モード名・挙動は CLI と共通です。

モデルの選択と使用量の管理​

モデルの種類と使い分け​

Claude Code は複数のモデルから選んで実行できます。モデルごとに推論の精度と、応答速度や消費するトークン量のトレードオフが異なるため、タスクの性質に応じて選び分けます。
/model では fable opus sonnet haiku という別名で指定でき、それぞれ各系列の最新バージョンに解決されます。

モデル特徴向いている場面
Fable最も高性能。長時間の自律的な作業や、事前調査・自己検証を要する大きなタスクに強い一区切りでは終わらない規模の作業（下記のとおり追加課金が必要な場合があります）
Opus複雑な推論に強いが、応答時間とトークン消費が大きい設計方針の検討、影響範囲が広い変更の計画
Sonnet精度とコストのバランスが良く、標準的な選択肢日常的な実装や修正のほとんど
Haiku最も高速で低コストだが、推論力は限定的で、単純なタスク向き定型的な小タスク、サブエージェントへの委譲

本リポジトリでは、Sonnet を基本モデルとする方針を採ります。日常的な実装や修正のほとんどは Sonnet の精度で足り、Opus に比べて応答時間とコストを抑えられるためです。
.claude/settings.json の model: sonnet がこの方針を対話セッションの既定として反映しており、学習者が個別に切り替えない限り Sonnet が使われます（advisorModel: opus は advisor ツール専用の指定で、この既定とは別に扱われます。言語・モデル設定を参照）。

Fable は追加課金（usage credits）が必要になる場合があります

Fable はどのアカウント種別でも既定のモデルにはならず、/model fable で明示的に選んだときだけ使われます。
プランとシート種別によっては、Fable の利用がプランに含まれる利用枠ではなく usage credits（追加課金）から引き落とされます。 その場合はモデル選択画面の Fable の行に「Requires usage credits」と表示され、対話セッションでは課金前に確認プロンプトが出ます。usage credits が有効になっていない環境では選べません。
研修課題は Sonnet を基本に進めてください。Fable を試したい場合は、費用が発生しうることを理解したうえで運営者に相談してください。

モデルを切り替える​

セッション中に /model コマンドを実行すると、対話形式でモデルを切り替えられます。
基本モデル（Sonnet）から恒久的に変更したい場合は /config から設定します（設定は settings.json の model キーに保存されます）。

Opus に切り替える場面

STEP-03 のように既存パターンをなぞる実装では Sonnet で十分ですが、AI-DLC の INCEPTION フェーズ（標準開発フロー）のように設計方針そのものを検討する場面では、Opus に切り替えると精度が上がることがあります。切り替えはそのタスクに限った一時的な操作とし、終わったら Sonnet に戻します。

応答を速くする（/fast）​

/fast は Opus の応答を最大 2.5 倍速くするモードです。モデルが変わるわけではなく、同じ Opus をレイテンシ優先の構成で動かすもので、品質は変わりません。

ただし標準の Opus よりトークン単価が高く（入力 $10 / 出力 $50 per MTok）、Pro・Max・Team・Enterprise ではプランの利用枠ではなく usage credits（追加課金）からのみ引き落とされます。usage credits を有効にしていない場合、/fast は使えません。
対応モデルは Opus 5 と Opus 4.8 のみで、VS Code 拡張では使えません（CLI 専用）。会話の途中で有効にすると、その時点までの全コンテキストに対して fast モード価格の未キャッシュ入力料金が一度かかるため、使うならセッションの最初に有効にします。

研修課題では常用しません。Fable と同じく、費用が発生しうることを理解したうえで必要な場面に絞って使ってください。

使用量と上限を確認する​

サブスクリプション（Pro・Max・Team・Enterprise）の利用上限には 2 種類あります。

  • 5 時間のローリングウィンドウ（セッション上限）
  • 週次のウィンドウ

どちらかに達すると、そのウィンドウがリセットされるまで新しいメッセージを送れません。この上限はモデル横断で共有されるため、/model でモデルを変えても回復しません（「Opus の上限に達しました」というモデル個別のメッセージの場合は、切り替えれば作業を続けられます）。

セッション中に /usage を実行すると、次の内容を確認できます。

表示内容
プラン利用量のバー上限に対する残量
利用の内訳スキル・サブエージェント・プラグイン・MCP サーバーごとの割合
挙動フラグ長いコンテキストやキャッシュミスなど、最近の利用の 10% 以上を占める要因

内訳は d / w キーで直近 24 時間と直近 7 日を切り替えられます。これは表示期間の切り替えであり、上記の利用上限のウィンドウ（5 時間・週次）とは別物です。
画面上部の Session ブロックはトークン数と概算金額を表示しますが、これは API 利用者向けの数値で、サブスクリプションの請求とは対応しません。また内訳はこのマシンのローカルなセッション履歴から計算した概算で、他のデバイスや claude.ai での利用は含まれません。

本リポジトリの statusline での確認

.claude/scripts/statusline-command.sh は、5 時間と週次のレートリミットを JST 表示で画面下部に常時表示する設定になっています（Claude Code のその他の設定）。
/usage を都度実行しなくても残量を把握できます。

効果的なプロンプトの書き方​

3 つの原則を意識すると、回答の精度が大きく変わります。

  1. コンテキストを先に伝える：何をしようとしていて、どこまで分かっているかを示す
  2. ゴールと制約を具体的に：完了条件、触ってよい範囲、守るべき規約を示す
  3. 仕様書を参照させる：本リポジトリでは docs-next/docs/spec/ が真実の源であり、実装の根拠は仕様に求める
Good な例
予約一覧画面に「ステータスで絞り込むフィルタ」を追加したい。
仕様は docs-next/docs/spec/screen-spec.md の予約一覧の節を参照して。
バックエンド API（GET /api/reservations）は status クエリパラメータを
すでにサポートしているので、フロントエンドのみ変更して。
既存のリソース一覧のフィルタ実装と同じパターンに合わせること。

目的、仕様の参照先、変更範囲、合わせるべき既存パターンが明確に伝わります。

Bad な例
フィルタ機能を作って

どの画面か、何で絞り込むか、どこまで作るかが不明で、意図と違う実装になりやすくなります。

回答を鵜呑みにせず、根拠を確認する

「その仕様はどこに書いてある？」「変更したファイルの diff を見せて」のように根拠を確認する習慣をつけると、AI の誤り（ハルシネーション）に気づきやすくなります。

GitHub 上で Claude を呼び出す​

ここまでは手元の Claude Code の話ですが、GitHub の Issue・PR からも Claude を呼び出せます。コメントの書き出しによって起動するものが変わります。

コメントの書き出し起動するものできること
@claude pr-reviewAI レビューPR を3観点で判定してコメントする。コードの変更はしない
@claude（pr-review を伴わない）汎用の Claude質問への回答、調査、修正コミットまで行える

@claude pr-review は AI レビュー専用です。タスク完了の判定に使うもので、この用途では Claude にコードを触らせません（AI レビューとの対応）。

@claude だけを書いた場合は汎用の Claude が応答します。 「このエラーの原因を教えて」「このテストを追加して」のように、Issue・PR 上で相談したいときに使います。こちらはコミットまで行えるため、生成された変更は必ず自分で読んでから扱ってください。

どちらも投稿してから応答まで数分から15分程度かかります。すぐに反応がなくても失敗ではないので、同じコメントを連投せずに待ってください（連投しても同一 PR に対する AI レビューは順番待ちになるだけです）。応答がないまま長時間経過した場合の確認手順は AI レビュー関連のトラブルシューティング を参照してください。

AI 利用ポリシー​

本リポジトリでの Claude Code の使い方について、何を任せてよく何を任せないかの線引きです。
表の✗項目のうち、機密情報の入力は本リポジトリでは実際に発生しません（架空のデータしか扱わないため）。それでも書くのは、ここで線を引く感覚を持っておくと、実在の機密情報を扱う実務でそのまま使えるからです。
一方、生成コードを検証せずコミットしない、という点は本リポジトリでも実際に効いているルールで、セルフレビューと理解度チェックの前提になっています。

利用範囲​

用途可否
コード補完・実装支援○
設計・仕様・エラーメッセージの解説○
テストコードの生成○
ドキュメント生成・要約○
顧客情報・認証情報・社外秘文書の入力✗
生成コードの無検証コミット✗
機密情報を入力しない

顧客情報、認証情報（パスワード、API キー、トークン）、社外秘の文書を、プロンプトやファイルとして AI に渡すわけにはいきません。
本リポジトリでも .env.local 等の値を会話に貼り付けない習慣をつけておいてください。

AI 生成コードを無検証でコミットしない

生成されたコードは必ず自分で読み、動作確認（テスト実行、画面確認）をしてからコミットしてください。理解できないコードをそのままコミットするわけにはいきません。
PR に @claude pr-review とコメントすると、この確認を助ける理解度チェックの4択問題が得られます。回答すると、正誤にかかわらず全問の解説が返ります。誤答してもタスク完了は妨げられませんが、誤答した事実は PR コメントに記録として残ります（セルフレビューしてマージする、ADR-026）。

責任とPRでの明記​

生成コードの責任はマージした開発者が負う

「AI が書いたから」は不具合の言い訳になりません。PR を出した時点で、そのコードの品質はあなたの責任です。

PR には AI を活用した箇所の明記が必須です。
.github/PULL_REQUEST_TEMPLATE.md の「AI ツールを使った箇所」欄に、AI に提示させた計画（Workflow Planning、または /aidlc を使わない場合は plan mode）、補完や生成に使った箇所を記入してください（詳しい手順は 標準開発フロー を参照）。
