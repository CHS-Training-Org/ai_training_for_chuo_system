ADR-034 — 運用プロセス：結合テストのワークフローを簡易な状態管理とダッシュボードで進める

Status​

Accepted（2026-09-27）。下の追記4件は 2026-10-04 に Accepted とした。

本文は 2026-09-27 時点の決定である。段階の数（4つから3つ）、案内スキルが AI の作業を行う範囲（試験観点だけから全段階）、AI がテストを実行するかどうかは、追記で変えた。本文と追記が食い違う場合は、追記を正とする。

Context​

結合テストは、試験観点、試験ケース、テストコード、実行の4つの段階で作る。各段階で AI が成果物を出力し、学習者が関門でレビューして確定させる（結合テストのワークフロー）。

この流れを動かしてみて、2つの問題が出た。1つは、今どの段階にいて次に何をするかが分からないことである。試験観点は観点一覧の6章「レビュー記録」の記入で見分けられるが、試験ケース以降は確定を記録する場所がない。もう1つは、観点一覧が Markdown の表で出力され、レビューしにくいことである。

実装の側には AI-DLC のエンジン（ADR-020）があり、進捗トラッカー、追記専用の監査ログ、ステージごとの承認ゲートを持つ。E2E テストの側には、これに当たる仕組みがない。

ADR-032 は、9月末までに運用に載せるために「用意する機構が最も少ない選択」を取った。この期限の前提は、その後外れている。

検討した候補：

候補今どこにいるかが分かるかレビューのしやすさ用意する機構
仕組みを作らず、ドキュメントの見分け方の表で判断する試験観点の段階だけ変わらないなし
AI-DLC のエンジンに E2E テストのステージを足す分かる変わらない大きい。エンジンは実装の流れと結びついており、ADR-032 が必須フローから切り離した本チュートリアルとぶつかる
AI-DLC の考え方を借りた簡易な仕組みを別に作る分かる画面で改善できる状態ファイル、案内スキル、ダッシュボード

Decision​

AI-DLC の進捗管理と承認ゲートの考え方を借り、簡略化した仕組みを E2E テスト専用に作る。

AI-DLC の仕組みE2E テストでの簡易版
進捗トラッカー（全体で1つ）画面ごとの状態ファイル Docs/test/<スラッグ>/state.json。4つの段階それぞれの状態（未着手、レビュー待ち、差し戻し、確定）を持つ
監査ログ（入出力を逐語で追記）状態ファイルの中の記録。誰が、いつ、どの段階で、何をしたか（AI の出力、学習者の確定と差し戻し）と、その理由だけを残す
3フェーズと条件付きのステージ4つの段階に固定する。条件分岐はしない
ステージごとの承認ゲート4つの関門。確定と差し戻しはダッシュボードの画面操作だけで書き、AI は「レビュー待ち」までしか進めない
エンジン本体のスキル案内スキル e2e-workflow。状態を読んで次の作業を示し、試験観点の段階の AI 作業だけを実行する

採らないもの：拡張機能、出力の深さの段階、質問をファイルに書く方式、作業場所の自動判定、作業単位の分割。

  • 状態ファイルの読み書きは1か所に集める：scripts/e2e-workflow/state.mjs が状態ファイルの検証と更新を担い、案内スキルとダッシュボードの両方がこれを通す。コマンドから行えるのは、作成、表示、「レビュー待ち」への更新だけで、確定と差し戻しのコマンドは用意しない。
  • ダッシュボードはローカルで動かす：scripts/e2e-workflow/server.mjs を devcontainer の中で起動し、VS Code のポート転送で開く（転送の設定は 2026-10-04 の追記）。依存パッケージを使わず Node の標準モジュールだけで書く。devcontainer の Python は標準ライブラリがそろっておらず、学習者の環境で動かないためである。
  • 正本はリポジトリのファイルに置く：状態ファイルと成果物は作業ブランチに置き、ダッシュボードはそれを表示して判断を書き戻すだけにする。成果物を main に入れない決まり（ADR-032 の追記）はそのまま守られる。
  • 今回作る範囲は試験観点の段階まで：状態ファイルは4段階すべての欄を持つが、案内スキルが AI の作業を実行するのは試験観点の段階だけにする。試験ケース以降は、手順ページと成果物の形がまだ新しい流れに合っていないため、手順ページを案内するだけにとどめる。
  • 差し戻したら AI が直す：学習者が理由を付けて差し戻すと、案内スキルが理由をもとに観点一覧を直し、状態を「レビュー待ち」に戻す。一から作り直さないのは、AI の出力が実行のたびに変わるため、作り直した一覧が学習者のレビューした一覧と別物になるからである。指摘から ID で参照されるため、既存の ID も振り直さない。
  • 仕様の食い違いへの回答はダッシュボードで選ぶ（2026-09-30 追記）：回答は状態ファイルに保存し、差し戻しと一緒に AI に渡す。AI が選ばれた回答の観点を観点一覧に入れ、4.1 の「回答」列を埋める。回答がすべて反映されるまでは確定できない。回答の保存も state.mjs を通し、書けるのはダッシュボードの操作だけとする。

Consequences​

  • 画面ごとに、今どの段階にいて、次に誰が何をするかを、ダッシュボードと案内スキルの両方で確かめられる。
  • 確定と差し戻しが、日時と理由付きで記録に残る。
  • 確定を学習者だけに限るのは、指示と構成による分担であり、機械的には強制していない。AI が状態ファイルを直接書き換えれば防げない。
  • 観点一覧は Markdown のままで、ダッシュボードでは読み取り専用で描画する。回答欄は、4.1 の表の「A. …／B. …」の形の選択肢を読み取って出す。形式が崩れると回答欄が出ないため、出力様式でこの形を固定している。
  • 学習者のレビュー記録（当初の観点一覧6章）は、2026-09-30 にやめた。問題のない行に印を付ける記録は負担が大きく、指摘は差し戻しの理由に、回答と確定の操作は状態ファイルの記録に残るためである。
  • 観点一覧の保存先を Docs/test/<スラッグ>/perspectives.md に変えた。
  • ダッシュボードは Markdown の描画に CDN のライブラリを使う。読めない環境では、生のテキストを表示する。記録の日時は UTC で保存し、日本時間で表示する。
  • 試験ケース以降の段階の手順と成果物の置き場所、その段階で差し戻したときに AI に直させる手順は、まだ決めていない。未決事項は Playwright 導入の進行状況 で管理する。

追記（2026-10-02）試験ケースの段階を仕組みに載せる​

Context（追記理由）​

Decision は「今回作る範囲は試験観点の段階まで」とした。その後、ワークフロー全体を先に形にする方針になり、試験ケースの段階を同じ仕組みに載せることにした。従来の試験ケースの手順ページは、観点一覧を貼り付ける固定のプロンプトで展開させ、学習者は一覧全体を一度だけ確認する形だった。この形は、試験観点の段階で採った「すべての行を仕様書と突き合わせる」「期待結果は仕様の言葉の範囲で書く」と食い違っていた。

Decision（追記）​

この追記は運営者の作業の中で案として書き、2026-10-04 に承認した。

試験ケースの段階も、試験観点の段階と同じ形（新規作成のスキル、状態ファイル、ダッシュボード、差し戻したら AI が直す）で進める。

  • 展開は新しいスキル generate-test-cases が行い、Docs/test/<スラッグ>/cases.md に出力する。入力は確定した観点一覧の2章だけで、3章と 4.2 は展開しない。実装コードは読まない。
  • 日時は割り当て枠からの相対で、テストデータは条件だけで書く。利用目的は、印（[e2e]）で始まる「テスト用の利用目的」と書く。具体的なデータとの対応づけはテストコードの段階に回す。
  • 仕様書に値がなく AI が選んだ値のうち、別の値にするとテストの結果か見つけられる不具合が変わるものは「AI が仮に決めた値」に、ケースにできなかった観点は「試験ケースにできなかった観点」に書き出し、学習者が判断する。
  • 観点一覧の2章のすべての観点が、試験ケースか「試験ケースにできなかった観点」のどちらかに載っていなければ、確定できない。この照らし合わせは state.mjs が機械的に行う。AI が数えた件数を信じないためである。
  • 差し戻したら、案内スキルが指摘に沿って試験ケース一覧を直す。確定した観点一覧は書き換えない。

Consequences（追記）​

  • 試験観点と試験ケースの2つの段階で、出力から確定までをダッシュボードで進められる。
  • 試験ケースのレビューで観点そのものの誤りに気づいても、確定した試験観点の段階を開き直す操作はまだない。テストコードと実行の段階も、手順ページの案内だけのままである。

追記（2026-10-03）テストコードの段階を仕組みに載せる​

Context（追記理由）​

試験ケースの段階に続いて、テストコードの段階を同じ仕組みに載せる。従来の手順ページは、試験ケースを貼り付ける固定のプロンプトでテストコードを書かせ、決まった5点だけをレビューする形だった。テストコードの段階には、前の2つの段階にない事情が3つある。実装を読まないと要素を指定できないこと、生成したテストが pnpm test:e2e のテスト対象になりうること、前提データ（他のユーザーの予約、初期データにない無効なリソース）を用意する手段がないことである。

Decision（追記）​

この追記は運営者の作業の中で案として書き、2026-10-04 に承認した。

テストコードの段階も、試験観点と試験ケースの段階と同じ形で進める。

  • 変換は新しいスキル generate-test-code が行う。出力はテストコード frontend/tests/e2e/workflow/<スラッグ>.spec.ts と、判断が要るところだけを書いた説明 Docs/test/<スラッグ>/code.md である。
  • 実装は、要素の指定と前提データの用意にだけ読む。期待結果は試験ケースからだけ取り、実装に合わせて弱めない。仕様と実装で名前が違うところは説明に書き出し、学習者が判断する。
  • テスト名はケース ID で始める。試験ケースのすべてが、テストか「テストコードにできなかったケース」のどちらかになければ確定できない。test.skip で止めたテストは数えない。この照らし合わせは state.mjs が機械的に行う。
  • 生成したテストは学習者の成果物として tests/e2e/workflow/ に置き、普段の pnpm test:e2e には含めない。E2E_WORKFLOW=1 を付けたときだけ有効になる Playwright の設定（workflow）で動かし、pnpm test:e2e:workflow を用意する。
  • 前提データを API で用意する補助関数 tests/e2e/helpers/setup-data.ts を、運営者の機構として用意する。予約は後片付けの印のある利用目的でしか作れないようにし、承認と却下は ADMIN で行う。初期データにない無効なリソースは、名前で見分けて1件だけ作る。
  • AI はテストを実行しない。読み込めることだけを確かめる。実行と失敗の切り分けは実行の段階で行う（次の追記で、テストコードを作った AI が続けて流すように変えた）。
  • 生成したテストは、結合テスト専用のデータベース（bookflow_e2e）で動かし、テストごとに初期データ（scripts/seed.sql）だけの状態に戻す。test は tests/e2e/helpers/workflow-test.ts から取り、後片付けは書かない。学習者が証拠の画面で判断するとき、ほかのテストや過去の実行のデータが写らないようにするためである。開発用のデータベースは戻さない。

Consequences（追記）​

  • 試験観点からテストコードまでの3つの段階を、ダッシュボードで進められる。
  • 補助関数は実際のバックエンドで動くことを確かめたが、生成したテストの実行結果は実行の段階で初めて分かる。
  • 生成したテストは、専用のデータベースを1本ずつ戻しながら流すので、並列には流せない。1回の初期化は0.3秒ほどである。
  • 専用のデータベースにつないだバックエンドを別に起動する手間が増える。開発用のデータベースにつないだまま流すと、テストは最初に止まる（開発用のデータベースが初期データとまったく同じ状態のときだけは見分けられない）。
  • 生成したテストを main に入れない決まりは、置き場所を分けたことで見分けやすくなったが、機械的には止めていない。

追記（2026-10-03）テストの実行を仕組みに載せ、テストコードの段階とまとめる​

Context（追記理由）​

テストコードの段階を仕組みに載せたあと、学習者がテストコードの段階で何をレビューするかを見直した。学習者に生成したテストコードを読ませるのは、このチュートリアルの学習者にとって負担が大きく、読んだとしても確かめ方の十分さを見落としやすい。確かめ方が足りないテストは、画面の振る舞いが間違っていてもパスするからである。そこで、テストが何を確かめたか（テストコードから機械的に抜き出した確かめ。2026-10-04 の追記）と、テストを流して集めた証拠（期待結果を確かめた場所の画面と、テストが実際に使った値）を、試験ケースの期待結果と照らして判断する形にする。

そのため、テストコードの段階の関門は、流した結果がないと意味のある判断ができない。一方、実行の段階は当初の手順ページのまま、AI が開発用のデータベースで pnpm test:e2e を流して失敗を切り分ける形で、生成したテストを含まず、仕組みにも載っていなかった。

Decision（追記）​

この追記は運営者の作業の中で案として書き、2026-10-04 に承認した。

テストコードの段階と実行の段階を、1つの段階（テストコードと実行）にまとめる。段階は3つ、関門は3つになる。

  • AI（案内スキル e2e-workflow）は、テストコードを作ったあと、続けて環境を整えてテストを流し、フェイルしたケースに見立てを書いてから、学習者に渡す。環境は scripts/e2e-workflow/env.mjs が用意する（結合テスト専用のデータベースと、そこにつないだバックエンド）。開発用のバックエンドを止めるときは、学習者に確かめる。
  • テストは scripts/e2e-workflow/run.mjs が流し、結果と証拠（確認箇所の画面、フェイルした時点の画面、テストが使った値）を run.json に機械的に集める。AI の説明は混ぜない。結果は、パス、フェイル（期待結果と違った、途中で止まった、前提データを用意できなかった、環境が整っていない）、実行されていない、に機械的に分ける。
  • AI の見立て（実装の不具合の候補、仕様の仮回答による候補、テストの誤りの候補、環境の問題、判断できない）は、別のファイル triage.md に書き、ダッシュボードでは機械的な区分とは別の欄に出す。判断するのは学習者である。
  • 環境が原因で流れなかったものは、AI が環境を直して流し直す。テストの誤りに見えるものは、AI は直さずに渡す。学習者が証拠を見て差し戻したときに、AI がテストコードを直して流し直す。AI が自分の判断でテストを直すと、期待結果に合わせてテストを弱めたことに学習者が気づけないためである。
  • 状態を「レビュー待ち」にできるのは、流した結果が今のテストコードのもので、全ケースが実行され、フェイルしたケースすべてに同じ実行への見立てがあるときだけとする。関門3 を確定できるのは、ケースとの対応に漏れがなく、流した結果が今のテストコードのもので、実行されていないケースがないときだけとする。どちらも state.mjs が機械的に確かめる（2026-10-04 の追記で、環境が整っていなかったケースと、フェイルしたケースごとの判断も条件に加えた）。
  • 学習者が実装の不具合だと判断したケースは、確定するときに指摘の欄に書いて記録に残す（2026-10-04 の追記で、ケースごとに原因と根拠を選んで書く形に変えた）。

既存の状態ファイルは、次の対応で一度だけ移した。テストコードと実行の段階がどちらも確定なら、まとめた段階は確定とする。テストコードだけが確定で、流した結果があればレビュー待ち、なければ未着手とする。実行の段階の記録は、まとめた段階の記録にする。

Consequences（追記）​

  • 学習者はテストコードを読まずに、説明の判断と実行の証拠だけで、テストコードと実行の段階を確定できる。
  • 関門が1つ減る。テストコードを確定してから流した結果で誤りが分かり、確定済みの段階へ戻れなくなる、ということが起きない。
  • AI がバックエンドを起動するので、devcontainer のメモリを多く使う。バックエンドの Java のヒープに上限を付けて起動する。
  • ADR-032 は、実行と失敗の切り分けを学習者の作業と定めていた。この追記の承認に合わせて、ADR-032 の追記で到達目標と担い手を改めた。

追記（2026-10-04）関門3 の判断、確かめの抜き出し、前の段階に戻す操作​

Context（追記理由）​

PR のレビューで、関門3 について3つの問題が見つかった。1つ目は、フェイルしたケースの原因を判断しなくても確定できたことである。チュートリアルの中心の判断が任意になっていた。2つ目は、実行の証拠だけでは、テストの確かめが足りているかを判断できないことである。証拠の画面は今回の実行の様子しか示さず、たとえば「申請できないこと」をマイ予約一覧に行がないことで確かめるテストは、申請ボタンを押せていなくても同じ画面になる。3つ目は、後の関門で前の段階の誤りに気づいても、戻す操作がなく、学習者が先へ進めなくなることである。

Decision（追記）​

  • 関門3 で、フェイルしたケースごとに原因と根拠を書く：学習者は、ダッシュボードの証拠の表で、フェイルしたケースごとに原因（実装の不具合、仕様の仮回答による、テストの誤り、前の段階の誤り）を選び、根拠を1行書く。すべてそろい、「テストの誤り」と「前の段階の誤り」がないときだけ確定できる。判断の対象は、送られてきた内容ではなく流した結果から state.mjs が決める。判断は確定と差し戻しの記録に残り、差し戻したときは理由に入って AI に渡る。ダッシュボードは、AI の見立てで判断を埋めておくことはしない。
  • 「仕様の仮回答による」を区別する：観点の段階で仕様の食い違いに仮に選んだ回答と実装が違うことによるフェイルは、実装の不具合と区別する。AI の見立てにも「仕様の仮回答による候補」を足す。
  • 環境が整っていないケースは渡さない：機械的な区分が「環境が整っていない」のケースが残っている間は、AI は学習者に渡せず（ai-output を受け付けない）、学習者も確定できない。
  • テストの確かめを機械的に抜き出す：生成したテストの expect には、何を確かめるかの説明を文字列で添える。ダッシュボードは、テストコードから説明と照合の種類（件数が0、表示されている など）を機械的に抜き出し、「このテストが確かめたこと」として期待結果の横に出す。説明は AI が書いた文で、照合の種類は機械的に決めた言葉である。学習者は、確かめが期待結果に足りているかをこれで判断する。「〜できないこと」を操作のあとで別の画面で確かめるケースでは、操作した直後の画面も証拠に撮る。
  • 前の段階に戻すのは運営者：学習者は、後の関門で前の段階の誤りに気づいたら差し戻し、理由に「前の段階の誤り：ID」と書いて運営者に相談する。AI はこの指摘を受けると、成果物を直さずに止まる。運営者が認めたら、node scripts/e2e-workflow/state.mjs reopen <画面> <段階> <理由> でその段階を差し戻しに戻す。後の段階は未着手に戻し、成果物は .tmp/e2e-workflow/reopened/ に移す。
  • ダッシュボードのポートを転送する：2026-10-03 に、ポート 3130 を devcontainer の転送設定に加えた。起動はコンテナの起動時には行わず、案内スキルか学習者が行う。結合テストのチュートリアルに取り組むのは一部の学習者だけのためである。

Consequences（追記）​

  • 関門3 の判断が記録に残り、確定した段階の記録で、どのケースをどの根拠で実装の不具合と判断したかを後から確かめられる。
  • フェイルしたケースが多い画面では、学習者の入力の手間が増える。入力は、画面を読み込み直しても消えないよう、そのブラウザに一時的に残す。
  • 確かめの抜き出しは、テストの中に直接書いた expect だけを対象にする。補助の関数の中の expect や、説明を変数で渡した expect は抜き出せないため、ダッシュボードが「決まりから外れた書き方」として知らせる。
  • 前の段階に戻すと、後の段階は作り直しになる。戻すかどうかは運営者が判断する。

追記（2026-10-07）前の段階に戻すのを学習者の判断にする​

Context（追記理由）​

教材のレビューで、前の段階の誤りを運営者に相談させても、運営者にできることは戻すコマンドを打つことだけだと指摘された。誤りかどうかの判断材料は学習者の手元の成果物にあり、相談を挟むと学習者の手が止まるだけになる。

Decision（追記）​

  • 前の段階に戻すのは学習者の判断：2026-10-04 の「前の段階に戻すのは運営者」を改める。学習者は、後の関門で前の段階の誤りに気づいたら差し戻し、理由に「前の段階の誤り：ID」と書く。案内スキルは成果物を直さずに止まり、誤りを確かめた結果と、戻すと後の段階が作り直しになることを示して、戻すかを学習者に尋ねる。学習者が戻すと答えたときだけ、案内スキルが state.mjs reopen でその段階を差し戻しに戻す。記録の by は learner にする。

Consequences（追記）​

  • 前の段階の誤りに気づいてから直し始めるまでに、運営者を待たなくてよくなる。
  • 戻すかどうかを AI が決めないよう、スキルで学習者の答えを待つことを定める。AI が reopen を勝手に使うことまでは、機械的には防いでいない。
