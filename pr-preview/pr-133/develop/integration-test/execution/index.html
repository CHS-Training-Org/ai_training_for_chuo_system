テストを実行する

このページは、Playwright コードを生成するに続く、結合テストのワークフローの3つ目の段階（テストコードと実行）の後半です。AI は、テストコードを作ったあと、続けてテストを流し、実行の証拠を集めて、フェイルしたケースに見立てを書いています。学習者は、その証拠を試験ケースの期待結果と照らし、テストが期待結果を本当に確かめたか、フェイルの原因は何かを判断して、関門3 で確定か差し戻しを選びます。

学習目標​

このページを終えると、次ができるようになります。

  • テストが確かめたこと（テストコードから抜き出した確かめ）と実行の証拠（見る場所の画面と、テストで使った値）を期待結果と照らし、確かめが足りているか、期待結果が成り立っていたかを判断できる
  • フェイルしたケースの原因（実装の不具合、仕様の仮回答による、テストの誤り、前の段階の誤り）を、AI の見立てを手がかりに、証拠と仕様で判断し、根拠を書ける
  • 関門3 で確定か差し戻しを選び、実装の不具合だと判断したケースを記録に残せる

ゴール​

テストコードと実行の段階を確定させます。

AI と学習者の役割分担​

AI がやること​

テストを流す作業は、案内スキル（e2e-workflow）が行います。

AI がやること中身
環境を整える結合テスト専用のデータベース（bookflow_e2e）を用意し、バックエンドをそこにつないで起動する。開発用のバックエンドが動いていれば、止めてよいかを学習者に確かめる
テストを流すnode scripts/e2e-workflow/run.mjs で流し、結果と証拠を集める。環境が原因で流れなかったものは、環境を直して流し直す。テストの誤りに見えるものは、ここでは直さない
見立てを書くフェイルしたケースごとに、実装の不具合の候補か、テストの誤りの候補かなどの見立てと、その根拠を Docs/test/<画面>/triage.md に書く

テストの誤りに見えても AI が直さずに渡すのは、直すかどうかを証拠で決めるのが学習者だからです。AI が自分の判断でテストを直して流し直すと、期待結果に合わせてテストを弱めたことに、学習者が気づけなくなります。

学習者がやること​

学習者がやること手順
実行の証拠を見て、期待結果が成り立っているかを確かめる手順1
フェイルしたケースの原因を選び、根拠を書く手順2
前のページで書き留めた指摘と合わせて、確定か差し戻しを選ぶ手順3

手順1 実行の証拠を見る​

テストの結果は、最後まで期待結果どおりだった「パス」と、それ以外の「フェイル」で表します。フェイルには、期待結果と違ったものだけでなく、手順の途中で止まったものや、環境が整っていなかったものも含みます（下の区分の表）。テストが一度も動かなかったケースは「実行されていない」と表示し、このケースがあるうちは確定できません。

パスかどうかだけでは、テストが期待結果を本当に確かめたかは分かりません。確かめ方が足りないテストは、画面の振る舞いが間違っていてもパスするためです。そこで学習者は、テストコードを読む代わりに、次の2つを期待結果と照らして判断します。

  • このテストが確かめたこと：テストの中の確かめ（expect）を、ダッシュボードがテストコードから機械的に抜き出したものです。確かめごとに、何を確かめるかの説明と、照合の種類（「件数が 0」「表示されている」など）が並びます。説明の文は AI が書いたもので、照合の種類は機械的に決めた言葉です。
  • 実行の証拠：見る場所の画面と、テストが実際に使った値です。

2つを分けて見るのは、証拠の画面が今回の実行の様子しか示さないためです。たとえば「申請できないこと」をマイ予約一覧に行がないことで確かめるテストは、実装が正しく申請を止めた場合も、テストが申請ボタンを押せていなかった場合も、同じ画面になります。今回たまたま正しく動いていれば、確かめが足りないテストもパスします。確かめが足りているかは「このテストが確かめたこと」で、期待結果が今回成り立っていたかは証拠の画面で判断します。

生成したテストは、試験ケースの「見る場所」（マイ予約一覧、予約申請フォームのメッセージ欄など）を開いたところで画面を撮ります。あわせて、テストが実際に使った値（利用目的の文字列、選んだリソースの名前、日時など）を残します。試験ケースには「テスト用の利用目的」「枠の開始」のように書かれていますが、画面には実際の文字列や日時が出るためです。

「〜できないこと」を操作のあとで別の画面で確かめるケースでは、操作した直後の画面（「予約を申請する」を押した直後の予約申請フォームなど）も撮ります。ボタンを押せたか、入力が入っていたか、入力のチェックで止まっていないかを、この画面で確かめます。

テストは、1件ごとに、結合テスト専用のデータベースを初期データだけの状態に戻してから動きます。そのため、証拠の画面には初期データと、そのテストが作ったデータだけが写ります。ほかのテストや過去の実行のデータは写りません。

ダッシュボードでテストコードと実行の段階を開き、テストコードの説明の下にある「実行の証拠」まで進むと、ケースごとに「期待結果、見る場所、このテストが確かめたこと、このテストで使った値」「結果」「証拠の画面」が並びます。結果、画面、使った値、照合の種類は、実行とテストコードから機械的に集めたものです。AI が書いたものは、確かめの説明の文と、フェイルしたケースの「AI の見立て」です。各ケースについて、次を確かめます。

  • 「このテストが確かめたこと」が、期待結果を確かめるのに足りているか（たとえば期待結果が「重複のメッセージが出て、申請できない」なら、メッセージが出ていることと、マイ予約一覧に予約がないことの両方を確かめているか）
  • 確かめの説明と照合の種類が食い違っていないか（説明が「予約がない」なのに照合が「件数が 1」なら、説明か確かめのどちらかが誤っている）
  • 証拠の画面に、見る場所が写っているか
  • 使った値で行を探し、その画面で期待結果が成り立っているか（たとえば「申請できないこと」なら、マイ予約一覧に、使った値の利用目的の予約がないこと）
  • 使った値が、試験ケースの手順と入力どおりか（たとえば「リソースを選ばないと申請できない」なら、リソースが「（空欄）」になっていること）

パスしたケースも見ます。パスしたテストは誰も疑わないので、確かめ方が足りないことに気づけるのはここだけです。確かめが足りないケース、説明と照合が食い違うケース、証拠の画面がないケース、見る場所と違う場所が写っているケース、値を入力するケースなのに使った値がないケースは、差し戻しの理由に書きます。値を入力しないケース（画面を開いて見るだけのケースなど）には、使った値はありません。

関門の欄に「決まりから外れた書き方」が出ていたら、その文言をそのまま差し戻しの理由に貼ります。テストコードを読まなくても、AI が直せます。

フェイルしたケースは、テストがどこで止まったかによって、次の区分に機械的に分けて表示します。表の上のボタンで、区分ごとに絞り込めます。

区分意味見るところ
期待結果と違った見る場所までたどり着き、期待結果を確かめたところでフェイルした見る場所の画面で、期待結果と何が違うか
途中で止まった見る場所にたどり着く前に、手順の途中でフェイルした（画面の要素が見つからない、画面が移らない、時間切れなど）フェイルした時点の画面で、どこで止まったか
前提データを用意できなかったテストの前提になるデータ（既存の予約など）を API で作れなかったエラーの内容
環境が整っていないバックエンドやデータベースにつながらなかったAI が環境を直して流し直す。残っている間は学習者に渡されず、確定もできない

見る場所が2つあるケース（メッセージ欄とマイ予約一覧など）では、1つ目の期待結果と違っても、テストは2つ目の見る場所まで進んで画面を撮り、期待結果を確かめます。この場合、エラーは起きた順に並びます。区分は、最後のエラーで決めます。

区分は、実装の不具合か、テストの誤りかまでは決めません。それは手順2で判断します。

テストコードを流したあとで変えると、証拠は古いものとしてダッシュボードに表示され、流し直すまで確定できません。

手順2 フェイルしたケースの原因を判断する​

フェイルしたケースには、AI の見立てが付いています。見立ては次の5つのどれかです。

見立てAI がそう書くとき
実装の不具合の候補証拠の画面や応答が、試験ケースの期待結果と違う振る舞いを示している
仕様の仮回答による候補展開元の観点が、観点の段階で仕様の食い違いに仮に選んだ回答に基づいていて、その回答と実装の振る舞いが違う
テストの誤りの候補テストの操作や確かめ方が、試験ケースの手順や見る場所と合っていない
環境の問題流し直しても同じ止まり方をし、環境が原因と考えられるもの
判断できない証拠から、どれとも言えない

見立ての根拠に書かれた証拠を、自分で見て確かめます。そのうえで、ダッシュボードの証拠の表で、フェイルしたケースごとに「あなたの判断」の原因を選び、根拠を1行書きます。根拠には、見た証拠の画面や仕様書の記述を書きます（例：「証拠1がエラー画面。仕様は重複のメッセージを出すと書いている」）。原因は次の4つから選びます。

原因当てはまるときそのあと
実装の不具合展開元の観点に立ち返り、期待している振る舞いが仕様に照らして正しいと確かめた。テストは正しい確定できる。判断は記録に残る。このチュートリアルの範囲では、記録に残すところまでとする
仕様の仮回答による期待結果が、観点の段階で仕様の食い違いに仮に選んだ回答から来ていて、実装はもう一方の振る舞いをしている確定できる。判断は記録に残る
テストの誤りテストの操作や確かめ方が、試験ケースと合っていない確定できない。差し戻すと、AI が判断と根拠を読んでテストを直す
前の段階の誤り試験ケースや観点の入力値、期待結果のほうが誤っている確定できない。差し戻して運営者に相談する（下の「前の段階の誤りを見つけたとき」）

「仕様の仮回答による」を「実装の不具合」と区別するのは、仕様書の別の箇所が実装と同じ振る舞いを書いていることがあるためです。仮に選んだ回答は、観点の段階で「どちらを選んでも誤りではない」としたものです。その回答と実装が違うことは、どちらかの誤りではなく、仕様が決まっていないことの表れです。

AI の見立ては手がかりです。ダッシュボードは、学習者の判断を AI の見立てで埋めておくことはしません。

AI の見立てをうのみにしない

AI が「実装の不具合の候補」とした見立てが、実際には試験ケースの入力値や期待結果の誤りであることもあります。見立ては候補です。根拠の証拠と、仕様書を自分で確かめてから決めてください。

前の段階の誤りを見つけたとき​

確定した試験ケースや観点の誤りに気づいたときは、その段階の成果物を直接直すことはできません。今の段階の関門で差し戻し、指摘の欄に「前の段階の誤り：ID」と、何が誤りかを書いて、運営者に相談します。AI はこの指摘を受けると、成果物を直さずに止まります。

運営者が誤りを認めると、その段階を確定から差し戻しに戻します。AI がその段階を直し、学習者が確定し直したあと、後の段階は作り直しになります。運営者が「前の段階の誤りではない」と判断した場合は、その旨を AI に伝えると、残りの指摘だけを反映して進めます。

手順3 差し戻すか確定するかを選ぶ​

ダッシュボードの「関門3 テストの確定」の欄で、選びます。

  • 差し戻す：前のページ（テストコードの説明の判断）で書き留めた指摘があれば、指摘の欄にケースの ID を添えて書き、「差し戻す」を押します。手順2で選んだ原因と根拠も、差し戻しの理由に入ります。もう一度 /e2e-workflow を実行すると、AI が指摘と判断に沿ってテストコードを直し、流し直して見立てを書き直し、状態が「レビュー待ち」に戻ります。直った証拠を、もう一度手順1から確かめます。
  • 確定する：指摘がなく、フェイルしたすべてのケースの原因が「実装の不具合」か「仕様の仮回答による」で、根拠を書いたら「確定する」を押します。フェイルしたケースが残っていても、原因をこのどちらかと判断できていれば確定してかまいません。選んだ原因と根拠は、確定の記録に残ります。

次のどれかに当たると、「確定する」は押せません。関門の欄に理由が表示されます。

  • 試験ケースのうち、どのテストにも「テストコードにできなかったケース」にも載っていないものがある
  • 同じケース ID のテストが2本以上ある
  • 試験ケース一覧にないケース ID のテストがある
  • 流した結果がない、テストコードが流したあとで変わっている、実行されていないケースや環境が整っていなかったケースがある
  • フェイルしたケースのうち、原因か根拠がないものがある。または「テストの誤り」か「前の段階の誤り」を選んだものがある

結合テスト用のバックエンドは、流したあとも動いたままです。開発に戻るときは、node scripts/e2e-workflow/env.mjs down で止め、cd backend && ./gradlew bootRun で開発用のバックエンドを起動し直します。

ここまでの流れ​

このチュートリアルで、次の3つの段階を体験しました。

  1. 試験観点：何を確かめるかを、仕様書を根拠に決める
  2. 試験ケース：観点を、前提、手順と入力、期待結果、見る場所に展開する
  3. テストコードと実行：AI がテストコードを作って流し、学習者が実行の証拠で判断する

どの段階でも、AI が成果物を出し、学習者が関門で確定させます。学習者はテストコードを読みませんが、何を確かめるか（観点と期待結果）と、本当に確かめられたか（実行の証拠）は、自分で判断します。どこかの段階でつまずいたときは、試験観点を作るから読み直してください。

予約申請画面を終えたら、別の画面で同じ流れを試せます。始め方と、進めなくなりやすいところは、予約申請画面以外の画面で進めるにあります。
