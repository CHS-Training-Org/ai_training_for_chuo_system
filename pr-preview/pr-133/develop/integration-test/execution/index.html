テストの結果を確かめる

試験仕様書を作るで確定した試験ケースは、何を入れて、どこを見ればよいかまで決まっています。この段階では、AI がそれを Playwright のテストコードに変換し、続けてテストを流して実行のエビデンスを集めます。

ここでは、結合テストのワークフローの3つの段階のうち、3つ目の段階（テストコードと実行）の手順を説明します。学習者はテストコードを読みません。AI が書いたテストコードの説明と、実行のエビデンスを試験ケースの期待結果と照らして判断し、関門3 で確定か差し戻しを選びます。

学習目標​

このステップでは、次のことができることを目標とします。

  • テストで確かめた内容を期待結果と照らし合わせ、テストが期待結果を十分に確かめているかを判断できる
  • AI がテストを試験ケースどおりに書けなかった箇所や、テストにできなかったケースで、本来見つけるはずだった不具合が見逃されていないかを判断できる
  • テストがフェイルしたとき、原因が実装の不具合なのかテストの誤りなのかを、エビデンスと仕様から見分けられる

このステップの到達点​

テストコードと実行の段階が確定した状態になります。ここまで来ると、試験観点と試験仕様書による E2E テストの設計から、テストの実行と結果の確認までが完了します。

AI と学習者の役割分担​

AI がやること​

テストコードは generate-test-code スキルが作り、テストを流す作業は案内スキル（e2e-workflow）が行います。

AI がやること中身
テストコードを作るfrontend/tests/e2e/workflow/<画面>.spec.ts に、試験ケース1件につき1つのテストを書く。テスト名はケースの ID で始まる
テストコードの説明を書くDocs/test/<画面>/code.md に、コードではなく文章で、学習者の判断が要るところだけを書く（下の表）
環境を整えるブラウザが立ち上がらなければ入れる。結合テスト専用のデータベース（bookflow_e2e）を用意し、バックエンドをそこにつないで起動する。開発用のバックエンドが動いていれば、止めてよいかを学習者に確かめる
テストを流すnode scripts/e2e-workflow/run.mjs で流し、結果とエビデンスを集める。環境が原因で流れなかったものは、環境を直して流し直す。テストの誤りに見えるものは、ここでは直さない
見立てを書くフェイルしたケースごとに、実装の不具合の候補か、テストの誤りの候補かなどの見立てと、その根拠を Docs/test/<画面>/triage.md に書く

テストコードの説明（code.md）の章は次のとおりです。

章AI が書く内容
1章 テストデータの用意試験ケースのテストデータ（「承認が必要な有効なリソース」など）を、初期データから選ぶか、API で作るか
2章 仕様と実装で名前が違うところ試験ケースの名前と、テストコードで指定した実装の名前が違うところ
3章 ケースどおりに書けなかったところ近い書き方にしたところと、それで結果がどう変わりうるか
4章 テストコードにできなかったケーステストにできなかったケースと、その理由
5章 集計件数

ボタンや入力欄を指定するには実装に付いている名前やラベルが要るので、テストコードを書くタイミングで、AI は画面の実装を読みます。ただし、期待結果は試験ケースからだけ取ります。実装が試験ケースの期待結果を満たしていないように見えても、AI はテストを弱めず、試験ケースのとおりに書きます。

AI が自分の判断でテストを直して流し直すと、期待結果に合わせてテストを弱めたことに、学習者が気づけなくなります。そのため、流したあとでテストの誤りに見えても AI は直さずに渡し、直すかどうかは学習者がエビデンスで決めます。

学習者がやること​

学習者がやること手順
AI が文章で書いたテストコードの説明（code.md）を読み、2〜4章を判断する手順2
実行のエビデンスを見て、テストが期待結果を十分に確かめているか、画面が期待結果どおりに動いたかを判断する手順3
フェイルしたケースごとに、原因（実装の不具合、テストの誤りなど）をダッシュボードの選択肢から選び、そう判断した根拠を自分で1行書く手順4
テストコードと実行の段階を確定するか、テストコードを AI に差し戻すかを選ぶ手順5

テストコードを読まない理由​

このチュートリアルでは、テストコードを、テストの結果を得るための中間生成物として扱います。テストの品質は、投入した試験観点と試験ケースが仕様に照らして正しいか、そして最終的な生成物であるテストの結果が、期待結果を十分に確かめたうえで得られたものかで担保します。AI 駆動開発では、人がテストコードを1行ずつ読むのではなく、入力（何を確かめるか）と出力（本当に確かめられたか）で品質を担保する進め方が中心になっていくと考えています。

そのために、テストコードを読まなくても判断できる仕組みを用意しています。

コードを読む代わりに確かめるもの確かめる仕組み
ケースとテストの対応AI が渡す前に、テスト名の先頭のケース ID を機械的に数え、漏れや重複がないことを確かめる。test.skip や test.describe.skip で止めたテストは数えない
要素の指定方法、固定時間の待機、テストごとの初期化AI が渡す前に、決まりから外れた書き方がないかを機械的に確かめる。見つかれば、AI が直してから渡す
要素の名前や入力の値の誤り誤っていれば、流したときにテストがフェイルして分かる
テストの確かめ方が、期待結果に足りているかダッシュボードがテストコードから機械的に抜き出した「このテストが確かめたこと」を、期待結果と並べて見る（手順3）
期待結果が今回の実行で成り立っていたか確認箇所の画面と、テストで使った値（実行のエビデンス）を見る（手順3）

学習者が読むのは、AI がテストコードについて文章で書いた説明（code.md）です。説明には、仕様と実装の名前の違い、ケースどおりに書けなかったところ、テストにできなかったケースなど、人の判断が要ることだけが書かれています。テストコードそのものは読みません。

ダッシュボードには、テストコードの全文も折りたたんで表示されます。これは補足として置いているもので、判断には使いません。

手順1 AI にテストを作って流させる​

試験仕様書を確定させたあと、Claude Code に次のように依頼します。

/e2e-workflow 予約申請画面（/reservations/new）の結合テストを進めたい

案内スキル（e2e-workflow）が generate-test-code スキルを呼び出し、テストコードとその説明を保存します。続けて、結合テスト専用のデータベースとバックエンドを用意してテストを流し、フェイルしたケースに見立てを書きます。すべて終わると、テストコードと実行の段階は「レビュー待ち」になります。流すのに数分かかります。初めて流すときと、コンテナを作り直したあとは、テストに使うブラウザを入れるので、さらに数分かかります。

開発用のバックエンドが動いているときは、止めて結合テスト用に起動し直してよいかを、案内スキルが確かめます。結合テスト用のバックエンドは、流したあとも動いたままになります。

テストコードの置き場所

frontend/tests/e2e/workflow/ に置いたテストは学習者の成果物で、普段の pnpm test:e2e には含まれません。ワークフローでは、AI が node scripts/e2e-workflow/run.mjs で流し、エビデンスを集めます。pnpm test:e2e:workflow でも流せますが、エビデンスは集まらず、ダッシュボードにも出ません（BookFlow での実行）。

手順2 テストコードの説明を判断する​

ダッシュボードでテストコードと実行の段階を選ぶと、上からテストコードの説明（code.md）、テストコードの全文（折りたたみ）、実行のエビデンスの順に表示されます。説明の2〜4章を読み、判断します。AI がテストを試験ケースどおりに書けなかったり、ケースを外したりすると、本来そのケースで見つけるはずだった不具合が見逃されます。説明の3章と4章では、それが起きていないかを判断します。直してほしい点が見つかったら、ケースの ID と一緒に書き留めておき、手順5で差し戻しの理由にまとめます。

2-1. 仕様と実装で名前が違うところを判断する​

説明の2章には、試験ケース（仕様書）の名前と、実装の名前が違うところが並んでいます。たとえば、仕様書は「申請する」ボタン、実装は「予約を申請する」ボタン、のような違いです。

テストコードは実装の名前で要素を指定しているので、このままでもテストは動きます。学習者は、その違いが表記の揺れか、仕様と実装が食い違っている不具合かを判断します。不具合だと考えた場合は、そのことを書き留めておき、手順5で確定するときに指摘の欄に書いて記録に残します。

2-2. ケースどおりに書けなかったところを判断する​

説明の3章には、試験ケースの記述をそのままテストコードにできず、近い書き方にしたところが並んでいます。「結果への影響」を読み、その書き方でも、試験ケースで担保したかった機能や仕様を確かめられるかを判断します。

2-3. テストコードにできなかったケースを判断する​

説明の4章の各行について、AI がテストコードにできなかった理由が妥当かを判断します。妥当であれば指摘は不要です。テストにしてほしい場合は、テストにする方法（用意するデータや確かめる場所など）を書き留めておき、手順5で差し戻します。

手順3 実行結果を確認する​

テストの結果は「パス」と「フェイル」で表示されます。フェイルには、期待結果と違ったものだけでなく、途中で止まったものも含みます（下の区分の表）。

検証が不十分なテストは、画面の振る舞いが誤っていてもパスします。そのため、パスかどうかだけでは判断せず、ケースごとに次の2つを期待結果と照らし合わせます。

  • このテストが確かめたこと：テストの中の検証（expect）を、ダッシュボードがテストコードから機械的に抜き出したものです。検証ごとに、何を検証するかの説明と、照合の種類（「件数が 0」「表示されている」などの分類）が並びます。
  • 実行のエビデンス：試験ケースの確認箇所を開いたところで撮ったスクリーンショットと、テストが実際に使った値（利用目的の文字列、リソースの名前、日時など）です。試験ケースには「テスト用の利用目的」のようにしか書かれていないので、画面のどの行がそのテストのものかは、使った値で探します。

スクリーンショットは、その実行で画面がどうなったかしか示しません。たとえば「申請できないこと」を、マイ予約一覧に予約がないことで確かめるテストは、申請ボタンを押せていなくても同じ画面になります。そのため、検証が十分かは「このテストが確かめたこと」から、期待結果が成り立っていたかはスクリーンショットから、分けて判断します。このように操作のあとで別の画面を確かめるケースでは、操作した直後の画面のスクリーンショットも撮るので、ボタンを押せたか、入力のチェックで止まっていないかもあわせて確かめます。

各ケースで、次を確かめます。

  • 「このテストが確かめたこと」が、期待結果を検証するのに足りているか（期待結果が「重複のメッセージが出て、申請できない」なら、メッセージと、マイ予約一覧に予約がないことの両方を検証しているか）
  • 検証の説明と照合の種類が食い違っていないか
  • スクリーンショットが確認箇所の画面になっているか
  • スクリーンショットで、期待結果が成り立っているか
  • 使った値が、試験ケースの手順と入力どおりか

パスしたケースも確かめます。パスしたテストで正しい検証が行われたかを確認できるのは、人間だけです。問題があったケースは、ケースの ID を添えて書き留め、手順5で差し戻しの理由にまとめます。

フェイルしたケースは、テストがどこで止まったかで、次の区分に機械的に分けて表示されます。区分は、実装の不具合かテストの誤りかまでは決めません。それは手順4で判断します。

区分意味確認するところ
期待結果と違った確認箇所までたどり着き、期待結果を確かめたところでフェイルした確認箇所の画面で、期待結果と何が違うか
途中で止まった確認箇所にたどり着く前に、手順の途中でフェイルした（画面の要素が見つからない、画面が移らない、時間切れなど）フェイルした時点の画面で、どこで止まったか
前提データを用意できなかったテストの前提になるデータ（既存の予約など）を API で作れなかったエラーの内容
環境が整っていないバックエンドやデータベースにつながらなかった。AI が環境を整えて流し直すので、学習者に渡る前に解消されるなし（残っている間は、学習者に渡らない）

フェイルとは別に、「実行されていない」ケースもあります。テストが止められていたり、前の準備が失敗したりして、流れなかったものです。これも AI が流し直し、残っている間は確定できません。

期待結果によっては、確認箇所が2つになるケースがあります（「重複のメッセージが出て、申請できない」なら、メッセージ欄とマイ予約一覧）。この場合、1つ目で期待結果と違っても2つ目まで進み、区分は最後のエラーで決まります。テストコードを流したあとで変えると、エビデンスは古いものとして表示され、流し直すまで確定できません。

手順4 フェイルしたケースの原因を判断する​

フェイルしたケースには、AI の見立てが付いています。見立ては次の5つのどれかです。

見立て意味
実装の不具合の候補エビデンスの画面や応答が、試験ケースの期待結果と違う振る舞いを示している
仕様の仮回答による候補展開元の観点が、仕様の矛盾に対して試験観点の段階で仮に決めた回答をもとにしており、実装はその回答と違う振る舞いをしている
テストの誤りの候補テストの操作や確かめ方が、試験ケースの手順や確認箇所と合っていない
環境の問題流し直しても同じ止まり方をし、環境が原因と考えられるもの
判断できないエビデンスから、どれとも言えない

見立てには根拠が添えられています。根拠が正しいかをスクリーンショットと仕様書で確かめたうえで、フェイルしたケースごとに、原因を次の4つから選びます。選ぶ場所は、ダッシュボードのエビデンスの表にある「あなたの判断」の欄です。この欄は空のまま表示され、AI の見立てでは埋まっていません。

原因選ぶ目安関門での扱い
実装の不具合展開元の観点に立ち返り、期待している振る舞いが仕様に照らして正しいと確かめた。テストは正しい確定できる。判断は記録に残る。このチュートリアルの範囲では、記録に残すところまでとする
仕様の仮回答による期待結果が、仕様の矛盾に対して試験観点の段階で仮に決めた回答をもとにしており、実装はもう一方の振る舞いをしている確定できる。判断は記録に残る
テストの誤りテストの操作や確かめ方が、試験ケースと合っていない確定できない。差し戻すと、AI が判断と根拠を読んでテストを直す
前の段階の誤り試験ケースや観点の入力値、期待結果のほうが誤っている確定できない。差し戻して、Claude Code にその段階を戻すよう頼む（下の「前の段階の誤りを見つけたとき」）

仮回答は、試験観点の段階で「どちらを選んでも誤りではない」として選んだものです。仕様の矛盾では、2つの仕様書が同じ振る舞いについて違うことを書いています（例は矛盾を確認する）。そのため、仮回答と実装の振る舞いが違っても、実装は仮回答で選ばなかったほうの記述どおりに動いているだけで、誤りとは言えません。この場合は「実装の不具合」ではなく「仕様の仮回答による」を選びます。

原因を選んだら、そう判断した根拠を1行書きます（例：「エビデンス1がエラー画面。仕様は重複のメッセージを出すと書いている」）。根拠は、差し戻したときは AI がテストを直す手がかりになり、確定したときは判断の記録として残ります。

AI の見立てをうのみにしない

AI が「実装の不具合の候補」とした見立てが、実際には試験ケースの入力値や期待結果の誤りであることもあります。見立ては候補です。根拠のエビデンスと、仕様書を自分で確かめてから決めてください。

前の段階の誤りを見つけたとき​

確定した試験ケースや観点の誤りに気づいたときは、その段階の成果物を直接直すことはできません。今の段階の関門で差し戻し、指摘の欄に「前の段階の誤り：ID」と、何が誤りかを書きます。そのあと /e2e-workflow を実行すると、AI は成果物を直さずに、指摘された誤りを確かめた結果と、戻すとどうなるかを示し、その段階を戻すかどうかを尋ねます。

  • 前の段階の誤りだった場合：戻すと答えます。AI がその段階を確定から差し戻しに戻して直します。学習者が確定し直したあと、後の段階は作り直しになります。
  • AI の確認結果を見て、誤りではなかったと分かった場合（仕様書を読み違えていたなど）：戻さないと答えます。AI は残りの指摘だけを反映して進めます。

手順5 差し戻すか確定するかを選ぶ​

ダッシュボードの「関門3 テストの確定」で、差し戻すか確定するかを選びます。

  • 差し戻す：手順2と手順3で書き留めた指摘があれば、指摘の欄にケースの ID を添えて書き、「差し戻す」を押します。手順4で選んだ原因と根拠も、差し戻しの理由に入ります。もう一度 /e2e-workflow を実行すると、AI が指摘と判断に沿ってテストコードを直し、流し直して見立てを書き直し、状態が「レビュー待ち」に戻ります。直ったエビデンスを、もう一度手順2から確かめます。
  • 確定する：指摘がなく、フェイルしたすべてのケースの原因が「実装の不具合」か「仕様の仮回答による」で、根拠を書いたら「確定する」を押します。フェイルしたケースが残っていても、原因をこのどちらかと判断できていれば確定してかまいません。

次のどれかに当たると、「確定する」は押せません。関門の欄に理由が表示されます。

  • テストコードか、その説明（code.md）がない
  • 試験ケースのうち、どのテストにも、説明の4章「テストコードにできなかったケース」にも載っていないものがある
  • 試験仕様書にないケースの ID で始まるテストがある
  • 同じケースの ID で始まるテストが2本以上ある
  • 流した結果がない
  • テストコードが、流したあとで変わっている
  • 実行の結果がない、または実行されていないケースがある
  • 環境が整っていなかったケースがある
  • フェイルしたケースのうち、原因を選んでいないものがある
  • フェイルしたケースのうち、根拠を書いていないものがある
  • 原因に「テストの誤り」を選んだケースがある
  • 原因に「前の段階の誤り」を選んだケースがある
開発に戻るとき

結合テスト用のバックエンドは、流したあとも動いたままです。開発に戻るときは、node scripts/e2e-workflow/env.mjs down で止め、cd backend && ./gradlew bootRun で開発用のバックエンドを起動し直します。

ここまでの流れ​

関門3 を確定すると、このチュートリアルで扱う E2E テストの設計から実行までが完了します。次の3つの段階で結合テストを作りました。

  1. 試験観点：何を確かめるかを、仕様書を根拠に決める
  2. 試験仕様書：観点を、前提、手順と入力、期待結果、確認箇所を持つ試験ケースに展開する
  3. テストコードと実行：AI がテストコードを作って流し、学習者が説明と実行のエビデンスで判断する

どの段階でも、AI が成果物を出し、学習者が関門で確定させます。学習者はテストコードを読みませんが、何を確かめるか（観点と期待結果）と、本当に確かめられたか（実行のエビデンス）は、自分で判断します。どこかの段階でつまずいたときは、Claude Code に今の状況を伝えて相談してください。たとえば次のように頼みます。

予約申請画面（/reservations/new）の結合テストで、RSV-NEW-TC-009 がフェイルした。原因が実装の不具合かテストの誤りか判断できないので、エビデンスと仕様書を見て、判断の手がかりを教えて
