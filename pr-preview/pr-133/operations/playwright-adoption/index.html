Playwright 導入の進行状況

Playwright による結合テストを、予約申請画面（/reservations/new）を対象とする独立したチュートリアルとして導入する。導入の判断とその理由は ADR-032 に記録している。本ページは進行状況と未決事項、および工程ごとの導入計画を扱う。決まったことと決まっていないことの現況は、次の節にまとめた。

学習者向けのページ

学習者向けのページは結合テストのワークフローから辿れる。ただし学習カリキュラムからの導線はまだつないでいない。

決まったことと決まっていないこと​

2026-10-07 時点の現況である。ここより下の節（工程の変化、スケジュール、未決事項、導入計画）は検討の経緯として残しており、スケジュールは現在のものではない。現況と経緯が食い違う場合は、この節を正とする。

学習者が従う全体の流れは結合テストのワークフローにまとめた。

提案中で確認待ちのこと​

運営者の作業の中で案として書き、まだ判断していないもの。判断が済んだら「決まったこと」へ移す。

案書いた場所
AI と学習者の役割分担と、学習者のレビュー手順（すべての観点の根拠の確認、食い違いの確認、除外への賛否、抜けの確認）AI と学習者の役割分担
段階ごとに関門を置き、関門を通すのは学習者だけとする。AI は自分の出力を確定にしない（段階と関門は 2026-10-04 に3つにまとめた）関門の決まり
2つ目の段階の成果物を「試験仕様書」と呼び、1件ずつを「試験ケース」と呼ぶ整理段階ごとの役割分担
結合テストの成果物（Docs/test/、tests/e2e/workflow/）を main に入れない決まりは、すべての結合テストのスキルに書く。CI では止めない結合テストのワークフロー

スキルの測り直し観点一覧の形式が決まってから行う。完了の基準を先に決め、各画面を2回ずつ実行する
スキルの description の最適化スキルの中身が固まってから行う
既存の選択課題「既存機能の E2E テスト追加」の扱い未決事項 8 のまま

Playwright MCP の評価別軸として後日評価する

工程の変化​

現在の必須課題は、課題の選択から実装、AI レビュー、マージまでを次の順で進む。検証にあたる工程は lint とユニットテスト、そして AI レビューの3つで、いずれも画面からの動作そのものは確かめていない。

導入するチュートリアルは、この流れには組み込まない。既にある予約申請画面を題材に、試験観点を作るところからテストを通すところまでを一続きで扱う。

太い枠が、学習者が判断を担う工程である。他の工程は AI に任せ、学習者は出てきたものを仕様に照らして確かめる側に回る。

未決事項​

A. 技術的な前提​

#決めること選択肢
1サインインの方式開発専用のロール別ログインを正式な手順とするのか、別の方式を用意するのか
2要素の指定方法data-testid を実装に入れるのか、役割とラベルで指定するのか
3バックエンドへの依存実際の API とデータベースを通すのか、BACKEND_URL の位置にスタブサーバーを立てるのか
4試験観点を作る手段独自の SKILL を使うのか、Playwright 公式のテストエージェントを使うのか、両方を併記するのか

1 は、ローカル環境ではブラウザからのサインインが成立しない（cognito-local が http で動き、認証クライアントのリダイレクトが失敗する）ことによる。2 は、現在の実装に data-testid が 1 つも入っていないことによる。3 の選択肢からブラウザ側での差し替えが外れているのは、予約申請画面のデータ取得がサーバー側で行われるためである（実環境の前提を参照）。この4つは机上では決まらないため、技術検証で実際に動かして確かめる。

B. 品質を担保する仕組み​

#決めること選択肢
5完了条件との接続結合テストが通ることを完了条件に加えるのか、加えないのか
6試験観点のレビュー観点生成された試験観点が妥当かを、誰がどの基準で判断するのか
7CI での実行独立したチュートリアルの段階では CI に載せるのか、ローカル実行に留めるのか
8既存の選択課題の扱い既存機能の E2E テスト追加の内容を書き換えて流用するのか、そのまま残すのか

5 は 2026-09-14 に決定した。今は完了条件に加えない。理由は2つある。ADR-032は学習者が書いたテストをリポジトリに取り込まないと定めており、完了を機械的に検証する手段がないため、加えるなら自己申告かレビュー時の口頭確認という弱い運用にせざるを得ない。また、必須課題への組み込みは学習時間の再配分などコストが高く実現性が低いと ADR-032 自身が一度退けた選択でもある。先行実施（9/24）の結果を見てから、完了条件への昇格を再検討する。

6 は 2026-09-14 に決定した。成果物を生成する手順を固定するだけでは、生成されたものが正しいかどうかを保証できないことによる。試験観点が仕様を網羅しているか、期待結果が妥当かは、別の仕組みで確かめることになる。暫定版の物差し（振る舞いの書き方と、確認しないと決めた振る舞いの併記）を定め、運営者から提供された標準観点セットをこの物差しに合わせて修正したうえで、試験観点を作るチュートリアルの付録として同梱した。通信の内部（HTTP ステータスコード）は、利用者に見える振る舞いですでに確認済みであるという理由を付けて「確認しないと決めた観点」に回している。承認ステップの生成有無は、当初この付録で対象範囲外としていたが、2026-09-17 に運営者提供の SKILL（未決事項4で採用）の完了条件を確認した結果、予約申請画面の処理結果として対象に含めるべき項目だと判明したため、確定した試験観点に戻した。2026-09-26 に、観点のたたき台を全画面共通のスキルが出力し、学習者が決まった手順でレビューする形に改めた。レビューの観点は、AI の特性（見落としと挙げすぎ、引用の取り違え、実行ごとのばらつき、業務上の重要度を判断できないこと）から決め、網羅の点検表とあわせて試験観点を作るチュートリアルに書いた。学習者は観点を一から作らず AI の出力をレビューするため、答え合わせ用の標準観点セットは付録から削除した。2026-09-30 に、網羅の点検表と優先度の案も削除し、根拠の確認を全件にした。

7 は 2026-09-14 に決定した。独立したチュートリアルの段階でも、運営者が用意する疎通確認テスト（機構が動くことを確かめる最小の1本）を既存の ci-frontend.yml に追加する。学習者が書くテストは前述のとおりリポジトリに残らないため、CI で実行できるのは疎通確認テストに限られる。追加する具体的なワークフローの変更は、工程2で疎通確認テストを用意した段階で行う。

B のうち 8 は未判断のまま残る。どの工程で判断するかは導入計画に置く。

導入計画​

導入は4つの工程に分ける。各工程は前の工程で決まったことを前提にする。技術的な前提（未決事項 A）を先に確定させる順にしたのは、品質を担保する仕組み（未決事項 B）のうち完了条件との接続と CI での実行が、A の実測結果を判断材料にするためである。

工程1 技術検証​

未決事項 A の4項目を実測で確定させる。この工程の成果物はテストコードではなく、決定とその根拠である。決まった内容は未決事項の表に反映する。

以下の4項目は、いずれも実際に devcontainer 上でバックエンドとフロントエンドを起動し、Playwright を実行して確かめた結果である。

1 サインインの方式：2026-09-17 に確定した。開発専用ロール別ログインを正式な手順として採用する。専用の検証設定で、環境の切り分け、セッションの保存、保存したセッションの再利用の3工程（計7件）を実行し、サインイン画面のロール別ボタンを押した際の cookie 発行と画面遷移、保存した storageState の再利用、cookie の有効期限（1時間、テスト全体の実行時間に十分耐える）をすべて確認した（検証設定は、この決定のあとに削除した）。テスト対象を本番ビルドに切り替えると NODE_ENV が production になりこの経路が遮断される制約と、cognito-local のエンドポイントが devcontainer のネットワーク内でしか解決しない制約は、確認前の見立てのとおり残る。

2 要素の指定方法：2026-09-17 に確定した。役割とラベルによる指定を全面的に採用し、data-testid は入れない。予約申請フォームのリソース選択（shadcn/ui の Select であり、ネイティブの <select> ではない。実環境の前提を参照）を含め、getByRole と getByLabel による指定で疎通確認テストが連続実行でも安定して通ることを確認した。判断軸は「そのテストはバグで落ちるか、意図した変更で落ちるか」に置いた。役割とラベルによる指定は、要素を利用者に見える契約に結びつける。ラベルの文言が変われば落ちるが、それは利用者から見た振る舞いが変わったということなので落ちてよい。一方で DOM の構造を組み替えただけでは落ちない。data-testid は逆に、DOM の変更には強い代わりに、利用者に見える契約から切り離された印を追うことになるうえ、学習者が触る既存実装への差分も増える。

3 バックエンドへの依存：2026-09-17 に確定した。devcontainer の postgres、cognito-local、バックエンドをそのまま起動し、実データを通す。バックエンドの起動はテスト実行前に ./gradlew bootRun で行う手順とし、Playwright の webServer はフロントエンドの起動だけを担う。seed.sql の投入は環境構築の手順に含め、テスト側では行わない。繰り返し実行しても同じ結果になる状態は、時間帯の割り当てと後片付けを機構側で引き受けることで確保した（2026-09-21 に方式を変更）。

当初は実行時刻から一意な未来日時を計算する方式を採ったが、これは2つの理由で退けた。テストの入力が時計に依存すると、落ちたときに同じ状況を再現できない。加えて、実行時刻の剰余からオフセットを作る実装は 8 分 20 秒周期で同じ日時を生成し、その間隔で走らせた2回の実行が衝突する。

現在の方式では、テストごとに決まった時間帯を配り（ワーカー番号とテスト名から決めるため、時計を読まず、並列実行中も重ならない）、テストが作った予約を終了時にキャンセルして枠を解放する。強制終了で後片付けが走らなかった場合に備えて、実行の冒頭でも取りこぼしを回収する。キャンセルを使うのは、重複判定の条件が status IN ('PENDING', 'APPROVED') であり、キャンセルすれば対象から外れるためである。同一リソースを奪い合う4本を並列実行しても衝突せず、3回連続実行しても予約が蓄積しないことを確認している。

2026-10-03 に、結合テストのワークフローで生成したテストに限って、この方式を改めることを提案した。上の「蓄積しない」は、重複判定の対象になる予約（承認待ちと承認済み）のことで、キャンセル済みの予約は消えずに残る。学習者がテストの撮った画面で判断するようになると、残った予約が画面に写り、マイ予約一覧が9ページになって「このテストの予約がないこと」を画面で確かめられなくなった。そこで、生成したテストは結合テスト専用のデータベース（bookflow_e2e）で動かし、テストごとに初期データだけの状態に戻す。開発用のデータベースは戻さないので、この決定の「seed.sql の投入はテスト側では行わない」は、開発用のデータベースについては変わらない。普段の pnpm test:e2e は、これまでどおり時間帯の割り当てと後片付けで動かす。

4 試験観点を作る手段：2026-09-17 に確定した。運営者（相沢さん）が用意した独自 SKILL（generate-reservation-test-perspectives）を採用する。設計書のファイルパスと出力先のみ本リポジトリ向けに調整し、判定ルール、分類、粒度は変更していない。Playwright 公式のテストエージェントとの比較検証は行っておらず、Playwright MCP と同じ別軸として後日評価する。Claude Code 設定台帳のスキル表に行を追加した。2026-09-23 に、予約申請画面専用のこの SKILL を、全画面共通の generate-test-perspectives に置き換えた。新しい画面を作ったときに使えるようにするためで、仕様書だけを根拠にし、実装コードは読まない。旧 SKILL は削除した。

4項目とも実測の結果と決定が出そろい、この工程は完了した。未決事項 B のうち、完了条件との接続（5）と CI での実行（7）もこの結果を踏まえて判断済みである（未決事項を参照）。

工程2 チュートリアル本体の作成​

工程1 の決定を、学習者が使える形にする。ADR-032 が定めた担い手の分離に従い、ここで作るのは学習者が成果物を作れるようにするための機構だけである。

リポジトリに入れるもの：

  • 認証の fixture（工程1 で決めた方式を、テスト間で共有できる形にしたもの）
  • 実行の前提を揃える手順（postgres と cognito-local とバックエンドの起動、seed.sql の投入）
  • 予約の時間帯の割り当てと後片付けの機構（テストごとに決まった枠を配り、テストが作った予約をキャンセルして解放する）
  • 要素の指定方法の規約（data-testid を入れると決めた箇所は、実装への差分が発生する）
  • 試験観点の物差し（後述）
  • よくある失敗と切り分け方
  • 学習者向けのページ

リポジトリに入れないもの：

  • 学習者が書いた試験観点、試験ケース、テストコード（ADR-032 の成果物の扱いに従う）
  • 手本として置くテストコード。機構が動くことを確かめる最小の1本は入れるが、これは学習者が写すためのものではない

試験観点の物差しは、観点を作らせるときと、できた観点をレビューするときの両方で使う 1 枚にする。ADR-032 は、手順を固定する仕組みが成果物を生成するだけで正しさを保証しないと述べており、未決事項 6 はその審査側をどう用意するかを問うている。生成用と審査用を別々に作ると、両者がずれたときにどちらが正なのかが決まらない。物差しに書くのは次の2つである。

  • 振る舞いの書き方：実装内部の名前を説明に持ち込まない。体言止めにせず「何をしたら、どうなれば正しいのか」を言い切る。1 項目には 1 つの振る舞いだけを書く。読み手はコードベースを知らない学習者である
  • 確認しないと決めた振る舞い：確認する観点の一覧の後に、意図して外した観点を理由付きで併記させる。理由は語彙を決めておく（取るに足らない、上流のテストで担保済み、手動確認に隔離、など）

除外を併記させるのは、レビューを学習者が担えるようにするためである。観点の一覧に漏れがないかを判断するには仕様の全体を把握している必要があるが、意図して外した理由が妥当かどうかは一つずつ独立に判断できる。ADR-028 が挙げた「AI が出したものの誤りに気づき、自分で直せる」状態に、この形なら手が届く。

書き方の規範が要るのも同じ理由による。生成された観点が実装内部の言葉で書かれていると、学習者は読み流すしかなくなり、判断役という到達目標そのものが成立しない。

この形は、フューチャー技術ブログの記事「AI がテストを書く中で、「あるべき仕様」を単体テストで担保するために工夫してみていること」から採っている。同記事が対象にしているのは単体テストで E2E はスコープ外だが、あるべき振る舞いを決めるのは人間であり、生成を任せる範囲との線引きを 1 枚の規範で担保するという考え方は、ADR-032 の担い手の分離と同じ構造である。層ごとのテストの厚みの出し分けは、同記事が presentation と I/O を薄い側に置いているのに対して本チュートリアルはその層そのものを扱うため、流用していない。

この工程で決める派生の項目が2つあった。どちらも 2026-09-21 に決定している。

学習者向けのページは docs-next/docs/develop/ 配下に置く。ディレクトリの分け方は「いつ読むか」を軸にしており、learn/ は最初に読む必修の導入、develop/ は実装中に引くものである。本チュートリアルは ADR-032 が必修フローに組み込まないと決めたものであり、テストを書いている最中に引く性質のため後者に当たる。4本のチュートリアルは結合テストのチュートリアルとして展開できるカテゴリにまとめ、Playwright 自体の使い方はPlaywright とはに分離した。

既存の frontend/tests/e2e/example.spec.ts は削除し、機構の疎通確認テストに置き換えた。このテストが期待する「BookFlow」という名前の見出しは、未認証と認証済みのどちらの状態にも存在せず、現在の実装では通らないためである。

この工程を終える条件は、上の機構が揃い、疎通確認のテストが pnpm test:e2e で通ることである。試験観点のレビュー観点（未決事項 6）の暫定版もこの工程で作る。

工程3 先行実施​

運営者以外が手順どおりに通せるかを確かめる。見るのは、手順の抜け、環境差による失敗、そして所要時間である。ADR-032 は所要時間を本体ができた段階で見積もるとしているため、ここで実測する。

この工程を終える条件は、先行実施者が手順だけで完走できることである。詰まった箇所が手順の修正では解消できないと判断した場合は、工程2 に戻る。

工程4 最終修正と正式導入​

先行実施で出た指摘を反映し、学習者への導線をつなぐ。やることは4つある。

  • 手順とページの修正
  • 学習カリキュラムと運用ガイドへの導線追加
  • 既存の選択課題の扱い（未決事項 8）の判断
  • 未決事項 B の判断を ADR-032 に追記

正式導入の条件は、学習者が参照するページから手順まで辿れて、未決事項の8項目すべてに決定が書かれた状態になることである。

導入に伴うコスト​

独立したチュートリアルとしたことで、必須課題の学習時間と完了条件には手を入れずに済む。それでも次の負担は残る。

テストの保守：画面の構造が変わると、教材として置く試験ケースとテストコードは壊れる。対象画面（予約申請画面）に手を入れる課題が実施されると、教材側の追従が必要になる。

実行の不安定さ：ブラウザを介するテストは、待ち時間の扱いによって同じコードでも成否が変わることがある。失敗したときに実装の問題なのかテストの問題なのかを切り分ける手間が、学習者と運営者の双方に生じる。

CI の実行時間：未決事項の 7 で CI に載せる判断をした場合に発生する。ci-frontend.yml は、報告されない check がブランチ保護と AI レビューの前提を満たせなくなる事情から、ジョブ自体をスキップしない設計になっている。結合テストをこの check に載せると、frontend に触れない PR も含めてすべての PR がブラウザテストの完了を待つ。載せるために要る作業も小さくない。postgres と cognito-local をサービスコンテナとして立て、バックエンドを起動し、ブラウザの実体を入れ、seed.sql を投入する必要がある。playwright.config.ts は CI での再試行を2回、並列度を1に設定しているため、失敗したときの所要時間はテスト本数に比例して伸びる。既存の check に載せず、独立したワークフローとして手動または夜間に回す形なら、この待ち時間は他の PR に波及しない。

後の2つは、ブラウザと実データを通すことに由来する構造的な差であり、運用の工夫で消えるものではない。結合テストは、ADR-032 が寿命の長さの根拠とした実装の内部に依存しない書き方と引き換えに、フィードバックの速さを手放している。

別軸としての Playwright MCP​

ここまではテストコードとしての Playwright を扱った。これとは別に、Claude Code 自身にブラウザを操作させる使い方がある。エージェントが実装後に画面を開いて動作を確かめ、その結果を報告する形になる。

本研修の学習範囲は Claude Code と AI 駆動開発なので、この使い方も範囲に含まれる。ただし現時点では評価していない。テストコードとしての運用が定まってから、別途検討する。

実環境の前提​

着手する際に前提となる、現在のリポジトリの状態を挙げる。

テスト基盤

  • フロントエンドには @playwright/test と playwright.config.ts が既にあり、pnpm で管理している。新たに導入する作業は要らない
  • pnpm test はユニットテスト（Vitest）を実行する。Playwright は pnpm test:e2e である
  • playwright.config.ts の webServer.command は pnpm dev である。テスト実行時の NODE_ENV が development になることが、開発専用ロール別ログインを使える前提になっている
  • ci-frontend.yml に Playwright を実行するステップはない
  • 既存の frontend/tests/e2e/example.spec.ts は、コードを読む限り現在の実装では通らない。トップページを開くと未認証ならサインイン画面へ戻され、そこの「BookFlow」は見出し要素ではない。認証済みでもヘッダーのロゴはリンクであり、見出しは「ダッシュボード」である。このテストが期待する「BookFlow」という名前の見出しは、どちらの状態にも存在しない

認証

  • ローカル環境ではブラウザからのサインインが成立しない（cognito-local が http で動き、認証クライアントのリダイレクトが失敗する）
  • 開発専用ロール別ログインが呼ぶ cognito-local のエンドポイントは、既定値が devcontainer のネットワーク内でしか解決しないホスト名である
  • 認証ガードのレイアウトは利用者情報の API（/api/users/me）を呼ぶ。バックエンドが起動していないと、cookie があっても全画面がサインイン画面へ戻る

予約申請画面

  • リソース一覧の取得はサーバー側から行われる。ブラウザを経由しないため、Playwright のルーティング機能では差し替えられない
  • リソース選択はネイティブの <select> ではない。ラベルからの取得では掴めず、選択肢を開いてから選ぶ手順になる
  • 実装に data-testid は 1 つも入っていない
  • 必須項目のラベルは末尾に半角スペースと * が付く。ラベルからの取得を完全一致で書くと外れる

テストデータ

  • seed.sql は Flyway の対象外で手動投入する。予約は2件で、同一リソースの重複時間帯のデータは含まない
この節の確認状況

上に挙げた内容は、いずれもコードを読んで確かめたものである。Playwright を実行して確かめたものではない。実行による確認は技術検証で行う。
