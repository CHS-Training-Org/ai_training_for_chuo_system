ADR-032 — 運用プロセス：結合テストを独立チュートリアルとして導入する

Status​

Accepted（2026-09-09）

Context​

ADR-028 は本リポジトリの目的を、AI 駆動開発が導入された現場についていける状態にすることと定めた。同時に、標準フローで学習者に強制される行為が Issue の選択、計画への同意、理解度チェックへの回答、マージの4つに限られることも記録している。

実装をエージェントに渡した以上、品質を担保する仕組みは実装の外側に置くことになる。現在リポジトリが持っている検証の工程は次の3つである。

手段何を確かめているか
lint と Vitest（pnpm test）構文と、実装の内部構造に依存した振る舞い
JUnit（./gradlew test）バックエンド各層の振る舞い
AI レビュー（ADR-025）差分の妥当性

いずれも画面から実際に操作した結果は確かめていない。画面から DB までを通した業務フローが成立しているかを確認する工程は、現在のカリキュラムに定義されていない。ADR-028 が課題として挙げた「AI が出したものの誤りに気づき、自分で直せる」ための検証の仕組みが、ここに欠けている。

Playwright は ADR-009 で既に採用済みであり、frontend/ に @playwright/test と playwright.config.ts が存在する。ただし CI（ci-frontend.yml）にも学習フローにも載っておらず、実質的に使われていない。

テストコードを書く作業そのものは、AI エージェントによって難しい作業ではなくなった。そのため学習の主題になるのはコードの書き方ではなく、何を検証対象として定義するかの側である。結合テストの成果物を層に分けると、人が担う範囲が明確になる。

層内容担い手
試験観点何を確認するかを、仕様書を根拠に列挙したもの人が決める。エージェントは生成を補助する
試験ケース前提条件、操作手順、入力値、期待結果に展開したものエージェントに任せられる
テストコードPlaywright のテストファイルエージェントに任せられる

結合テストをこの位置に置く理由は、寿命の違いにもある。ユニットテストは実装の内部構造に依存するため、エージェントが内部を書き換えれば書き直しが要る。結合テストは操作と結果という利用者から見える言葉で書かれるため、下の実装が入れ替わっても定義がそのまま残る。エージェントが実装を頻繁に書き換える前提では、この差が効く。

一方で、結合テストが通ることは品質が担保されたことを意味しない。テストコードが生成された後も、人が担い続ける作業がある。

  • 初めて作る機能を探索的に確かめる
  • 画面の見た目が意図どおりかを判断する
  • 性能とセキュリティを確認する
  • 業務として受け入れてよいかを判断する

制約として、9月末までに実施可能な形で運用に載せることを優先し、用意する機構が最も少ない選択を取る必要があった。

検討した候補：

候補学習効果用意する機構9月末までの実現性
必須課題の各実装に結合テストを組み込む高い。課題ごとに反復する受入条件から試験観点を作る手順、CI での実行、完了条件の再定義、学習時間の再配分低い
独立したチュートリアルとして1画面を対象にする中。一度だけ通る対象画面の手順と、実行環境の前提整理高い
バックエンドを含めた結合テストを対象にする高い上記に加えてテストデータの用意と別の検証機構低い
Playwright MCP でエージェントに画面を操作させる別軸。検証工程の追加ではなく確認の代行MCP 設定未評価

Decision​

Playwright による結合テストを、必須課題とは独立したチュートリアルとして導入する。

  • カリキュラム上の扱い：必須課題のフローには組み込まない。独立したチュートリアルとする。
  • 対象：予約申請画面（/reservations/new）の結合テスト。既存のベース実装を題材とするため、試験観点は完成したものに対して作る。
  • 範囲：フロントエンドに限る。バックエンドを含めた結合テストは対象外とする。
  • 到達目標：学習者が、AI を使って結合テストの試験観点とテストコードを作り、実行して通せる状態になる。
  • 担い手の分離：成果物を作るのは学習者である。運営者が用意するのは、学習者がそれをできるようにするための機構に限る。特に試験観点は学習者自身が AI と対話しながら決める部分であり、運営者が中身を埋めない。
層学習者がやること運営者が用意する機構
試験観点仕様を読み、AI と対話しながら自分で決める観点の切り口を促す仕組み、仕様のどこを根拠にするかの手順、妥当性を測るレビュー観点
試験ケースAI に展開させ、結果を確認する展開の手順、前提データとテストユーザーの用意
テストコードAI に生成させる本リポジトリで動く生成手順（サインイン方式、要素の指定方法）
実行と切り分け実行し、落ちたら直す実行コマンド、よくある失敗と切り分け方
  • 成果物の扱い：学習者が書いたテストはリポジトリに取り込まない。学習の過程そのものが目的であり、成果物の蓄積は目的ではないためである。ADR-030 は完了した課題の実装を学習者ごとのトランクブランチに積み上げる運用だが、本チュートリアルの成果物はそこにも積まない。

Consequences​

ポジティブ：

  • 画面から DB までを通した業務フローを確認する工程が、カリキュラムに初めて入る。
  • 学習者が判断を担う範囲（試験観点）と、AI に任せる範囲（試験ケースとテストコード）の線引きを、具体的な作業として体験できる。これは ADR-028 が掲げた到達目標に直接あたる。
  • Playwright が導入済みのまま使われていない状態が解消される。
  • 必須課題のフローを変更しないため、実施中の学習者に影響しない。完了条件と学習時間の配分にも手を入れずに済む。

留意点：

  • 独立したチュートリアルであるため、学習者が結合テストを作る経験は一度だけになる。反復による定着は本チュートリアルの範囲外であり、必須課題への組み込みは独立したチュートリアルが回るようになってから検討する。
  • 必須課題の学習時間（合計 17〜24 時間）には手を入れないが、本チュートリアル自体が学習者の時間を消費する。所要時間は本体ができた段階で見積もる。
  • 対象を1画面に絞るため、画面ごとに事情が異なる部分（一覧画面の並び替えや、承認フローをまたぐ操作など）は扱わない。
  • 現在の実装に data-testid は 1 つも入っていない。要素の指定方法を決める必要がある。
  • ローカル環境ではブラウザからのサインインが成立しない（cognito-local が http で動き、認証クライアントのリダイレクトが失敗する）。開発専用のロール別ログインを正式な手順とするかを決める必要がある。
  • 生成された試験観点が妥当かどうかを判断する仕組みは、これから整備する。手順を固定する仕組みは成果物を生成するだけで、生成されたものの正しさは保証しない。

未決事項：

技術的な前提（サインイン方式、要素の指定方法、バックエンドへの依存、試験観点を作る手段）と、品質を担保する仕組み（完了条件との接続、試験観点のレビュー観点、CI での実行、既存の選択課題との関係）は本 ADR では決めていない。進行状況と未決事項の一覧は Playwright 導入の進行状況 で管理する。
