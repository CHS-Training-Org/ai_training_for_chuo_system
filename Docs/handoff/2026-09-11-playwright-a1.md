### 相沢さんのチュートリアル案のレビュー結果

相沢さんから Teams で 2 ファイル（`CreateTestCondition.md`、`ReferenceAnswer.md`）が共有された。試験観点作成のチュートリアルと、答え合わせ用の標準観点セット。実装と仕様に照らして確認した結果は次のとおり。いずれもコードと仕様書の読解によるもので、実行して確かめたものではない。

**先に相沢さんへ返すべき 2 点**

1. `CreateTestCondition.md` の STEP1 成果物例に「過去日は登録不可」とあるが、このルールは BookFlow に存在しない。`docs-next/docs/spec/`、`backend/src/main/java`、`frontend/src` を検索した限り該当なし。STEP3 で学習者に根拠の確認を求めているため、この例をなぞると詰まる
2. `ReferenceAnswer.md` は CP932（Shift_JIS）で保存されている。リポジトリに入れる前に UTF-8 と LF へ変換が要る

**標準観点セットが見落としている、実装と仕様の食い違い**

`screen-spec.md` は予約申請画面のリソース選択を「有効リソース一覧」と書いているが、`ResourceController` が `isAdmin` を渡し `ResourceService.list` が ADMIN のとき `is_active = false` を含めるため、ADMIN で開くと無効なリソースが選択肢に出る。標準観点セットの観点 3 は「有効なリソースが表示されること」だけで、無効なものが出ないことを見ていない。観点 15 に「ADMIN で申請できること」があるので学習者はこの経路を通る。

**その他**

- 観点 2（画面初期表示）の 7 項目は、フォームの要素一覧を写した形で、意図した画面編集で落ち振る舞いのバグを捕まえない。物差しを当てる最初の対象
- 参加人数の境界値がない。スキーマは `z.number().int().positive()`、入力欄に `min={1}`
- 利用目的 255 文字の根拠は `api-spec.md` と `requirements.md` にあり、`screen-spec.md` のバリデーション表にはない
- 申請ボタンのラベルが仕様（「申請する」）と実装（「予約を申請する」）で違う
- 観点 10 の「409 Conflict が返却されること」は利用者に見える契約ではなく通信の中身。観点 12 の「承認ステップが生成されること」は画面から確認できるが、ADR-032 が対象を予約申請画面に限っているためスコープ外。どちらも「確認しないと決めた振る舞い」として理由付きで残す形が物差しと噛み合う
- 「網羅率を評価してください」という答え合わせのプロンプトは、観点を増やす方向に効く。標準観点セットに「含まれているが今回は確認しないと決めてよい観点」の節を足すのが安い対処

絞り込む 4 観点（必須入力、利用目的文字数制限、日時整合性、正常な予約申請）の選定自体は妥当。ただし前 3 つはクライアント側の Zod で止まるものの、**画面自体がバックエンドなしでは描画されない**（サーバーコンポーネントがリソース一覧を取得し、認証ガードが利用者情報 API を呼ぶ）。「クライアント側だけだから環境構築を省ける」という読みは成り立たない。

## 次の作業：A1 の技術検証

手順は [A1 検証手順書](./A1-runbook.md)。リポジトリに入っているファイルは次のとおり。

```
frontend/playwright.a1.config.ts          検証専用の設定（既存の playwright.config.ts は触っていない）
frontend/tests/e2e/a1-preflight.spec.ts   環境の切り分け
frontend/tests/e2e/auth.setup.ts          ログインしてセッションを保存
frontend/tests/e2e/a1-signin.spec.ts      保存したセッションの再利用
```

実行は前提（provision-cognito、seed 投入、bootRun）を揃えてから次のとおり。

```bash
cd frontend
pnpm exec playwright test -c playwright.a1.config.ts
```

この検証の山は、`storageState` が httpOnly cookie を保存するかどうか。保存されない場合はセッション再利用を諦め、テストごとにログインを通す設計に切り替える判断になる。

実行結果は手順書の 5 節の様式で記録し、進行状況ページの未決事項の表に反映する。

## 注意点

- **A1 の検証キットは、ドキュメントだけだったブランチに混ざっている。** 検証をチュートリアル本体から切り離す方針なら、ここから検証用ブランチを切って移す
- **PR を出す前に `pnpm format` と `pnpm lint` を通すこと。** 検証キットのコードはリモート環境で整形を実行できていない。`ci-frontend.yml` は `frontend/` の変更で Lint と Format check を走らせる
- `pnpm test`（Vitest）の include は `tests/unit/**` 限定なので、`tests/e2e/` への追加とは衝突しない
- `.gitignore` に `frontend/playwright/.auth/` を追記済み。保存されるセッションには cognito-local が発行した実物の IdToken が入る
