# Business Logic Model - resource-keyword-filter

## 対象範囲

リソース一覧取得（`GET /api/resources`）の絞り込み処理に、キーワード検索条件を追加する。リソース詳細取得・登録・更新・空き照会は対象外。

## 処理フロー（業務レベル）

1. 呼び出し元（フロントエンドのフィルタフォーム）が、カテゴリ・期間（`from`/`to`）・キーワードのうち、指定された条件のみを URL パラメータとして送信する。
2. リソース一覧取得は、ロール別可視性（ADMIN は無効リソースも含む全件、それ以外は有効リソースのみ）をまず適用したうえで、指定された条件を **すべて AND** で組み合わせて絞り込む。
3. 期間（`from`/`to`）が指定されている場合、絞り込み後の候補に対して予約重複判定（既存ロジック）を適用してから手動ページネーションする。期間未指定の場合は DB のページネーションをそのまま使う。
4. キーワード条件は、この可視性適用・カテゴリ絞り込みと同じ段階（DB クエリ）で評価する。期間フィルタの前段（候補取得）・期間フィルタなしの通常経路のどちらでも同じ絞り込み条件を使うことで、結果の一貫性を保つ。

## キーワード条件の評価規則

- 対象フィールド：リソース名（`name`）またはリソース説明（`description`）のいずれかに部分一致すれば該当とする（OR）。
- 大文字・小文字を区別しない。
- キーワード未指定、または空文字・空白のみの場合は、キーワード条件自体を評価しない（フィルタ解除と同義）。
- カテゴリ条件・可視性条件・キーワード条件は互いに独立した AND 条件であり、一部のみ指定した場合は指定された条件だけが効く。

## 設計判断：検索条件の実装方式

`ResourceRepository` は現在 Spring Data のメソッド名派生方式で、可視性（ADMIN/非ADMIN）・カテゴリ有無・ページ有無の組み合わせにより6メソッドが存在する。ここにキーワードを単純追加すると組み合わせが破綻するため、`@Query`（JPQL）による1メソッドへの集約に置き換える（ユーザー承認済み。判断根拠：`ResourceRepository` のメソッドは `ResourceService` 以外から呼ばれておらず置換の影響範囲が閉じている、既存コードベースに `@Query` の前例が複数ある一方 Specification の前例はない）。

後継課題（リソース一覧のソート順選択）で `Sort`/`Pageable` の扱いを拡張する際も、この集約後のメソッドに手を加える形になる。
