# Business Rules — resource-search

## BR-01: 大文字小文字を区別しない部分一致

`keyword` は `resources.name` または `resources.description` のいずれかに、大文字小文字を区別せず部分文字列として含まれるリソースを検索対象とする（OR 条件で 2 カラムを評価し、その結果を他フィルタと AND 合成する）。

- **対応要件**: RES-01, RES-02
- **検証例**: `keyword="room"` は `name="Meeting Room A"` にも `name="meeting room a"` にもマッチする

## BR-02: 未入力（null/空/空白のみ）は「フィルタなし」

`keyword` を trim した結果が空文字の場合、keyword フィルタを一切適用しない（他の条件のみで絞り込む、または無条件で全件対象とする）。

- **対応要件**: RES-05, NFR-02
- **理由**: 受入条件「キーワードを空にして絞り込むと条件が解除される」を、スペースのみの入力に対しても一貫させるため
- **適用層**: フロントエンド（送信前）・バックエンド（受信後）の両方で trim・null 判定を行う（多層防御。片方のみだと直接 API 呼び出し時に一貫しない挙動になる）

## BR-03: `description` が NULL のレコードの扱い

`description` は NULL 許容カラムである。keyword 検索条件の評価時、`description IS NULL` のレコードは「description 側ではマッチしない」として扱う（エラーにはしない）。`name` 側でマッチすれば結果に含まれる。

- **対応要件**: NFR-03

## BR-04: ワイルドカード文字のエスケープ

`keyword` に `%` または `_` が含まれる場合、それらは LIKE 演算子のワイルドカードとしてではなく、リテラル文字として扱われるようエスケープする。

- **対応要件**: NFR-05
- **検証例**: `keyword="50%"` は文字列 "50%" を含むリソースのみにマッチし、任意の文字列にマッチしてはならない

## BR-05: 既存フィルタとの AND 合成

`category`・`from`/`to`（空き確認）・`keyword` は独立した条件として評価され、すべて **AND** で合成される。いずれかの条件が未指定の場合、その条件は評価対象から外れる（絞り込まない）。

- **対応要件**: RES-04

## BR-06: ロール別可視範囲は keyword フィルタの前提条件として維持

ADMIN は `is_active` を問わず検索対象、それ以外のロールは `is_active = true` のみが検索対象という既存ルールは変更しない。keyword はこの可視範囲の**内側**でさらに絞り込む条件として働く。

- **対応要件**: 既存仕様の維持（`requirements.md` スコープ外だが、回帰させてはならない制約として明記）

## BR-07: `keyword` 未指定時の後方互換性

`keyword` パラメータ自体が送信されない場合、既存の動作（category/from/to のみによる絞り込み、または全件取得）から一切変化しない。

- **対応要件**: NFR-02
