# Business Rules — reservation-draft

## 設計で確定した判断（Functional Design の質問への回答を含む）

| # | 論点 | 決定 | 出どころ |
|---|---|---|---|
| BR-D1 | 下書きの再編集でのリソース変更 | **不可**。変えたいときは削除して作り直す | Q1 の回答 |
| BR-D2 | 削除前の確認ダイアログ | **出す**（キャンセルボタンと同じ作り） | Q2 の回答 |
| BR-D3 | `draft: true` を `DRAFT` 以外に指定した場合 | **422** | 要件書の前提・解釈 3（承認済み） |
| BR-D4 | 正式申請の API | 新しいエンドポイントは作らず、`PUT /api/reservations/{id}`（`draft` なし）で行う | 要件書 FR-05 |
| BR-D5 | 正式申請の失敗時 | 状態を変えない（`DRAFT` のまま残す） | 下の「正式申請の原子性」 |
| BR-D6 | ADMIN 自身の下書き | ADMIN も、**自分の下書き**なら更新・正式申請・削除ができる。他人の下書きは閲覧のみ | ユーザーの回答（Functional Design の途中で追加。要件書 D-10） |

## `PUT /api/reservations/{id}` の分岐

権限チェック（本人のみ。ロールは問わない）を最初に行い、そのあとで状態と `draft` で分岐する。

| 予約の状態 | `draft` | 動作 | 失敗時 |
|---|---|---|---|
| `DRAFT` | `true` | 下書きの更新。必須項目と時刻の整合を検証し、重複判定はしない。`DRAFT` のまま | 422（時刻の不整合） |
| `DRAFT` | `null` / `false` | 正式申請。重複判定を行い、承認要は `PENDING` と承認ステップ生成、承認不要は `APPROVED` | 409（重複）、422（承認者なし、時刻の不整合） |
| `PENDING` | `null` / `false` | 既存の更新（変更なし） | 既存どおり |
| `PENDING` | `true` | 拒否 | 422 |
| それ以外 | 任意 | 拒否（既存の状態ガード。メッセージに `DRAFT` を加える） | 422 |

## 検証ルール

| 操作 | 必須項目（リソース、開始、終了、目的） | 終了が開始より後 | 重複判定 | 承認ステップ |
|---|---|---|---|---|
| 下書き保存（`POST`、`draft: true`） | 検証する（Bean Validation） | 検証する（422） | しない | 作らない |
| 下書きの更新（`PUT`、`draft: true`） | 検証する | 検証する（422） | しない | 作らない |
| 正式申請（`PUT`、`DRAFT` で `draft` なし） | 検証する | 検証する（422） | する（自分自身は除外。409） | 承認要のときに生成 |
| 通常申請（`POST`、`draft` なし） | 検証する | 検証する | する | 承認要のときに生成（既存のまま） |

- リソースの存在確認（404）は、すべての操作で行う。下書き保存では、重複判定をしないため、リソースを悲観ロックしない（ロックするのは正式申請と通常申請）。
- 利用停止（`is_active = false`）のリソースや過去の日時は、既存の通常申請と同じく、検証しない。正式申請も同じ扱いにする。

## 正式申請の原子性

正式申請の処理は 1 つのトランザクションで行い、次の順で進める。

1. リソースを悲観ロックで取得する。
2. 時刻の整合を検証する。
3. 重複を判定する（自分自身は除外）。
4. 入力値で `update(...)` し、状態を遷移させる。
5. 承認が必要なら承認ステップを生成する。

3 で `409`、5 で `APPROVER_NOT_AVAILABLE`（422）になった場合は、例外でトランザクションが巻き戻る。入力値の更新と状態の遷移も取り消され、`DRAFT` のまま残る。

## 権限（下書きに対して）

| 操作 | 本人（ADMIN を含む） | 他人の MEMBER | 他人の APPROVER | 他人の下書きに対する ADMIN |
|---|---|---|---|---|
| 閲覧（`GET /{id}`） | 可 | 403 | 403 | 可 |
| 更新・正式申請（`PUT`） | 可 | 403 | 403 | 403 |
| 削除（`DELETE`） | 可 | 403 | 403 | 403 |
| 取消（`POST /{id}/cancel`） | 不可（422） | 403 | 403 | 不可（422） |
| 一覧に出る（`status=DRAFT`） | 自分の下書き | 自分の下書きのみ | 自分の下書きのみ | 全ユーザーの下書き |

- 「本人」はロールを問わない。ADMIN が自分の下書きを操作する場合も、本人として扱う（バックエンドの更新と削除は、申請者かどうかだけで権限を判定する）。
- 各操作は、存在確認（404）、権限（403）、状態（422）の順に判定する。
- 取消は、既存の取消可能状態（`PENDING`、`APPROVED`）に `DRAFT` を含めないことで、422 になる。権限チェックは既存のまま。

## 削除のルール

| 条件 | 結果 |
|---|---|
| 予約が存在しない | 404 |
| 本人以外（ADMIN も、他人の下書きなら） | 403 |
| 本人だが `DRAFT` 以外 | 422（`VALIDATION_ERROR`） |
| 本人の `DRAFT` | 物理削除して 204 No Content |

## 一覧のルール（`GET /api/reservations`）

| `status` の指定 | ADMIN | それ以外 |
|---|---|---|
| なし | `DRAFT` を除く全ユーザーの予約 | `DRAFT` を除く自分の予約 |
| あり（`DRAFT` を含む） | 指定した状態の全ユーザーの予約 | 指定した状態の自分の予約 |

並び順は、既存どおり指定しない（ページサイズ 20 のみ）。今回は変えない。

## 変更しないルール

- 時間帯の占有判定は、`PENDING` と `APPROVED` のみ（`DRAFT` は含まれず、占有しない）。
- 承認一覧と承認の操作は、承認ステップが無い下書きには影響しない。承認時の `PENDING` ガードも変えない。

| 編集画面: 「下書き保存」「申請する」 | `DRAFT` のとき |
