# ブラウザでの動作確認手順 — 予約の下書き保存

**作成日時**: 2026-10-09
**対象**: 学習者によるセルフレビュー
**所要時間**: 25分から30分程度

画面に表示される文字をそのまま載せた打鍵手順である。
各シナリオの末尾のチェック欄を埋めながら進める。

---

## 準備

### 手順 A. 依存サービスを起動する

ターミナルを1つ開き、次を実行する。

```bash
docker compose -f .devcontainer/docker-compose.yml up -d
```

すでに起動している場合は何も起きない。これで `postgres`（データベース）と `cognito-local`（認証）が動く。

### 手順 B. バックエンドを起動する

**新しいターミナル**を開き、次を実行する。

```bash
cd backend && ./gradlew bootRun
```

最後に次の行が出れば起動完了である。このターミナルは閉じずに置いておく。

```
Started BookflowApplication in 5.004 seconds
```

### 手順 C. フロントエンドを起動する

**さらに新しいターミナル**を開き、次を実行する。

```bash
cd frontend && pnpm dev
```

`✓ Ready in ...` が出れば起動完了である。このターミナルも閉じずに置いておく。

### 手順 D. データの初期状態を確認する

4つめのターミナルで次を実行する。

```bash
docker exec ai_training_for_chuo_system_devcontainer-postgres-1 \
  psql -U bookflow -d bookflow -t -c \
  "SELECT status || ' | ' || purpose || ' | ' || start_at FROM reservations ORDER BY start_at;"
```

次の2行だけが出る状態から始めるのが望ましい。

```
 APPROVED | 部内勉強会 | 2026-06-02 10:00:00
 PENDING | 部署合同レビュー | 2026-06-03 14:00:00
```

3行以上出る場合は、以前の確認で作った予約が残っている。最後の「後片付け」の SQL を先に実行してから始める。

### 覚えておく情報

| 種別 | 値 |
|---|---|
| リソース | **第1会議室（要承認）** / プロジェクターA（即時確定） / 社用車A（即時確定） |
| ログインできる人 | 田中 花子（一般社員） / 鈴木 一郎（承認者） / 管理 太郎（管理者） |

### ログインとログアウトのやり方（全シナリオ共通）

ブラウザからの通常のサインインはローカルでは動かない。開発用のボタンを使う。

**ログインする**

1. ブラウザで `http://localhost:3000/auth/signin` を開く。
2. 画面に「BookFlow」「施設・備品予約システム」と表示され、その下に「サインイン」ボタンがある。**この「サインイン」ボタンは押さない**（ローカルでは動かない）。
3. さらに下に区切り線があり、「開発用：ロールを選択してログイン（cognito-local シードユーザー）」という小さな文字がある。
4. その下に並ぶ3つのボタンから、使いたいロールを押す。
   - `一般社員（MEMBER）でログイン`
   - `承認者（APPROVER）でログイン`
   - `管理者（ADMIN）でログイン`
5. 押すとダッシュボードに移動する。画面右上に名前（例「田中 花子」）とロール（例「一般社員」）が出る。

**ログアウトする**

画面右上の `サインアウト` を押す。サインイン画面に戻る。

**画面左側のメニュー**

ログインすると左側に縦のメニューが出る。ロールによって項目が変わる。

| ロール | メニュー項目 |
|---|---|
| 一般社員 | ダッシュボード / リソース一覧 / マイ予約 |
| 承認者 | ダッシュボード / リソース一覧 / マイ予約 / **承認待ち一覧** |
| 管理者 | ダッシュボード / リソース一覧 / マイ予約 / 承認待ち一覧 / リソース管理 / ユーザー管理 |

## シナリオ 1. 下書きでも入力は必須であることを確認する

**目的**: 下書き保存でも、通常の申請と同じ入力チェックが働くことを確認する（AC-01-5）
**ロール**: 一般社員（田中 花子）

### 打鍵手順

1. `一般社員（MEMBER）でログイン` でログインする。
2. 左メニューの `リソース一覧` を押す。
3. 「第1会議室」のカードの中にある `詳細を見る →` を押す。
4. リソース詳細の画面が開く。説明文の下にある **`このリソースを予約する`** を押す。
   - この導線で開くと、予約申請フォームの `リソース *` に「第1会議室（要承認）」があらかじめ選ばれた状態になる。
   - アドレス欄に `http://localhost:3000/reservations/new` を直接入力してもよい。その場合はリソースが未選択の状態で開く。
5. 「予約申請」という見出しの画面が開く。入力欄は上から順に次のとおり。
   - `リソース *`（「リソースを選択してください」と書かれた選択欄）
   - `開始日時 *`
   - `終了日時 *`
   - `利用目的 *`
   - `参加人数`
6. 画面を下にスクロールすると、ボタンが3つ横に並んでいる。
   `予約を申請する` / `下書き保存` / `キャンセル`
7. **何も入力しない状態で** 真ん中の `下書き保存` を押す。

### 期待する画面

各入力欄の下に赤い文字でエラーが出る。アドレスは `/reservations/new` のまま変わらない。

```
リソース *
  （選択欄）
  有効なリソース ID を選択してください    ← 手順4の導線で開いた場合、リソースは選択済みなのでこの行は出ない

開始日時 *
  開始日時は必須です

終了日時 *
  終了日時は必須です

利用目的 *
  利用目的は必須です
```

予約は作られない。

### チェック

- [ ] 1-1 何も入力せずに `下書き保存` を押すとエラーが出る
- [ ] 1-2 画面が移動しない（予約が作られない）

> **なぜこうなっているか**：「入力途中の保存」には対応していません。利用目的や日時を空のまま保存できるようにするには、データベースの `NOT NULL` 制約を外す変更が必要で、工数が課題の見積もりに収まらないためスコープ外としました。下書きは「内容は揃っているが、まだ申請したくない」状態を表します。

## シナリオ 2. 下書きとして保存する

**目的**: 下書き保存で `DRAFT` の予約が作られ、詳細画面に移ることを確認する（AC-01-1、AC-01-6）
**ロール**: 一般社員（田中 花子）
**前のシナリオからの続き**: シナリオ1の画面のまま進める

### 打鍵手順

1. `リソース *` が未選択（「リソースを選択してください」と表示）の場合は、その箱を押す。
   すでに「第1会議室（要承認）」が選ばれている場合はこの手順を飛ばす。
2. 選択肢が3つ（`第1会議室（要承認）` / `プロジェクターA（即時確定）` / `社用車A（即時確定）`）出るので、
   `第1会議室（要承認）` を押す。
3. `開始日時 *` の欄を押し、`2026/12/15 10:00` を入力する。
   - 日付時刻の入力欄なので、キーボードで打つか、欄の右端のカレンダーアイコンから選ぶ。
   - 入力順は環境によって `年/月/日` か `月/日/年` のどちらかになる。欄に表示される薄い文字（プレースホルダ）の並びに従う。
   - **年の欄が4桁ちょうど（`2026`）になっているか必ず確認する。** 下の注意を参照。
4. `終了日時 *` の欄に `2026/12/15 12:00` を入力する。同じく年が4桁であることを確認する。

> **⚠ 日時入力の既知の不具合**
>
> 年が4桁以外（`20261` のように5桁、など）になっていると、保存時に
> **「リクエストボディが不正です。」というエラーになり、予約が作られません。**
>
> 年の欄にカーソルがある状態で数字を打ち足すと、`2026` が `20261` に変わってしまうことがあります。
> いったん年の欄を選択し直してから `2026` と打つか、カレンダーアイコンから日付を選ぶと確実です。
>
> これは下書き保存に限らず、**`予約を申請する`（通常の申請）でも同じく起きる既存の不具合**です。
> 日時を整形する処理が「文字列の長さが16文字のときだけ秒を補う」という作りになっており、
> 年が4桁でないと長さが変わって秒が補われず、バックエンドが日時として解釈できないことによります。
> 詳細は[Build and Test の残課題](./build-and-test-summary.md)を参照。
5. `利用目的 *` の欄に **`下書きの確認`** と入力する。
6. `参加人数` の欄に `4` と入力する。
7. `下書き保存` を押す。

### 期待する画面

アドレスが `http://localhost:3000/reservations/<長い英数字>` に変わり、「予約詳細」の画面になる。
**「マイ予約」の一覧ではなく、作った予約そのものの画面に移る**のが正しい。

画面の内容は次のとおり。

```
← 予約一覧に戻る
予約詳細                                    ［ドラフト］   ← 右上に灰色のバッジ
┌────────────────────────────────┐
│ 第1会議室                                              │
│ 申請者      田中 花子                                   │
│ 開始日時    2026/12/15 10:00:00                        │
│ 終了日時    2026/12/15 12:00:00                        │
│ 利用目的    下書きの確認                                 │
│ 参加人数    4 名                                        │
│ 申請日時    （今日の日時）                               │
│ 更新日時    （今日の日時）                               │
└────────────────────────────────┘
［予約内容を編集する］［正式に申請する］
```

### チェック

- [ ] 2-1 予約詳細画面（`/reservations/<id>`）に移動した
- [ ] 2-2 右上のバッジが **「ドラフト」** になっている（灰色の背景で文字が読める）
- [ ] 2-3 ボタンが `予約内容を編集する` と `正式に申請する` の2つ
- [ ] 2-4 **`予約をキャンセルする` が表示されない**

> **`予約をキャンセルする` が出ないのは意図したとおりです**。下書きの削除や破棄は今回の課題のスコープ外としました（要求シートの要件には「削除できる」とありますが、受入条件に項目がなく、API にも削除の口がないため）。

### このあと使う情報

**このページのアドレス（URL）をコピーしてメモしておく。** シナリオ6と7で使う。
ブラウザのアドレス欄を選択してコピーすればよい。

**目的**: 既存の不具合の現れ方を把握する（修正は別課題）
**ロール**: 一般社員（田中 花子）

### 期待する画面

実際にはシナリオ6と同じ開発用エラーオーバーレイが出る。赤い文字の内容だけが違う。

```
┌──────────────────────────────────────────────┐
│ ［Runtime ApiClientError］［Server］                                  │
│                                                                      │
│ 同一リソースの同一時間帯に承認済みまたは承認待ちの予約が存在します。   │
│                                              ↑ 赤い文字               │
│  src/lib/api-client.ts (68:9) @ assertOk                             │
│                                                                      │
│ Call Stack 9                                                         │

└──────────────────────────────────────────────┘
```

赤い文字が `同一リソースの同一時間帯に…` になっていれば、バックエンドが 409（重複）を返したということである。
左下の `✕` でオーバーレイを閉じると、素のエラー画面が見える。

### 続きの打鍵手順（データが壊れていないことの確認）

4. ブラウザの戻るボタン、または左メニューの `マイ予約` → `ドラフト` タブを押す。

### 期待する画面

`重なる下書き` が **まだ「ドラフト」のまま一覧に残っている**。
バックエンドは 409 を返して処理を巻き戻すため、予約は壊れていない。

### チェック

- [ ] 11-1 重複する下書きの正式申請で `同一リソースの同一時間帯に…` のエラーが出る（既知の制約）
- [ ] 11-2 失敗後も予約は「ドラフト」のまま残っている（データは壊れない）

> **原因と扱い**
>
> Server Action（サーバー側の処理）が投げたエラーがブラウザ側に届くとき、エラーの種類の情報が失われます。
> そのため「重複エラーかどうか」の判定ができず、用意したメッセージに分岐できません。
>
> **既存の予約申請フォームも同じ作り**で、シナリオ10の手順9（通常の申請で重なる時間帯）でも同じ画面になります。
> つまり今回の変更で持ち込んだ不具合ではありません。
>
> 直すには Server Action の返し方をエラー送出から戻り値に変える必要があり、
> 申請フォーム・編集フォーム・正式申請ボタンの3箇所に影響します。
> 下書き保存の課題の範囲を超えるため、**別課題として切り出す**方針としました。
