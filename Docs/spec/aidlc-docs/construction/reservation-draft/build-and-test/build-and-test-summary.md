## 4. 残課題

### 409 のエラー表示が機能しない（既存の不具合・別課題）

Server Action が投げた例外はクライアントに渡るときクラス情報を失うため、
`err instanceof ApiClientError` が成立せず、409 を捕捉できない。
結果としてインラインメッセージではなく Next.js の既定エラー画面が出る。

ブラウザで検証したところ、**既存の予約申請フォームでも同じ挙動**であり、今回の変更で持ち込んだものではない。
影響するのは予約申請フォーム・予約編集フォーム・正式申請ボタンの3箇所。

修正には Server Action の戻り値を例外から結果型に変える必要があり、呼び出し側3箇所とそのテストに波及する。
下書き保存のスコープを超えるため、学習者の判断により **別課題として切り出す** こととした（2026-10-02）。

データが壊れる問題ではない。409 で失敗しても予約は `DRAFT` のまま残る。

### 日時入力で年が4桁でないと保存できない（既存の不具合・2026-10-09 発見）

学習者の動作確認で「リクエストボディが不正です。」というエラーが報告され、再現した。

原因は `frontend/src/server/actions/reservations.ts` の `toIsoWithSeconds` にある。

```ts
function toIsoWithSeconds(value: string): string {
  if (value.length === 16) return `${value}:00`;
  return value;
}
```

`datetime-local` の値は通常 `2026-12-15T10:00`（16文字）だが、年が4桁でない場合は長さが変わる。
たとえば年の欄に数字を打ち足して `20261` になると `20261-12-15T10:00`（17文字）となり、
秒が補われないままバックエンドに渡る。
`LocalDateTime` として解釈できず `HttpMessageNotReadableException` となり、
`GlobalExceptionHandler` が 400 と「リクエストボディが不正です。」を返す。

**この関数は本ユニットより前から存在し、通常の予約申請（`予約を申請する`）でも同じ結果になる**ことを実機で確認した。
今回の変更で持ち込んだものではない。

想定される直し方は2通りある。

1. 長さではなく「秒が欠けているか」で判定する（`/T\d{2}:\d{2}$/` にマッチしたら `:00` を補う）。
   1行で済むが、年が5桁のまま西暦 20261 年の予約が黙って作られることになる。
2. Zod スキーマに年の妥当な範囲の検証を足し、入力欄の下にエラーを出す。
   利用者にとっては分かりやすいが、検証の方針を決める必要がある。

学習者の判断により **別課題として切り出す** こととした（2026-10-09）。
動作確認は年を4桁に直せば進められるため、手順書のシナリオ2に注意書きを追加した。
