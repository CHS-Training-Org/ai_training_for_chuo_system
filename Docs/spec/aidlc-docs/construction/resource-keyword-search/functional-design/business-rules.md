# Business Rules — `resource-keyword-search`

各ルールに、対応する要件（FR）と受入基準（AC）を示す。

## BR-01 照合対象は名称と説明文

キーワードは `Resource.name` と `Resource.description` の2つのフィールドに対して照合する。`location` その他のフィールドは対象としない。

- **対応**: FR-02 / AC-01-1、AC-01-2

## BR-02 部分一致で照合する

キーワードは前方一致でも完全一致でもなく、フィールド値の任意の位置に含まれていれば一致とする。

- **対応**: FR-02 / AC-01-1

## BR-03 名称と説明文のいずれかが一致すれば採用する

2つのフィールドに対する照合結果を OR で結ぶ。両方に一致する必要はない。

`description` が null の行では、その側の比較結果が SQL の3値論理で UNKNOWN になる。`name` 側が一致していれば `TRUE OR UNKNOWN` は TRUE となり行は残る。どちらにも一致しない場合は `FALSE OR UNKNOWN` が UNKNOWN となり、WHERE 句で行は採用されない。いずれも意図どおりであるため、`COALESCE` 等による回避は行わない。

- **対応**: FR-02、FR-14 / AC-01-2、AC-01-3

## BR-04 大文字小文字を区別しない

照合対象の値とキーワードの双方を小文字に変換してから比較する。PostgreSQL 固有の `ILIKE` は使わない。テスト DB が H2（PostgreSQL 互換モード）であり、`ILIKE` の受理が DB と Hibernate のバージョンに依存するためである。

小文字変換はロケール非依存で行う（Java 側は `Locale.ROOT` を指定する）。ロケール依存の変換では、トルコ語ロケールで `I` が `ı` になるなど、環境によって結果が変わる。

- **対応**: FR-03、FR-13 / AC-02-1、AC-02-2

## BR-05 キーワードの正規化

照合に用いる文字列は次の手順で決める。

1. 入力が `null` なら、キーワード条件を課さない。
2. 前後の空白文字を除去する（全角空白を含む。Java の `String.strip()` を用いる）。
3. 除去後が空文字なら、キーワード条件を課さない。
4. それ以外は、除去後の文字列を照合に用いる。

内部の空白は保持し、入力全体を1つのリテラルとして扱う。空白区切りによる AND 分解は行わない。

- **対応**: FR-05、FR-06 / AC-05-3、AC-05-4

## BR-06 ワイルドカードはリテラルとして扱う

キーワードに含まれる次の文字は、LIKE のパターン記号ではなく文字そのものとして照合する。

| 文字 | LIKE での本来の意味 | 本システムでの扱い |
|---|---|---|
| `%` | 任意の0文字以上 | リテラル |
| `_` | 任意の1文字 | リテラル |
| `\` | エスケープ文字 | リテラル |

エスケープ文字には `\` を用い、**バックスラッシュを最初にエスケープしてから** `%` と `_` をエスケープする。順序を誤ると、`%` のエスケープで挿入した `\` がさらにエスケープされて二重になる。

エスケープ後の文字列を前後に `%` で囲んで LIKE パターンとし、LIKE 式にはエスケープ文字を明示する。

- **対応**: FR-15 / AC-03-1、AC-03-2

## BR-07 他のフィルタとは AND で組み合わせる

キーワード条件は、ロール別の有効フラグ条件およびカテゴリ条件と AND で結合する。空き確認期間（`from` / `to`）による除外とも AND の関係になる。

- **対応**: FR-04 / AC-04-1、AC-04-2、AC-04-3

## BR-08 キーワード条件は2つの取得経路の双方に適用する

合成した述語は `from` / `to` の分岐より前に1回だけ組み立て、ページネーション経路と全件取得経路の双方が同じものを使う。

- **対応**: FR-12 / AC-04-2、AC-04-4

## BR-09 ロール別の可視範囲はキーワードの有無で変わらない

非 ADMIN に対しては `isActive = true` の制約を常に課す。ADMIN に対しては課さない。この規則はキーワード指定の有無にかかわらず適用される。

- **対応**: FR-11 / AC-09-1、AC-10-1、AC-10-2

## BR-10 キーワードの最大長は 100 文字

前後の空白を除去した後の文字列が 100 文字を超える場合、`400 Bad Request`（`code: VALIDATION_ERROR`）を返す。100 文字は検索対象である `resources.name` の列長（varchar 100）に合わせた値であり、既存 DTO の `@Size(max = 100)` と規則が揃う。

検証の対象を除去後の文字列とするのは、貼り付け時に付いた前後の空白が長さ超過の原因になると利用者に理解しにくいためである。

- **対応**: 設計判断（Functional Design の Q2）

## BR-11 未指定時は既存の挙動を変えない

`keyword` パラメータを指定しない要求に対する結果は、本変更の前と一致する。カテゴリのみ、期間のみ、いずれも未指定のいずれの場合も同様である。

- **対応**: FR-05、NFR-01 / AC-05-4、AC-11-1、AC-11-2、AC-11-4

## BR-12 期間パラメータの検証は変更しない

`from` と `to` の片方のみを指定した場合に `400 Bad Request`（`code: VALIDATION_ERROR`）を返す既存の検証は、そのまま維持する。

- **対応**: FR-05 / AC-11-3
