# Story Generation Plan — usage-report

## 方針

- **Breakdown Approach**: Feature-Based を基本とし、アクセス制御（USG-03）だけはロール別の視点が必要なため Persona-Based の要素を取り入れたハイブリッドとする
- **ペルソナ**: 3 ペルソナ（ADMIN：集計を見る、MEMBER：見られない、APPROVER：見られない）
- **粒度**: 要件（USG-01〜06）と受入条件 9 項目に対応する 5 ストーリーに分解する
- **フォーマット**: 「〜として、〜したい。それによって〜できる」形式 + Gherkin 形式の受入条件（既存ユニットの stories.md と同じ形式を踏襲）

## 実行チェックリスト

- [x] Step A: `personas.md` を生成する（ADMIN・MEMBER・APPROVER の 3 ペルソナ）
- [x] Step B: `stories.md` を生成する。以下の 5 ストーリー候補を INVEST 基準で検証しながら作成する
  - US-01 リソース別の利用実績の表示（`/admin/reports` の棒グラフ 2 本と表、並び順、時間の整形、期間未指定は全期間）
  - US-02 期間を指定した集計（期間重複で対象を選ぶ、境界をまたぐ予約は 1 件と数え合計時間は切り詰める、`from`/`to` の片方だけは 400、リセットで全期間に戻る）
  - US-03 承認済みのみの集計（`APPROVED` 以外は件数にも時間にも含まれない、過去・未来を問わない）
  - US-04 実績 0 件のリソースの表示（有効なリソースは常に表示、無効なリソースは期間内に実績があるときだけ表示）
  - US-05 権限のないロールの拒否（MEMBER・APPROVER は 403、未認証は 401、サイドナビの「利用実績」は ADMIN にだけ表示、ページも非 ADMIN には 403 画面）
- [x] Step C: 各ストーリーに受入条件（Gherkin 形式）を記載し、requirements.md の受入条件 9 項目（生成中に追加した `from >= to` の 400 を含む）（OpenAPI への反映と集計ロジックのユニットテストは US-02〜US-04 のテスト観点と非機能要件として対応付ける）をすべてカバーしていることを確認する

## 確認事項

requirements.md の決定事項（10 件）と既定の前提により、ストーリー作成に必要な曖昧点はすべて解消済みと判断する。追加の確認質問はない。
