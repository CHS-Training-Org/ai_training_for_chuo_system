# User Stories — 予約の下書き保存

**対象**: `docs-next/docs/spec/enhancements/intermediate/reservation-draft.md`
**ペルソナ**: [`personas.md`](./personas.md)
**要件**: [`requirements.md`](../../requirements/reservation-draft/requirements.md)
**分解方式**: ハイブリッド（User Journey を主軸に、ロール差が生じる振る舞いを Persona で切り出す）
**受入基準の形式**: Given/When/Then

各受入基準の末尾に検証レイヤーを示す。**BE** はバックエンドのテスト、**FE** はフロントエンドのテスト、**E2E** はブラウザでの動作確認を指す。

---

## US-01 予約を下書きとして保存する

**P-01 一般社員**として、入力した予約内容を申請せずに保存したい。
なぜなら、参加人数や利用目的の確認が終わる前に席を立つことがあり、入力をやり直したくないため。

### 受入基準

- **AC-01-1**: 予約申請フォームに必要な項目を入力した状態で、「下書き保存」ボタンを押したとき、ステータス `DRAFT` の予約が作成される。（BE / FE / E2E）
- **AC-01-2**: `draft` に `true` を指定して `POST /api/reservations` を呼んだとき、リソースの `requires_approval` が `true` でも `false` でも、ステータスは `DRAFT` になる。（BE）
- **AC-01-3**: `draft` を省略して `POST /api/reservations` を呼んだとき、従来どおり `requires_approval` に応じて `PENDING` または `APPROVED` になる。（BE）
- **AC-01-4**: 同じリソースの同じ時間帯に `PENDING` の予約が既に存在する状態で、`draft` に `true` を指定して予約を作成したとき、409 は返らず `DRAFT` の予約が作成される。下書きは時間帯を占有しないため。（BE）
- **AC-01-5**: 「下書き保存」でも、リソース・開始日時・終了日時・利用目的は入力を必須とする。未入力のまま押したとき、通常の申請と同じバリデーションエラーが表示される。（FE / BE）
- **AC-01-6**: 下書き保存の成功後、作成された下書きの詳細画面に遷移する。（FE / E2E）

## US-02 保存した下書きを一覧から見つける

**P-01 一般社員**として、保存した下書きを予約一覧から探したい。
なぜなら、後日戻ってきたときに、どの予約が未申請なのかを他のステータスと区別して把握したいため。

### 受入基準

- **AC-02-1**: 予約一覧画面を開いたとき、ステータスフィルタのタブに「ドラフト」が表示される。（FE / E2E）
- **AC-02-2**: 「ドラフト」タブを選んだとき、自分の `DRAFT` 予約だけが一覧に表示される。（FE / E2E）
- **AC-02-3**: 「すべて」タブを選んだとき、`DRAFT` を含む全ステータスの予約が表示される。（FE / E2E）
- **AC-02-4**: 一覧の `DRAFT` 行のステータス欄に「ドラフト」のバッジが表示される。（FE）

---

## US-03 下書きの内容を直す

**P-01 一般社員**として、保存した下書きの内容を後から直したい。
なぜなら、関係者への確認が取れてから日時や参加人数を確定させるため。

### 受入基準

- **AC-03-1**: 自分の `DRAFT` 予約の詳細画面を開いたとき、編集ボタンが表示される。（FE / E2E）
- **AC-03-2**: `DRAFT` 予約に対して `PUT /api/reservations/{id}` を呼んだとき、内容が更新され、ステータスは `DRAFT` のまま変わらない。（BE）
- **AC-03-3**: 編集画面を `DRAFT` 予約の ID で開いたとき、`notFound()` にならずフォームが表示される。（FE）
- **AC-03-4**: 他人の `DRAFT` 予約に対して `PUT` を呼んだとき、403 が返る。（BE）
- **AC-03-5**: `APPROVED` や `CANCELLED` の予約に対して `PUT` を呼んだとき、従来どおり 422 が返る。（BE）

---

## US-04 下書きを正式に申請する

**P-01 一般社員**として、内容が固まった下書きをその場で正式申請したい。
なぜなら、別の画面に入力し直すことなく、取り置いた内容をそのまま申請に進めたいため。

### 受入基準

- **AC-04-1**: 自分の `DRAFT` 予約の詳細画面を開いたとき、正式申請ボタンが表示される。（FE / E2E）
- **AC-04-2**: `DRAFT` 予約に対して `status` に `"PENDING"` を指定して `PUT` を呼び、リソースの `requires_approval` が `true` のとき、ステータスが `PENDING` になり `approval_steps` が1件生成される。（BE）
- **AC-04-3**: 同じ操作でリソースの `requires_approval` が `false` のとき、ステータスは `PENDING` になり `approval_steps` は生成されない。この予約は承認待ち一覧に現れず進まなくなる（既知の制約。要件定義 §7 を参照）。（BE）
- **AC-04-4**: 正式申請の時点で重複予約チェックを実行する。下書きの時間帯が他の `PENDING` または `APPROVED` の予約と重なっているとき、409 `RESERVATION_CONFLICT` が返り、ステータスは `DRAFT` のまま変わらない。（BE）
- **AC-04-5**: `DRAFT` 以外のステータスの予約に対して `status` に `"PENDING"` を指定して `PUT` を呼んだとき、422 が返る。（BE）
- **AC-04-6**: `status` に `"PENDING"` 以外の値（`"APPROVED"` や `"CANCELLED"` 等）を指定して `PUT` を呼んだとき、422 が返る。（BE）
- **AC-04-7**: `status` を省略して `PUT` を呼んだとき、内容のみが更新され、ステータスは変わらない。（BE）
- **AC-04-8**: 正式申請の成功後、詳細画面のステータス表示が更新され、正式申請ボタンが消える。（FE / E2E）

## US-05 下書きが承認業務に流れ込まない

**P-02 承認者**として、確定していない予約が承認待ち一覧に現れないでほしい。
なぜなら、申請者がまだ検討している段階の予約を承認してしまうと、意図しない確定が起きるため。

### 受入基準

- **AC-05-1**: `draft` に `true` を指定して予約を作成したとき、`approval_steps` が1件も生成されない。（BE）
- **AC-05-2**: `DRAFT` の予約が存在する状態で承認待ち一覧（`GET /api/approvals`）を呼んだとき、その予約に紐づくステップは含まれない。（BE）
- **AC-05-3**: 承認者が `/approvals` 画面を開いたとき、他人の下書きは表示されない。（E2E）

---

## US-06 他人の下書きを開けない

**P-02 承認者**として、他人の下書きの詳細を開けないでほしい。
なぜなら、承認フローに流れない予約の内容を承認者が見る理由がなく、申請者にとっても検討中の内容を見られたくないため。

### 受入基準

- **AC-06-1**: APPROVER が他人の `DRAFT` 予約に `GET /api/reservations/{id}` でアクセスしたとき、403 が返る。（BE）
- **AC-06-2**: MEMBER が他人の `DRAFT` 予約にアクセスしたとき、403 が返る。（BE）
- **AC-06-3**: APPROVER が他人の `PENDING` や `APPROVED` の予約にアクセスしたとき、従来どおり 200 が返る。`DRAFT` 以外の可視範囲は変えない。（BE）
- **AC-06-4**: 予約一覧（`GET /api/reservations`）で、APPROVER には従来どおり自分の予約のみが返る。他人の下書きは含まれない。（BE）

> 403 を受けたときの画面表示は検証対象に含めない。
> frontend にエラーバウンダリ（`error.tsx`）が存在せず、他人の予約にアクセスした場合の既存挙動（Next.js の既定エラー画面）と同一になるため。
> エラーバウンダリの追加は本課題のスコープ外（要件定義 §8）。

## US-08 下書きを破棄する

**P-01 一般社員**として、不要になった下書きを消したい。
なぜなら、申請しないと決めた案が一覧に残り続けると、本当に対応が必要な予約が埋もれるため。

### 受入基準

- **AC-08-1**: 自分の `DRAFT` 予約の詳細画面に削除ボタンが表示される。（FE）
- **AC-08-2**: 削除ボタンを押すと確認ダイアログが表示され、確認せずに削除されない。（FE）
- **AC-08-3**: 確認すると `DELETE /api/reservations/{id}` が呼ばれ、予約一覧へ遷移する。（FE）
- **AC-08-4**: `DRAFT` の予約を削除するとレコードごと削除され、204 が返る。（BE）
- **AC-08-5**: `DRAFT` 以外の予約を削除しようとすると 422 が返る。（BE）
- **AC-08-6**: 他人の下書きを削除しようとすると 403 が返る。ADMIN も同様に 403。（BE）
- **AC-08-7**: 削除ボタンは `DRAFT` かつ申請者本人のときのみ表示される。ADMIN には表示されない。（FE）

> 確定済みの予約（`PENDING` / `APPROVED`）はキャンセルで `CANCELLED` に遷移させ履歴を残す。
> 削除の対象を `DRAFT` に限るのは、確定前の予約に履歴を残す必要がないためである。

## US-07 管理者が下書きを把握する

**P-03 管理者**として、他人の下書きも含めて予約の状況を把握したい。
ただし他人の下書きを代理で編集したり申請したりはしない。
なぜなら、リソースの利用見込みを把握する必要がある一方、申請の意思決定は申請者本人に属するため。

### 受入基準

- **AC-07-1**: ADMIN が他人の `DRAFT` 予約に `GET /api/reservations/{id}` でアクセスしたとき、200 が返る。（BE）
- **AC-07-2**: ADMIN が予約一覧の「ドラフト」タブを開いたとき、全ユーザーの `DRAFT` 予約が表示される。（BE / FE）
- **AC-07-3**: ADMIN が他人の `DRAFT` 予約に `PUT` を呼んだとき、403 が返る。既存の権限マトリクスどおり、ADMIN に更新権限はない。（BE）
- **AC-07-4**: ADMIN が他人の `DRAFT` 予約の詳細画面を開いたとき、編集ボタンと正式申請ボタンが表示されない。（FE）

## INVEST 適合の確認

| 基準 | 確認結果 |
|---|---|
| Independent | US-02 から US-04 は US-01 が作る下書きを前提とするが、テストデータを直接用意すれば単独で検証できる。実装順序の強い依存はない |
| Negotiable | 各ストーリーは利用者の目的として書かれており、実装手段（`@PreAuthorize` の採否等）には踏み込んでいない |
| Valuable | 各ストーリーが、取り置き・発見・修正・申請・誤承認の防止という具体的な価値を述べている |
| Estimable | いずれも変更対象のレイヤーが特定でき、見積もり可能な粒度である |
| Small | 1ストーリーあたり数十分から1時間程度。最大の US-04 でも Service のメソッド1つと画面の操作1つに収まる |
| Testable | 受入基準41件がすべて検証レイヤーを持ち、そのままテストケースに対応づけられる |
