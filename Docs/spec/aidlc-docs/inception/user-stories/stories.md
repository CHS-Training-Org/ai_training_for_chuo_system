# User Stories — 予約の下書き保存（Issue #30）

分割アプローチ：User Journey-Based（下書き保存 → 一覧確認 → 再編集 → 正式申請 → 削除の操作フロー順）。受入条件は要求シートと同じ素の箇条書き形式。

---

## Story 1: 下書きとして保存する

**As a** MEMBER（申請者本人）
**I want to** 予約申請フォームの入力内容を、正式申請せずに `DRAFT` として保存したい
**So that** 内容が固まっていない予約や後で見直したい予約を、承認フローに乗せずに保持できる

### 受入条件

- 予約申請フォーム（`/reservations/new`）に「下書き保存」ボタンがある
- 「下書き保存」をクリックすると、`DRAFT` ステータスで予約が保存される
- 下書き保存時も既存の必須項目（リソース・開始日時・終了日時・利用目的）は入力必須のまま（D1）
- 下書き保存時は重複予約チェックを行わない（D5）。他人の予約と時間帯が重複していても保存できる
- 下書き保存時は承認ステップ（`approval_steps`）を生成しない

**トレーサビリティ**: RSV-08（要求シート RSV-01）、RSV-12（要求シート RSV-04）／Design Decisions D1・D5

---

## Story 2: 下書き一覧を確認する

**As a** MEMBER（申請者本人）
**I want to** 自分が保存した下書きを一覧で確認したい
**So that** 後からどれを再編集・正式申請するか選べる

### 受入条件

- 予約一覧（`/reservations`）に `DRAFT` を確認できるフィルタ（タブ）がある
- 自分の `DRAFT` はステータスバッジ付きで一覧に表示される
- ADMIN は他ユーザーの `DRAFT` を含む全予約を一覧で確認できる（既存の全件閲覧の延長）

**トレーサビリティ**: RSV-13（要求シート RSV-05）／Design Decision D4

---

## Story 3: 下書きの詳細を確認する（本人以外は拒否される）

**As a** MEMBER（申請者本人）
**I want to** 自分の下書きの詳細を確認したい
**As an** APPROVER または他の MEMBER
**I want NOT to** 他人の下書きの詳細を見られてしまいたくない（意図しない閲覧を防ぎたい）

### 受入条件

- 申請者本人は `DRAFT` の詳細（`/reservations/{id}`）を確認できる
- 申請者本人以外（APPROVER・他の MEMBER）が `DRAFT` の詳細にアクセスすると 403 が返る
- ADMIN は例外的に他人の `DRAFT` の詳細を確認できる
- `PENDING`/`APPROVED`/`REJECTED`/`CANCELLED` の予約に対する既存の閲覧範囲（APPROVER は全件閲覧可）は変更しない

**トレーサビリティ**: RSV-09（要求シート RSV-02 前半）／Design Decision D4

---

## Story 4: 下書きを再編集する

**As a** MEMBER（申請者本人）
**I want to** 保存した下書きの内容（日時・目的・参加人数）を編集し直したい
**So that** 正式申請する前に内容を調整できる

### 受入条件

- 下書き詳細ページ（`/reservations/{id}`）から予約編集画面（`/reservations/{id}/edit`）へ遷移できる
- `DRAFT` の編集画面では、内容を更新して `DRAFT` のまま保存し直せる（正式申請しない場合）
- 編集画面のバリデーション（終了 > 開始等）は既存の予約編集と同じ
- 申請者本人以外は編集できない（ADMIN も含む。既存の `update()` に ADMIN 例外はない）

**トレーサビリティ**: RSV-10（要求シート RSV-03）、RSV-15／Design Decisions D2・D6・D7

---

## Story 5: 下書きを正式申請する

**As a** MEMBER（申請者本人）
**I want to** 内容を確定させた下書きを正式に申請したい
**So that** リソースの `requires_approval` に応じて即座に確定、または承認待ちにできる

### 受入条件

- 下書き詳細ページから「正式申請」を実行できる
- `requires_approval=false` のリソースの下書きを正式申請すると、即座に `APPROVED` になる
- `requires_approval=true` のリソースの下書きを正式申請すると、`PENDING` になり承認ステップが1件生成される
- 正式申請時に重複予約チェックを実行する（下書き保存中に他の予約で枠が埋まっている可能性があるため）。重複していれば 409 が返り `DRAFT` のまま維持される
- バックエンドのステータス遷移テストに `DRAFT → PENDING` および `DRAFT → APPROVED` のケースを含める

**トレーサビリティ**: RSV-10（要求シート RSV-03）、RSV-14／Design Decisions D2・D7

---

## Story 6: 不要になった下書きを削除する

**As a** MEMBER（申請者本人）
**I want to** 不要になった下書きを削除したい
**So that** 一覧を整理できる

### 受入条件

- 下書き詳細ページから既存の「キャンセル」操作で `DRAFT` を `CANCELLED` にできる（物理削除ではない）
- ADMIN も他人の `DRAFT` をキャンセルできる（既存の `cancel()` の所有権チェックをそのまま適用）
- キャンセル後の `DRAFT` は `CANCELLED` として一覧に残る（既存のキャンセル済み予約と同じ扱い）

**トレーサビリティ**: RSV-11（要求シート RSV-02 後半）／Design Decision D3

---

## 検証のみで満たされる受入条件（実装ストーリーではない）

- 「下書き予約は承認一覧に表示されない」：Story 1 で `approval_steps` を生成しない設計から自動的に満たされる。テスト観点としてのみ記録する
