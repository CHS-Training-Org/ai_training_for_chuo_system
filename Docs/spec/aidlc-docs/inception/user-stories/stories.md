# User Stories — リソース一覧のキーワード検索追加

分解方式：User Journey ベースを主軸とし、ロール差が生じる振る舞いを Persona で切り出すハイブリッド
受入基準の形式：Given / When / Then
ペルソナ定義：[personas.md](./personas.md)
要件定義：`Docs/spec/aidlc-docs/inception/requirements/requirements.md`

各受入基準の末尾に検証層を示す。**BE** はバックエンドのユニットテストまたは Controller テスト、**FE** はフロントエンドのユニットテスト、**手動** は画面操作による確認を指す。

---

## ジャーニー A：キーワードで探す

### ST-01 キーワードで一覧を絞り込む

**一般社員**として、**リソース名や説明文に含まれる語句で一覧を絞り込みたい**。
**なぜなら**、リソース件数が増えるとカテゴリだけでは候補が絞りきれず、目当てのものを見つけるまでに時間がかかるからである。

**受入基準**

- AC-01-1: 名称に「会議」を含むリソースと含まないリソースが存在する状態で、キーワード「会議」を入力して「絞り込む」を押したとき、名称に「会議」を含むリソースのみが表示される。（BE / 手動）
- AC-01-2: 説明文にのみ「プロジェクター」を含むリソースが存在する状態で、キーワード「プロジェクター」で絞り込んだとき、そのリソースが結果に含まれる。（BE）
- AC-01-3: 説明文が未設定（null）のリソースが存在する状態で、そのリソースの名称に含まれる語句で絞り込んだとき、そのリソースが結果に含まれる。（BE）
- AC-01-4: 名称にも説明文にも一致しない語句で絞り込んだとき、結果が0件となり「リソースがありません。」が表示される。（BE / 手動）

**関連要件**: FR-01、FR-02、FR-14

---

### ST-02 大文字小文字を意識せずに検索する

**一般社員**として、**入力した語句の大文字小文字が実際の表記と違っても同じ結果を得たい**。
**なぜなら**、リソース名の正確な表記を覚えていないことが多く、表記の違いで見つからないと探し直す手間が生じるからである。

**受入基準**

- AC-02-1: 名称が `Projector Room` のリソースが存在する状態で、キーワード `projector` で絞り込んだとき、そのリソースが結果に含まれる。（BE）
- AC-02-2: 同じ状態でキーワード `PROJECTOR` で絞り込んだとき、AC-02-1 と同じ結果が返る。（BE）

**関連要件**: FR-03、FR-13

---

### ST-03 記号を含む語句をそのまま検索する

**一般社員**として、**`%` や `_` を含む語句を入力したとき、その記号が文字どおりに扱われてほしい**。
**なぜなら**、検索構文を知らないまま記号を入力したときに、意図せず全件が一致したり結果が消えたりすると、システムの挙動が理解できなくなるからである。

**受入基準**

- AC-03-1: 名称に `50%OFF備品` を含むリソースと含まないリソースが存在する状態で、キーワード `50%` で絞り込んだとき、`50%` を名称に含むリソースのみが表示される（全件一致にはならない）。（BE）
- AC-03-2: キーワード `_` で絞り込んだとき、名称または説明文に文字 `_` を含むリソースのみが表示される（任意の1文字への一致にはならない）。（BE）

**関連要件**: FR-15

---

## ジャーニー B：条件を組み合わせる

### ST-04 キーワードとカテゴリ・期間を組み合わせる

**一般社員**として、**キーワードとカテゴリ、利用したい時間帯を同時に指定したい**。
**なぜなら**、「今日の午後に空いている、プロジェクターのある会議室」のように、複数の条件を満たすリソースを一度に絞り込みたいからである。

**受入基準**

- AC-04-1: キーワードとカテゴリを同時に指定したとき、両方の条件を満たすリソースのみが表示される。（BE）
- AC-04-2: キーワードと期間（`from` / `to`）を同時に指定したとき、キーワードに一致し、かつ当該時間帯に `PENDING` / `APPROVED` の予約が無いリソースのみが表示される。（BE）
- AC-04-3: キーワード・カテゴリ・期間の3つを同時に指定したとき、3条件すべてを満たすリソースのみが表示される。（BE）
- AC-04-4: 期間指定ありの状態でキーワードを指定したとき、期間指定なしのときと同じキーワード照合規則が適用される（照合対象・大文字小文字の扱いが一致する）。（BE）

**関連要件**: FR-04、FR-12

> AC-04-2 と AC-04-4 は、`ResourceService.list` が `from` / `to` の有無で内部経路を分けている構造に対応する。期間指定側の経路にキーワード条件が適用されないままだと、ST-01 の受入基準は満たされても本ストーリーが満たされない。

## ジャーニー C：絞り込みをやり直す

### ST-05 キーワード条件だけを解除する

**一般社員**として、**キーワード欄を空にして絞り込み直したとき、キーワード条件だけが外れてほしい**。
**なぜなら**、候補が絞り込まれすぎたときに、カテゴリや期間の指定はそのままでキーワードだけを外して探し直したいからである。

**受入基準**

- AC-05-1: キーワードを指定した状態から、キーワード欄を空にして「絞り込む」を押したとき、URL から `keyword` パラメータが除かれる。（FE / 手動）
- AC-05-2: AC-05-1 の操作の後、キーワードによる絞り込みが行われていない結果が表示される。（BE / 手動）
- AC-05-3: キーワード欄に空白のみを入力して「絞り込む」を押したとき、未指定と同じ結果が返る。（BE）
- AC-05-4: `keyword` パラメータを付けずにリソース一覧を要求したとき、本変更の前と同じ結果が返る。（BE）

**関連要件**: FR-05、FR-06

---

### ST-06 すべてのフィルタを一度に解除する

**一般社員**として、**「リセット」を押したとき、キーワードを含むすべての絞り込みが解除されてほしい**。
**なぜなら**、条件を複数変更した後は、個別に外すより初期状態に戻してやり直すほうが早いからである。

**受入基準**

- AC-06-1: キーワード・カテゴリ・期間を指定した状態で「リセット」を押したとき、`/resources`（クエリパラメータなし）に遷移する。（FE / 手動）
- AC-06-2: 遷移後、一覧の絞り込みが解除され全件が表示される。（手動）

**関連要件**: FR-09

> **入力欄の表示について**：「リセット」を押しても、入力欄に打ち込んだ文字列は残る。フィルタフォームの各入力は非制御コンポーネント（`defaultValue`）であり、`defaultValue` はマウント時にしか反映されない。App Router 内での遷移では `ResourceFilterForm` が再マウントされないため、DOM 上の入力値はそのまま維持される。
>
> これはキーワード追加以前からの挙動であり、カテゴリと日時の各入力も同じ状態になる。本課題はこの既存挙動を変更しない。入力欄も併せてクリアする改善は、キーワードだけでなくフィルタフォーム全体に及ぶため別課題として扱う。

## ジャーニー D：結果を読み進める

### ST-07 キーワードを保ったままページを送る

**一般社員**として、**検索結果が複数ページにわたるとき、ページを送ってもキーワード条件が保たれてほしい**。
**なぜなら**、ページを送るたびに条件が外れると、絞り込みの意味がなくなるからである。

**受入基準**

- AC-07-1: キーワードで絞り込んだ結果が2ページ以上ある状態で「次へ」を押したとき、遷移先の URL に `keyword` が保持されている。（FE / 手動）
- AC-07-2: 遷移後の2ページ目に、同じキーワード条件を満たすリソースのみが表示される。（手動）

**関連要件**: FR-10

---

### ST-08 入力したキーワードが画面に残る

**一般社員**として、**絞り込んだ後も、入力したキーワードが入力欄に表示されていてほしい**。
**なぜなら**、いま何で絞り込んでいるかが分からないと、条件を変えるべきか判断できないからである。また、絞り込んだ状態の URL を同僚に共有したとき、相手の画面でも同じ条件が見えてほしい。

**受入基準**

- AC-08-1: `keyword` を含む URL でリソース一覧を開いたとき、キーワード入力欄にその値が初期表示される。（手動）
- AC-08-2: 絞り込み後にブラウザを再読込したとき、キーワード条件と入力欄の表示がいずれも維持される。（手動）

**関連要件**: FR-07、FR-08

---

## ジャーニー E：ロールによる違い（Persona 切り出し）

### ST-09 管理者が無効リソースを検索で見つける

**管理者**として、**無効化したリソースもキーワード検索の対象に含めたい**。
**なぜなら**、リソース台帳を維持するうえで、無効化済みのものを名称で探して再有効化や内容修正の判断をする必要があるからである。

**受入基準**

- AC-09-1: `isActive = false` のリソースが存在する状態で、ADMIN がそのリソースの名称に含まれる語句で検索したとき、そのリソースが結果に含まれる。（BE）
- AC-09-2: AC-09-1 の結果表示において、無効リソースはグレーアウトと「無効」バッジで区別される（既存表示の踏襲）。（手動）

**関連要件**: FR-11

---

### ST-10 一般社員の検索結果に無効リソースが現れない

**一般社員**として、**無効化されたリソースが検索結果に出てこないでほしい**。
**なぜなら**、予約できないリソースが候補に混ざると、選んでから予約できないと分かって手戻りになるからである。

**受入基準**

- AC-10-1: `isActive = false` のリソースが存在する状態で、MEMBER がそのリソースの名称に含まれる語句で検索したとき、そのリソースは結果に含まれない。（BE）
- AC-10-2: APPROVER が同じ操作をしたとき、AC-10-1 と同じ結果になる。（BE）

**関連要件**: FR-11

---

## ジャーニー F：既存の振る舞いを壊さない

### ST-11 既存のフィルタ操作が変わらない

**既存の利用者**として、**キーワード検索が追加されても、これまでのカテゴリ・期間フィルタの使い方が変わらないでほしい**。
**なぜなら**、慣れた操作が変わると、機能追加が使いにくさとして受け取られるからである。

**受入基準**

- AC-11-1: カテゴリのみを指定して絞り込んだとき、本変更の前と同じ結果が返る。（BE）
- AC-11-2: 期間（`from` / `to`）のみを指定して絞り込んだとき、本変更の前と同じ結果が返る。（BE）
- AC-11-3: `from` と `to` の片方のみを指定したとき、従来どおり `400 Bad Request`（`code: VALIDATION_ERROR`）が返る。（BE）
- AC-11-4: 既存のバックエンドテストとフロントエンドテストが pass する。（BE / FE）

**関連要件**: FR-05、NFR-01
