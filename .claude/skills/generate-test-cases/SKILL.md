# 試験ケース生成（新規作成）

## このスキルの位置づけ

結合テストは、試験観点、試験仕様書、テストコードと実行の3つの段階で進める。このスキルは2つ目の段階を担い、学習者が確定させた試験観点を、実際に操作して確かめられる試験ケースに展開する。出力は人がレビューして確定させる前提の**たたき台**であり、従来のテスト仕様書に当たる。

何を確かめるかは、試験観点の段階で学習者が決め終えている。このスキルが決めるのは、それを**どう確かめるか**（前提、操作、入力する値、確認箇所）だけである。観点を増やしたり減らしたり、期待結果を変えたりしない。展開の途中で、確定した観点では足りない、または誤っていると気づいた場合も、観点を書き換えずに「AI が仮に決めた値」か「試験ケースにできなかった観点」に書いて人に委ねる。

期待結果の出どころは仕様書に限る。これは試験観点の段階と同じ理由による。動いている画面や実装から期待結果を作ると、仕様とずれた実装をそのまま正解として固定してしまう。だからこのスキルも実装コード（`frontend/`、`backend/`）を読まない。要素の指定方法や初期データとの対応づけは、次のテストコードの段階で行う。

## 作らないもの

- Playwright のコード、要素の指定方法（ボタンのロケータなど）
- 実装や初期データに依存する具体値（リソースの名前や ID、絶対日時）
- 観点一覧にない観点、観点と異なる期待結果
- 仕様書や観点一覧の修正

## 手順

### Step 1: 対象画面を決め、入力がそろっているかを確かめる

プロンプトから画面のパスかスラッグを読み取る。スラッグの決め方は `.claude/skills/generate-test-perspectives/SKILL.md` の「出力」の節と同じ（例：`/reservations/new` は `reservations-new`）。決まらなければ `AskUserQuestion` で確認する。

次のコマンドで状態を確かめる。

```bash
node scripts/e2e-workflow/state.mjs show <スラッグ>
```

試験観点の段階が「確定」でなければ、試験ケースは作らずに止め、試験観点の段階を先に確定させるよう伝える。観点が確定していないまま展開すると、後で観点が変わったときにケースとの対応が崩れるためである。

`Docs/test/<スラッグ>/cases.md` が既にあれば、上書きせずに止めて知らせる。

### Step 2: 観点一覧を読む

`Docs/test/<スラッグ>/perspectives.md` を読む。展開するのは **2章「試験観点」のすべての観点**である。

| 章 | 扱い |
|---|---|
| 1章 根拠にした仕様 | 観点の根拠を読むときの手がかりにする |
| 2章 試験観点 | すべて展開する。分類（2.1、2.2 …）もそのまま使う |
| 3章 確認しない観点 | 展開しない。学習者が除外を確定させている |
| 4.1 仕様の矛盾 | 「回答」列を読む。回答に合わせた観点は2章に入っているので、それを展開する |
| 4.2 仕様に書かれていない点 | 展開しない。ただし、展開で値を選ぶときに、その値が仕様に書かれていないことの裏付けとして使う |

観点の「備考」に書かれた前提データや観察する場所は、試験ケースにそのまま引き継ぐ。

### Step 3: 観点の根拠を読み直す

具体的な値（文字数、件数、画面に出る文言、ボタンの名前など）を決めるために、各観点の「仕様根拠」に書かれた節を仕様書（`docs-next/docs/spec/`）で開く。値は仕様書に書かれているものだけを使う。読む文書の範囲は試験観点の段階と同じで、実装コード、図のファイル（`.drawio`、`.svg`）、既存の画面の課題シートは読まない。

### Step 4: テスト環境の前提に合わせる

テストは次の環境で動く。試験ケースはこの前提で書き、1章「テストの前提」にも同じことを書く。

| 前提 | 試験ケースでの書き方 |
|---|---|
| MEMBER、APPROVER、ADMIN の3つのロールごとに、サインイン済みの状態が用意されている | 前提条件に「MEMBER でサインイン済み」のようにロールを書く。サインインの操作は手順に書かない。サインインしていない状態を確かめる観点だけ「サインインしていない」と書く |
| テストごとに、他のテストと重ならない1時間の時間帯が割り当てられる（以下「割り当て枠」） | 日時は割り当て枠からの相対で書く（例：「開始日時＝枠の開始、終了日時＝枠の開始の1時間後」）。絶対日時は書かない。既存の予約が要る場合も、割り当て枠の中に置く（例：「既存予約：枠の開始から1時間、承認済み」） |
| 各テストの前に、結合テスト専用のデータベースが初期データだけの状態に戻る | 前のテストのデータは残っていない前提で書く。後片付けの手順は書かない |
| 画面でそのテストの予約を見分けられるように、利用目的には、テストごとに、印（`[e2e]`）で始まる専用の文字列が用意される（以下「テスト用の利用目的」）。前提として API で作る予約も、この印で始まる | 利用目的には「テスト用の利用目的を入れる」と書き、具体的な文字列（「結合テスト」など）は書かない。文字数を確かめる観点では、「テスト用の利用目的に文字を足して、全体を255文字にした文字列」のように、印を含めた全体の文字数で書く |
| テストを流したあと、テストが実際に使った値（テスト用の利用目的の文字列、選んだリソースの名前、日時）が、確認箇所の画面と並べて表示される | 確認箇所には、画面の中のどの行かを書かなくてよい。学習者は、表示された値で行を探す |

次の2つは、毎回同じ決まりで書く。実行のたびに決め直したり、3章「AI が仮に決めた値」に載せたりしない。

| 決まり | 書き方 |
|---|---|
| 観点がロールを指定していなければ、MEMBER で確かめる | 前提条件に「MEMBER でサインイン済み」と書く。1.1「テスト環境」にもこの決まりを書く |
| 申請などで作った予約があるかどうかは、テスト用の利用目的と割り当て枠で見分ける | 確認箇所は「マイ予約一覧」と書く。ロールごとのサインイン済みの状態は他のテストと共有するので、一覧全体の件数では確かめない。1.1「テスト環境」にもこの決まりを書く |

観点が対象にしない入力項目（観点が「他の項目は正しく入れる」と書いている項目など）の値は、1.3「基本の入力」の表に一度だけ書き、ケースでは「基本の入力のまま」「利用目的だけ空欄にし、ほかは基本の入力」のように書く。基本の入力は、仕様のどの制約にも当たらない値にする。

既存のデータに条件がある場合（承認が必要なリソース、無効なリソースなど）は、1.2「テストデータ」の表に `<略号>-D-01` のような ID で**条件だけ**を書き、試験ケースからはその ID で参照する。リソースの名前や ID のような具体値は書かない。条件を満たすデータを初期データから選ぶか、テストの前に作るかは、テストコードの段階で決める。

### Step 5: 観点を試験ケースに展開する

分類ごとに、観点の順に展開する。

- **1つの観点を1つの試験ケースにする。** 観点は試験観点の段階で、1観点に1つの振る舞いになるよう分けてある。1つのケースで確かめられない場合（複数のロールで同じことを確かめる観点など）だけ複数に分け、前提条件の違い（ロールなど）で分けたことが分かるようにする。分けたケースは「展開元」が同じ観点になる。
- **前提条件**：ロール、テストデータの ID、開く前の画面の状態（どの画面から、どのクエリ付きで開くか）を書く。
- **手順と入力**：操作を番号付きで書く。表のセル内では「1. …<br>2. …」のように `<br>` で区切る。入力する値は具体的に書く（割り当て枠からの相対日時、「256文字の文字列」のような文字数、「0」のような数値）。「不正な値」「適当な値」のような曖昧な語を使わない。画面の部品の名前は、仕様書に書かれた名前を使う。
- **期待結果**：観点の期待結果を、仕様の言葉の範囲で書く。観点にない表示や文言を足さない。仕様書に文言が書かれていれば、原文どおり「」で引用する。仕様が「申請不可」としか書いていなければ、「エラーが表示される」とは書かない。
- **確認箇所**：期待結果が成り立っているかを、どの画面のどの部分を見て判断するかを、画面の名前と部分の名前だけで書く（例：「マイ予約一覧」「予約申請フォームのメッセージ欄」「リソース選択の選択肢」）。場所が2つあれば「、」でつなぐ（例：「予約申請フォームのメッセージ欄、マイ予約一覧」）。観点の「備考」に観察する場所があれば、それを引き継ぐ。次のことは書かない。
  - 何が成り立てばよいか。それは期待結果の列に書いてある。確認箇所で繰り返すと、期待結果と確認箇所のどちらが判断の基準かが分からなくなる
  - 「目的がテスト用の利用目的の予約」「RSV-NEW-D-03」「枠の開始の1時間後」のような、画面には出ない言葉。画面には実際の文字列や名前、日時が出る。どの行を見ればよいかは、実行の段階で表示される「このテストで使った値」で分かる
- **学習者の判断による観点**（仕様根拠が「仕様に記載なし。学習者の判断」の観点）は、観点の期待結果の文をそのまま期待結果にする。言い換えない。
- **境界の観点**は、観点が示す境界の値をちょうど使う（例：「終了日時＝開始日時と同じ」）。「入力できる最小の差」のように、仕様が値を決めていない場合は、次の Step 6 で選んだ値を使う。

### Step 6: AI が仮に決めた値を書き出す

3章「AI が仮に決めた値」に載せるのは、次の2つを**両方とも**満たす値だけである。学習者に判断してもらう価値があるものに絞り、判断の要らないものに埋もれさせないためである。

- 仕様書に値が書かれておらず、AI が選んだ
- 別のもっともらしい値を選ぶと、テストの結果（通るか落ちるか）か、そのテストで見つけられる不具合が変わる

載せるものの例：

- 「入力できる最小の差」を何分にしたか。入力欄の刻みが違えば、そのケースは入力の時点で成り立たない
- 文字数を数える文字に何を使ったか。半角だけを使うと、全角を1文字と数えない誤りは見つからない
- 二重送信を、どのタイミングの2回目の操作で確かめるか

載せないもの：

- Step 4 の決まりで決まること（基本のロール、確認箇所）と、1.3「基本の入力」の値
- 仕様から理屈で一つに決まること（承認待ちの予約は承認が必要なリソースにしか生まれない、など）
- どの値を選んでも結果が変わらないこと（重複予約の時間帯を割り当て枠の中のどこに置くか、別のリソースにどれを使うか、など）。これらはケースの手順と入力に具体的に書いてあり、学習者がケースを1件ずつ観点と突き合わせるときに確かめる

各行には「選んだ理由」と「別の値にするとどうなるか」を1文ずつ書く。「別の値にするとどうなるか」を書けない値は、載せる基準を満たしていないので載せない。

### Step 7: 試験ケースにできなかった観点を書き出す

前提を作れない、観察する場所が画面にないなどの理由で、試験ケースにできない観点があれば、消さずに4章「試験ケースにできなかった観点」に理由とともに書く。外すかどうかを決めるのは学習者である。観点を減らす誤りは、増やす誤りより気づきにくいためである。

### Step 8: ID を付ける

ID の略号は観点一覧と同じものを使う（例：観点一覧が `RSV-NEW` なら `RSV-NEW-TC-001`）。試験ケースは `<略号>-TC-001`、テストデータは `<略号>-D-01` とし、並び順を確定してから欠番なしで通し番号を振る。「展開元」には観点の ID を書く。

### Step 9: 自己点検してから保存する

次をすべて確かめ、満たさない点は直してから保存する。

- 2章のすべての観点 ID が、いずれかの試験ケースの「展開元」か、4章「試験ケースにできなかった観点」のどちらかにある。
- 「展開元」の観点 ID が、すべて観点一覧の2章に実在する。
- 期待結果に、観点と仕様にない表示や文言を足していない。「」で囲んだ文言は仕様書の原文どおりである。
- 絶対日時、リソースの名前や ID、実装のファイル名、HTTP ステータス、テーブル名が入っていない。
- 「不正な値」のような曖昧な入力が残っていない。
- 利用目的に具体的な文字列を書かず、「テスト用の利用目的」と書いている。
- 確認箇所に、画面の名前と部分の名前だけを書いている。期待結果の繰り返し、「テスト用の利用目的」、テストデータの ID、割り当て枠からの相対日時が入っていない。
- 3章には、別の値を選ぶと、テストの結果や、見つけられる不具合が変わるものだけを載せ、各行に「別の値にするとどうなるか」を書いている。基本のロール、確認箇所、基本の入力の値を3章に載せていない。
- 集計の数が表の行数と一致している。

## 出力

保存先は `Docs/test/<スラッグ>/cases.md` とする。この成果物は学習者の作業ブランチにコミットしてよいが、main にはマージしない。ファイルの様式は [`references/output-template.md`](references/output-template.md) に従う。

保存したら、状態ファイルの試験仕様書の段階を「レビュー待ち」にする。状態ファイルは直接編集せず、必ず次のコマンドを使う。

```bash
node scripts/e2e-workflow/state.mjs ai-output <スラッグ> cases "試験ケースを出力"
```

`state.mjs` は、観点一覧の2章の観点のうち、試験ケースの「展開元」にも4章「試験ケースにできなかった観点」にも載っていないものがあると受け付けない。表示された観点 ID を展開し直す（展開できなければ4章に理由付きで書く）か、観点一覧にない ID を直してから、もう一度 `ai-output` を実行する。学習者には渡さない。

保存と状態の更新が済んだら、チャットには次だけを返す（一覧の全文は貼らない）。

- 保存先のパス
- 試験ケースの数、テストデータの数、AI が仮に決めた値の数、試験ケースにできなかった観点の数
- 3章「AI が仮に決めた値」のうち、レビューで最初に見てほしいものを最大3つ
- レビューが済んだら、ワークフローのダッシュボード（`http://localhost:3130/screen/<スラッグ>`）で確定か差し戻しを選ぶこと
