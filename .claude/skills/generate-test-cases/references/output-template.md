# 出力様式

`<...>` を埋めて使う。節の順番と表の列は変えない。列の見出しの文字も変えない（ダッシュボードが見出しの文字で列の役割を見分けるため）。該当する行がない表は、表の代わりに「該当なし」と書く。

````markdown
# <画面名>（`<画面パス>`）試験仕様書

| 項目 | 内容 |
|---|---|
| 対象画面 | <画面名>（`<画面パス>`） |
| 対象工程 | 結合テスト（E2E） |
| ID 略号 | `<略号>` |
| 展開元 | `Docs/test/<スラッグ>/perspectives.md` |
| 作成日 | <YYYY-MM-DD> |

この一覧は試験ケースのたたき台である。人がレビューして確定させたうえで、テストコードへ変換する。

## 1. テストの前提

### 1.1 テスト環境

- MEMBER、APPROVER、ADMIN の3つのロールごとに、サインイン済みの状態が用意されている。サインインの操作は手順に含めない。
- テストごとに、他のテストと重ならない1時間の時間帯が割り当てられる（以下「割り当て枠」）。日時は割り当て枠からの相対で書く。
- 各テストの前に、結合テスト専用のデータベースが初期データだけの状態に戻る。前のテストのデータは残っていない。
- 観点がロールを指定していなければ、MEMBER で確かめる。
- 作った予約があるかどうかは、テスト用の利用目的と割り当て枠で見分ける。一覧全体の件数では確かめない。
- 利用目的には、画面でそのテストの予約を見分けるために、テストごとに、印（`[e2e]`）で始まる専用の文字列が用意される（以下「テスト用の利用目的」）。文字数は印を含めた全体で数える。
- テストを流したあと、テストが実際に使った値（テスト用の利用目的の文字列、選んだリソースの名前、日時）が、確認箇所の画面と並べて表示される。確認箇所の画面のどの行を見ればよいかは、その値で分かる。
````

## 書き方の例

良い例：

| 前提条件 | 手順と入力 | 期待結果 | 確認箇所 |
|---|---|---|---|
| MEMBER でサインイン済み。予約申請画面を開いている | 1. リソース選択で RSV-NEW-D-01 を選ぶ<br>2. 開始日時に枠の開始、終了日時に枠の開始と同じ日時を入れる<br>3. 利用目的にテスト用の利用目的を入れて「申請する」を押す | 申請できないこと | マイ予約一覧 |
| MEMBER でサインイン済み。既存予約：枠の開始から1時間、承認済み | 1. 既存予約と同じリソースを選ぶ<br>2. 開始日時に枠の開始、終了日時に枠の開始の1時間後を入れる<br>3. 「申請する」を押す | 「指定した時間帯は既に予約が入っています」と表示され、申請できないこと | 予約申請フォームのメッセージ欄、マイ予約一覧 |

悪い例と、その理由：

| 悪い例 | 理由 |
|---|---|
| 開始日時に 2027-01-01 10:00 を入れる | 絶対日時。割り当て枠からの相対で書く |
| リソース選択で「会議室A」を選ぶ | 初期データの名前。条件を 1.2 に書き、ID で参照する |
| 利用目的に「結合テスト」を入れる | 画面でこのテストの予約を見分けられない。「テスト用の利用目的」と書く |
| 不正な値を入れて申請する | 何を入れるかが決まらない |
| 3章に「ロールの指定がない観点は MEMBER で確かめる」と書く | 毎回同じ決まりで、判断が要らない。1.1 に書く |
| 確認箇所に「マイ予約一覧に、目的がテスト用の利用目的の予約がないこと」と書く | 期待結果の繰り返しで、しかも「テスト用の利用目的」は画面に出ない言葉。「マイ予約一覧」とだけ書く |
| 確認箇所に「リソース選択の選択肢に RSV-NEW-D-03 がないこと」と書く | テストデータの ID は画面に出ない。「リソース選択の選択肢」とだけ書く。どのリソースを探せばよいかは、実行の段階で使った値として表示される |
| 「利用目的は必須です」と表示されること | 仕様にない文言。仕様が「申請不可」としか書いていなければ「申請できないこと」と書く |
