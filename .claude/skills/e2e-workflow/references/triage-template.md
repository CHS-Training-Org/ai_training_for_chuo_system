# フェイルの見立ての様式

`Docs/test/<スラッグ>/triage.md` に書く。`<...>` を埋めて使う。表の列の見出しの文字は変えない（`scripts/e2e-workflow/state.mjs` とダッシュボードが、見出しの文字で列を見分けるため）。

````markdown
# <画面名>（`<画面パス>`）フェイルの見立て

| 項目 | 内容 |
|---|---|
| 実行の ID | `<run.json の runId>` |

この見立ては AI の推測である。実装の不具合か、テストの誤りかを判断するのは学習者である。

| ケース ID | 見立て | 根拠 |
|---|---|---|
| <略号>-TC-0nn | <下の4つのどれか> | <何を見てそう考えたかを1〜2文で> |
````

「見立て」の列は、次の4つのどれかで始める。

| 見立て | 使うとき |
|---|---|
| 実装の不具合の候補 | 証拠の画面や応答が、仕様（試験ケースの期待結果）と違う振る舞いを示している |
| テストの誤りの候補 | テストの操作や確かめ方が、試験ケースの手順や見る場所と合っていない（要素の名前の取り違え、待ち方の不足など） |
| 環境の問題 | バックエンドやデータベースの状態が原因と考えられる（流し直しても直らなかったもの） |
| 判断できない | 証拠から、どちらとも言えない |

「根拠」には、画面に何が写っていたか、エラーの内容、使った値など、学習者が証拠で確かめられることを書く。「〜と思われる」で終わらせず、どの証拠を見ればよいかを書く。

例：

| ケース ID | 見立て | 根拠 |
|---|---|---|
| RSV-NEW-TC-021 | 実装の不具合の候補 | フェイルした時点の画面が、409（予約の重複）の応答で落ちたサーバーのエラー画面になっている。期待結果のメッセージは出ていない |
| RSV-NEW-TC-008 | 実装の不具合の候補 | ADMIN のリソース選択の選択肢に「[e2e] 無効なリソース」が写っている。仕様の食い違いへの回答（A：含めない）と違う |
