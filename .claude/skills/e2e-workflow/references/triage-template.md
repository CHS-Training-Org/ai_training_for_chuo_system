# フェイルの見立ての様式

`Docs/test/<スラッグ>/triage.md` に書く。`<...>` を埋めて使う。表の列の見出しの文字は変えない（`scripts/e2e-workflow/state.mjs` とダッシュボードが、見出しの文字で列を見分けるため）。

````markdown
# <画面名>（`<画面パス>`）フェイルの見立て

| 項目 | 内容 |
|---|---|
| 実行の ID | `<run.json の runId>` |

この見立ては AI の推測である。実装の不具合か、テストの誤りかを判断するのは学習者である。

| ケース ID | 見立て | 根拠 |
|---|---|---|
| <略号>-TC-0nn | <下の5つのどれか> | <何を見てそう考えたかを1〜2文で> |
````

「見立て」の列は、次の5つのどれかで始める。

| 見立て | 使うとき |
|---|---|
| 実装の不具合の候補 | エビデンスの画面や応答が、仕様（試験ケースの期待結果）と違う振る舞いを示している |
| 仕様の仮回答による候補 | 展開元の観点が、仕様の矛盾への回答（観点一覧の 4.1 で学習者が選んだもの）に基づいていて、その回答と実装の振る舞いが違う |
| テストの誤りの候補 | テストの操作や確かめ方が、試験ケースの手順や確認箇所と合っていない（要素の名前の取り違え、待ち方の不足など） |
| 環境の問題 | 機械的な区分は「環境が整っていない」ではないが、流し直しても同じ止まり方をし、バックエンドやデータベースの状態が原因と考えられる |
| 判断できない | エビデンスから、どれとも言えない |

機械的な区分が「環境が整っていない」のケースは、見立てを書く前に環境を直して流し直す（残っている間は、学習者に渡せない）。

学習者は、関門3でケースごとに原因（実装の不具合、仕様の仮回答による、テストの誤り、前の段階の誤り）を選び、根拠を書く。見立ては、その手がかりである。

「根拠」には、画面に何が写っていたか、エラーの内容、使った値など、学習者がエビデンスで確かめられることを書く。「〜と思われる」で終わらせず、どのエビデンスを見ればよいかを書く。

例：

| ケース ID | 見立て | 根拠 |
|---|---|---|
| RSV-NEW-TC-021 | 実装の不具合の候補 | フェイルした時点の画面が、409（予約の重複）の応答で落ちたサーバーのエラー画面になっている。期待結果のメッセージは出ていない |
| RSV-NEW-TC-008 | 仕様の仮回答による候補 | ADMIN のリソース選択の選択肢に「[e2e] 無効なリソース」が写っている。展開元の観点は、仕様の矛盾への回答（RSV-NEW-Q-001 の A：含めない）に基づく。要件定義書と API 仕様書は、ADMIN には無効なリソースも返すと書いている |
