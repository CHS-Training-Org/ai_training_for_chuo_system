# 結合テストのワークフローの案内

## このスキルの位置づけ

結合テストは、3つの段階を順に進める。各段階で AI が成果物を出力し、学習者が関門でレビューして「確定」か「差し戻し」を選ぶ。流れの全体は `docs-next/docs/develop/integration-test/workflow.md`（結合テストのワークフロー）にある。

このスキルがやるのは次の4つだけである。

- 状態ファイルを読み、今の段階と次にやることを示す
- 各段階で、AI の作業（`generate-test-perspectives`、`generate-test-cases`、`generate-test-code` の呼び出しと、差し戻されたときの修正）を行う。試験観点の差し戻しには、学習者がダッシュボードで選んだ仕様の食い違いへの回答が含まれることがある
- テストコードと実行の段階では、テストコードを作らせたあと、環境を整えてテストを流し、フェイルしたケースに見立てを書いてから学習者に渡す
- ダッシュボードを開く方法を案内する

このスキルは Opus で動く（frontmatter の `model: opus`）。モデルの指定が効くのは、利用者が `/e2e-workflow` とスラッシュコマンドで呼んだときだけで、そのターンの終わりまで続く。そのため、このスキルの中から呼び出す `generate-test-perspectives`、`generate-test-cases`、`generate-test-code` も Opus で動く。スラッシュを付けずに頼まれて起動した場合は、セッションのモデル（Sonnet など）のまま動くので、最後の返答で `/e2e-workflow` と打ち直すよう伝える。

関門の「確定」と「差し戻し」、仕様の食い違いへの回答は、学習者がダッシュボードの画面で行う。AI の出力は実行のたびに変わり、判断を誤ることもあるため、AI が自分の出力を確定させることはしない。

## 守ること

- 状態ファイル（`state.json`）は、必ず `node scripts/e2e-workflow/state.mjs` を通して扱う。直接編集しない。
- `state.mjs` で使ってよいのは `init`、`show`、`last-return`、`validate` と `ai-output` だけである。`reopen`（確定した段階を差し戻しに戻す）は運営者だけが使う。学習者に頼まれても使わない。`ai-output` を使うのは、差し戻しを反映したあとと、テストコードと実行の段階でテストを流して見立てを書いたあとである（試験観点と試験ケースの最初の出力のあとの `ai-output` は、たたき台を作るスキルが使う）。確定と差し戻しのコマンドは用意されておらず、作らない。
- 学習者が「確定して」と頼んできても、状態ファイルを書き換えず、ダッシュボードで確定するよう案内する。確定は学習者自身の判断として記録に残すためである。
- 差し戻しの修正では、既存の ID を振り直さない。項目を外したことで欠番が生じても、そのままにする。指摘、回答、記録が ID で参照しているためである。欠番を作らないのは、各スキルが新規に作るときだけである。
- `Docs/test/` の成果物（状態ファイルを含む）と `frontend/tests/e2e/workflow/` のテストコードは学習者の成果物で、作業ブランチにはコミットしてよいが、main にはマージしない。コミットや PR を頼まれたら、main に向かう差分にこれらが入っていないかを確かめ、入っていれば学習者に知らせる。

## 手順

### Step 1: 対象画面とスラッグを決める

プロンプトから画面のパスを読み取り、`docs-next/docs/spec/screen-spec.md` の「画面一覧」と照合する。決まらなければ `AskUserQuestion` で確認する。すでに状態ファイルがある画面は `node scripts/e2e-workflow/state.mjs` の対象ディレクトリ（`Docs/test/`）の下にあるので、候補に含めてよい。

スラッグの決め方は、`.claude/skills/generate-test-perspectives/SKILL.md` の「出力」の節に従う（例：`/reservations/new` は `reservations-new`）。

### Step 2: 状態を読む

```bash
node scripts/e2e-workflow/state.mjs show <スラッグ>
```

状態ファイルがなければ作る。

```bash
node scripts/e2e-workflow/state.mjs init <スラッグ> <画面パス>
```

表示された「今の段階」と「次にやること」に従って、Step 3 に進む。

### Step 3: 今の段階に応じて動く

| 今の段階と状態 | このスキルがやること |
|---|---|
| 1 試験観点、未着手 | `generate-test-perspectives` スキルを呼び出して観点一覧（`Docs/test/<スラッグ>/perspectives.md`）を出力させる。状態を「レビュー待ち」にする更新は `generate-test-perspectives` が行うので、このスキルでは行わない。終わったら `show` で状態を確かめる |
| 1 試験観点、レビュー待ち | AI の作業はない。学習者に、`docs-next/docs/develop/integration-test/viewpoints.md` の手順3と手順4でレビューし、ダッシュボードで仕様の食い違いに回答して、確定か差し戻しを選ぶよう案内する |
| 1 試験観点、差し戻し | 下の「差し戻しを反映する」の手順で観点一覧を直し、状態を「レビュー待ち」に戻す |
| 2 試験ケース、未着手 | `generate-test-cases` スキルを呼び出して試験ケース一覧（`Docs/test/<スラッグ>/cases.md`）を出力させる。状態を「レビュー待ち」にする更新は `generate-test-cases` が行う。終わったら `show` で状態を確かめる |
| 2 試験ケース、レビュー待ち | AI の作業はない。学習者に、`docs-next/docs/develop/integration-test/cases.md` の手順でレビューし、ダッシュボードで確定か差し戻しを選ぶよう案内する |
| 2 試験ケース、差し戻し | 下の「差し戻しを反映する（試験ケースの段階）」の手順で試験ケース一覧を直し、状態を「レビュー待ち」に戻す |
| 3 テストコードと実行、未着手（テストコードと説明がすでにある） | 前回、テストを流したところで止まった状態である（環境の失敗など）。`generate-test-code` は呼ばず、下の「テストを流して見立てを書く」の1から行う |
| 3 テストコードと実行、未着手 | `generate-test-code` スキルを呼び出して、テストコード（`frontend/tests/e2e/workflow/<スラッグ>.spec.ts`）とレビュー用の説明（`Docs/test/<スラッグ>/code.md`）を出力させる。そのあと、下の「テストを流して見立てを書く」を行い、状態を「レビュー待ち」にする |
| 3 テストコードと実行、レビュー待ち | AI の作業はない。学習者に、テストコードは読まずに、説明の2〜4章を `docs-next/docs/develop/integration-test/code-generation.md` の手順で判断し、ケースごとの実行の証拠を `docs-next/docs/develop/integration-test/execution.md` の手順で見て、確定か差し戻しを選ぶよう案内する |
| 3 テストコードと実行、差し戻し | 下の「差し戻しを反映する（テストコードと実行の段階）」の手順でテストコードを直し、流し直して見立てを書き、状態を「レビュー待ち」に戻す |
| すべて確定 | 完了した旨を伝える |

成果物のファイル（観点一覧や試験ケース一覧）がすでにあるのに、その段階が「未着手」の場合は、上書きしない。たたき台を作るスキルも、既存のファイルがあれば止まる。学習者に、既存のファイルを使うかどうかを確認する。テストコードと実行の段階で、テストコードと説明がすでにある場合だけは、上の表のとおり流すところから再開する。

`last-return` が「運営者が確定から差し戻し」と表示した段階は、運営者が `reopen` で確定から戻した段階である。学習者が後の関門で前の段階の誤りを見つけ、運営者が認めたときに起きる。その段階の「差し戻し」と同じ手順で直す。後の段階は「未着手」に戻り、成果物は運営者の操作で別の場所へ移されているので、直して学習者が確定したあと、後の段階を一から作り直す。

### 前の段階の誤りの指摘を受けたとき

学習者が、確定した前の段階の誤り（試験ケースや観点の期待結果、入力値の誤りなど）を指摘して差し戻すことがある。差し戻しの理由に「前の段階の誤り」と書かれている、またはフェイルしたケースの判断に「前の段階の誤り」がある場合である。このときは次のようにする。

- 確定した段階の成果物は書き換えない。今の段階の成果物も直さず、状態も変えずに止める（`ai-output` を使わない）。
- 最後の返答で、運営者に相談するよう学習者に伝える。運営者が誤りを認めると、`state.mjs reopen` でその段階を差し戻しに戻し、そこから直して進め直すことになる。
- 運営者がその指摘を取り下げた（前の段階の誤りではないと判断した）と学習者か運営者が伝えてきた場合は、残りの指摘だけを反映して、いつもの差し戻しの手順で進める。

### 差し戻しを反映する（試験観点の段階）

学習者が差し戻した観点一覧を、指摘と仕様の食い違いへの回答に沿って直す。`generate-test-perspectives` は呼ばない。既存のファイルがあると止まるうえ、一から作り直すと出力が実行のたびに変わるため、学習者がレビューした一覧とは別物になり、指摘で参照していた ID も変わってしまうためである。

1. 差し戻しの理由と、仕様の食い違いへの回答を読む。

   ```bash
   node scripts/e2e-workflow/state.mjs last-return <スラッグ> perspectives
   node scripts/e2e-workflow/state.mjs show <スラッグ>
   ```

   差し戻しの理由には、学習者の指摘と、そのとき選んだ回答（「仕様の食い違いへの回答：…」の行）が入っている。`show` は、これまでに保存された回答をすべて表示する。

2. 観点一覧（`Docs/test/<スラッグ>/perspectives.md`）を読む。
3. 仕様の食い違いへの回答を反映する。回答があった 4.1 の行ごとに、次のようにする。
   - 「影響する観点」に回答ごとの観点案があれば、選ばれた案を2章の該当する分類へ観点として入れる。仕様根拠には、食い違う両側の記載元と、どちらに合わせたかを書く。
   - 「影響する観点」が既存の観点 ID なら、その観点を回答に合わせて直す。
   - 4.1 の「回答」列に、選ばれた選択肢の記号と案を書く（例：「A. 含めない」）。回答が選び直された場合は書き換える。ダッシュボードは、この列の先頭の記号が保存された回答と一致することで反映済みと判断する。
4. 指摘に沿って、1章から5章を直す。観点の書き方と根拠の規則は `generate-test-perspectives` の SKILL.md と出力様式に従う。次の点を守る。
   - 既存の ID は振り直さない。指摘や記録から ID で参照されているため。観点を足すときは、同じ種類の ID の最大値の続きを使う。
   - 観点を外すときは消さずに3章「確認しない観点」へ移し、理由を書く。
   - 4.1 の項目が食い違いではないと指摘されたら、両側の記載元を読み直す。一方が詳細を省いているだけなら、その行を 4.1 から外し（Q の ID は欠番のままにする）、1章の該当する行を「確定」に直し、詳しく書いている側に合わせた観点を2章に入れる。読み直しても食い違いに見える場合は 4.1 に残し、その理由を最後の返答で伝える。
   - 4.2「仕様に書かれていない点」の項目を観点にするよう指摘されたら、学習者が期待結果を書いている場合に限り、観点として足して 4.2 から外す。仕様根拠には「仕様に記載なし。学習者の判断（差し戻しの理由）」と書く。期待結果が書かれていなければ推測で補わず、最後の返答で学習者に期待結果を尋ねる。
   - 5章の集計を、直したあとの行数に合わせる。
5. 直したら、何を直したかを1〜2文にまとめて状態を「レビュー待ち」に戻す。

   ```bash
   node scripts/e2e-workflow/state.mjs ai-output <スラッグ> perspectives "差し戻しを反映：<直したことの要約>"
   ```

6. 学習者に、直した点を伝え、もう一度レビューしてダッシュボードで確定か差し戻しを選ぶよう案内する。

### 差し戻しを反映する（試験ケースの段階）

学習者が差し戻した試験ケース一覧を、指摘に沿って直す。`generate-test-cases` は呼ばない。理由は試験観点の段階と同じで、作り直すと学習者がレビューした一覧とは別物になり、指摘で参照していた ID も変わるためである。

1. 差し戻しの理由を読む。

   ```bash
   node scripts/e2e-workflow/state.mjs last-return <スラッグ> cases
   ```

2. 試験ケース一覧（`Docs/test/<スラッグ>/cases.md`）と、確定した観点一覧（`Docs/test/<スラッグ>/perspectives.md`）を読む。
3. 指摘に沿って試験ケース一覧を直す。書き方の規則は `generate-test-cases` の SKILL.md と出力様式に従い、期待結果の根拠は観点一覧と仕様書だけとする。次の点を守る。
   - 観点一覧は書き換えない。確定した観点を変える必要がある指摘（観点の誤り、観点の追加）は、上の「前の段階の誤りの指摘を受けたとき」に従う。
   - 既存の ID は振り直さない。ケースを足すときは、同じ種類の ID の最大値の続きを使う。
   - ケースを消さない。展開をやめる観点は、4章「試験ケースにできなかった観点」に理由とともに移す。
   - 3章「AI が仮に決めた値」か 1.3「基本の入力」の値を変えるよう指摘されたら、その値と、その値を使うすべてのケースを直す。
   - 5章の集計を、直したあとの行数に合わせる。
4. 直したら、何を直したかを1〜2文にまとめて状態を「レビュー待ち」に戻す。

   ```bash
   node scripts/e2e-workflow/state.mjs ai-output <スラッグ> cases "差し戻しを反映：<直したことの要約>"
   ```

5. 学習者に、直した点を伝え、もう一度レビューしてダッシュボードで確定か差し戻しを選ぶよう案内する。

### テストを流して見立てを書く（テストコードと実行の段階）

テストコードができたら（差し戻しで直したあとも）、次の順に進める。学習者が判断するのは、流した結果と証拠である。テストコードを書いただけでは学習者に渡さない。

1. 環境を整える。結合テスト専用のデータベース（`bookflow_e2e`）を用意し、バックエンドをそこにつないで起動する。

   ```bash
   node scripts/e2e-workflow/env.mjs up
   ```

   バックエンドの起動を待つので、数分かかることがある。これもバックグラウンドにせず、終わるまで待つ。

   開発用のバックエンドが動いていると、終了コード 2 で止まる。このときは `AskUserQuestion` で、開発用のバックエンドを止めて、結合テスト用に起動し直してよいかを学習者に確かめる。了承されたら `--replace` を付けて実行し直す。了承されなければ、流さずに止め、その旨を最後の返答で伝える。

2. テストを流す。数分かかる。バックグラウンドにせず、終わるまで待つ（Bash のタイムアウトは 600000 ミリ秒にする）。待たずに返答を終えると、結果も見立てもないまま止まる。

   ```bash
   node scripts/e2e-workflow/run.mjs <スラッグ>
   ```

   - 流す前に止まった場合（データベースやバックエンドのエラー）は、表示に従って環境を直し、流し直す。テストコードは変えない。
   - 結果に「環境が整っていない」か「実行されていない」のケースがあれば、環境を直して流し直す。これらのケースが残っている間は、`state.mjs` が「レビュー待ち」への更新を受け付けず、学習者も確定できない。2回流し直しても直らなければ、状態を変えずに止め、何が起きているかを最後の返答で学習者に伝える。もう一度呼ばれたときは、Step 3 の表のとおり流すところから再開する。
   - それ以外のフェイルは、ここでは直さない。テストの誤りに見えても、テストコードを書き換えて流し直さない。直すかどうかは、証拠を見た学習者が決める。

3. フェイルしたケースの見立てを書く。`Docs/test/<スラッグ>/run.json` で、フェイルしたケースと、そのエラー、証拠の画面のファイル名、使った値を確かめる。証拠の画面とフェイルした時点の画面（`frontend/playwright/evidence/<スラッグ>/` の PNG）を読み、試験ケース一覧の期待結果と見比べる。テストコードと実装は、原因を考えるために読んでよい。そのうえで、`references/triage-template.md` の様式で `Docs/test/<スラッグ>/triage.md` を書く。
   - 実行の ID は、`run.json` の `runId` をそのまま写す。
   - フェイルしたケースすべてに1行ずつ書く。パスしたケースは書かない。
   - 見立ては候補である。「実装の不具合」と言い切らない。
   - フェイルしたケースの展開元の観点が、仕様の食い違いへの回答（観点一覧の 4.1 で学習者が選んだもの）に基づいていて、フェイルがその回答と実装の違いから来ているなら、「仕様の仮回答による候補」とする。実装の不具合とは区別する。仕様書の別の箇所は実装と同じ振る舞いを書いていることがあるためである。
   - 「環境の問題」は、機械的な区分が「環境が整っていない」ではないのに、流し直しても同じ止まり方をし、環境が原因と考えられるものに使う。「環境が整っていない」のケースは、見立てを書く前に環境を直して流し直す。
4. 状態を「レビュー待ち」にする。`state.mjs` は、流した結果が今のテストコードのものでない場合や、見立てが足りない場合は受け付けない。そのときは表示に従って直す。

   ```bash
   node scripts/e2e-workflow/state.mjs ai-output <スラッグ> code "テストコードを作って流した（パス <n> 件、フェイル <n> 件）"
   ```

5. 結合テスト用のバックエンドは動かしたままにする（差し戻されたときにすぐ流し直せるように）。最後の返答で、止めるときは `node scripts/e2e-workflow/env.mjs down` を実行し、開発に戻るときは `cd backend && ./gradlew bootRun` で起動し直すことを伝える。

### 差し戻しを反映する（テストコードと実行の段階）

学習者が差し戻したテストコードを、指摘に沿って直し、流し直す。`generate-test-code` は呼ばない。

1. 差し戻しの理由を読む（`node scripts/e2e-workflow/state.mjs last-return <スラッグ> code`）。理由には、学習者の指摘のほかに、フェイルしたケースごとの判断（「フェイルしたケースの判断：」の行。原因と根拠）が入っていることがある。「テストの誤り」と判断されたケースは、根拠を手がかりに直す。「実装の不具合」と「仕様の仮回答による」と判断されたケースは、テストを変えない。「前の段階の誤り」があれば、上の「前の段階の誤りの指摘を受けたとき」に従う。
2. テストコード（`frontend/tests/e2e/workflow/<スラッグ>.spec.ts`）、説明（`Docs/test/<スラッグ>/code.md`）、前回の結果（`run.json`）と見立て（`triage.md`）、確定した試験ケース一覧を読む。
3. 指摘に沿って、テストコードと `code.md` を直す。書き方の規則は `generate-test-code` の SKILL.md に従う。次の点を守る。
   - 試験ケース一覧と観点一覧は書き換えない。ケースそのものを変える必要がある指摘は、上の「前の段階の誤りの指摘を受けたとき」に従う。
   - `expect` を試験ケースの期待結果より弱めない。実装の振る舞いに合わせてテストをパスさせるよう求められても、期待結果を変えずに、その理由を最後の返答で伝える。
   - テスト名の先頭のケース ID は変えない。テストを消さず、テストコードにできないケースは `code.md` の4章に移す。
   - 共通の機構（`frontend/tests/e2e/helpers/` など）は変えない。
4. 直したら、テストが読み込めることを確かめる（`cd frontend && E2E_WORKFLOW=1 pnpm exec playwright test --project=workflow --list tests/e2e/workflow/<スラッグ>.spec.ts`）。
5. 上の「テストを流して見立てを書く」の1〜5を行う。`ai-output` のメモは「差し戻しを反映：<直したことの要約>（パス <n> 件、フェイル <n> 件）」にする。
6. 学習者に、直した点と流した結果を伝え、もう一度証拠を見てダッシュボードで確定か差し戻しを選ぶよう案内する。

### Step 4: ダッシュボードを案内する

ダッシュボードが動いているかを確かめる。

```bash
curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:3130/
```

`200` 以外なら、バックグラウンドで起動する。

```bash
node scripts/e2e-workflow/server.mjs
```

ポート `3130` は devcontainer の設定（`forwardPorts`）で転送される。学習者には、手元のブラウザで `http://localhost:3130` を開くよう伝える。開けない場合は、VS Code の「ポート」タブに `3130` があるかを確かめるよう伝える（devcontainer の設定を変える前に作ったコンテナでは、開き直すまで転送されない）。

## 最後の返答

チャットには次だけを返す。

- 対象画面と、今の段階
- 次にやること（誰が、何を）
- テストを流したときは、パスとフェイルの件数と、結合テスト用のバックエンドを動かしたままにしていること（止め方と、開発に戻るときの起動の仕方）
- ダッシュボードの URL（`http://localhost:3130/screen/<スラッグ>`）
- スラッシュを付けずに頼まれて起動した場合は、次からは `/e2e-workflow` と打つと Opus で動くこと
