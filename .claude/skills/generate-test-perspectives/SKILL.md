# 試験観点生成（全画面共通・新規作成）

## このスキルの位置づけ

E2E テストを AI と協働して作るとき、人が責任を持って決めるのは「何を確かめるか」である。このスキルが出すのは、その判断の**たたき台**であり、人がレビューして確定させる前提で書く。後工程（試験ケース、Playwright コード、実行）はこの観点一覧を入力にする。

期待結果の出どころは**仕様書に限る**。動いている画面や実装コードから期待結果を作ると、仕様とずれた実装をそのまま正解として固定してしまう。また新しい画面では、実装より先に仕様がある（Spec-first）。だからこのスキルは実装コード（`frontend/`、`backend/`）を読まない。

## 作らないもの

- 試験ケース（具体的な入力値、操作手順、期待する文言の全文）
- Playwright コード、API テストコード
- 実装や仕様書の修正
- 仕様書に書かれていない振る舞いを、一般論で補った観点

## 手順

### Step 1: 対象画面を特定する

プロンプトから画面のパス（例：`/resources`）か画面名を読み取り、`docs-next/docs/spec/screen-spec.md` の「画面一覧」と照合する。

- 一意に決まれば、そのまま進む。
- 決まらない（画面の指定がない、複数に当てはまる、画面一覧にない）場合は `AskUserQuestion` で確認する。候補は画面一覧から関係しそうなものを最大4つに絞る。画面一覧にない新しい画面は、エンハンス要件シート（`docs-next/docs/spec/enhancements/`）に定義があるかを確認し、あればそれを根拠にする。
- 1回の実行で扱う画面は1つにする。複数を頼まれたら、1画面ずつ順に作る。

### Step 2: 仕様を集める

根拠に使う文書と、そこから拾うものは次のとおり。画面のパス、画面名、その画面が呼ぶ API のパスで検索して、関係する節を漏れなく集める。

| 文書 | 拾うもの |
|---|---|
| `screen-spec.md` の対象画面の節 | UI 要素、バリデーション、操作後のフロー、表示の条件 |
| `screen-spec.md` の画面遷移図・他画面の節 | 対象画面へ入る導線（クエリパラメータ付きの遷移など）と、出ていく先 |
| 各文書の Markdown 本文に文字で書かれた図の注記（シーケンス図の下の注記など） | 注記に書かれた条件（例示の検索条件など）が本文の条件と一致しているか |
| `screen-spec.md` のアクセス制御の記述 | 未認証時・権限不足時の扱い |
| `requirements.md` | ロール・権限定義、画面アクセス権限、該当ユースケースの要件 ID、業務ルール、非機能要件 |
| `api-spec.md` | 画面が呼ぶ API のパラメータの制約、エラー時の扱い（画面にどう現れるかの手がかり） |
| `er-diagram.md` | 型や長さなどのデータ上の制約（画面のバリデーションと同じとは限らない。記載元を明示して使う） |
| `enhancements/` の該当シート | 対象画面が画面仕様書の画面一覧にない新しい画面の場合だけ開く。画面一覧にある既存の画面では開かない（課題シートの「背景」は現在の実装の説明で、仕様ではないため）。テストを追加する課題シート（「既存機能の E2E テスト追加」など）は、どの場合も根拠にしない |

図のファイル（`.drawio`、`.svg`）は開かない。図の中の矢印やラベルは本文の要約で、解析に時間がかかるわりに、本文にない条件はほとんど書かれていないためである。

共通レイアウト（ヘッダー、サイドナビ）と未認証時のリダイレクトは全画面で共有される。対象画面に固有の記述がない限り、観点にはせず「確認しない観点」に理由「共通の観点で担保」として1行だけ残す。「固有の記述」とは、対象画面の画面仕様書の節に、共通と異なる振る舞いが書かれていることを指す（例：その画面だけ別の画面へリダイレクトする）。

### Step 3: 根拠にする仕様を整理する

観点を書く前に、拾った仕様を1つずつ次のどれかに振り分ける。「確定」と「矛盾」は成果物の「根拠にした仕様」節に出す。レビューする人が、観点より先にここで誤りに気づけるようにするためである（AI が架空のルールを持ち込むのは、たいていこの段階）。「記載なし」は根拠ではないので、この節には出さず仕様確認事項の「仕様に書かれていない点」にだけ書く（同じことを2か所に書くと、一覧が長くなって読みにくい）。

| 区分 | 扱い |
|---|---|
| 確定 | 複数の文書で一致している、または1つの文書に明記されている。記載元を併記して観点に使う |
| 矛盾 | 文書どうしで食い違っている。どちらが正しいか判断せず「仕様確認事項」の「仕様の食い違い」に回す |
| 記載なし | 試験に必要そうだが、どの文書にも書かれていない。観点にはせず、「仕様確認事項」の「仕様に書かれていない点」に回す |

矛盾が見つかりやすいのは、画面の節が書く表示・入力の条件に対して、要件や API の側にだけロールによる例外や追加の条件が書かれている所である。同じデータを別の画面でも使う場合は、その画面の節の書き方とも突き合わせる。図の注記が本文の条件（ロールの例外など）を落としている場合も、例示にすぎないと自分で判断せず「矛盾」として挙げ、どちらを正とするかは人に委ねる。画面の節だけを読んで確定扱いにしない。

### Step 4: 観点を書く

分類は次の順に並べる。対象画面に当てはまる分類だけを使い、入力項目・フィルタ・業務ルールは仕様に出てくる単位で分類を立てる（例：「開始日時」「カテゴリフィルター」「重複予約」）。

1. 画面アクセス・認可
2. 初期表示（遷移元から引き継ぐ初期値を含む）
3. 入力項目・操作部品ごと（仕様の UI 要素の順）
4. 項目間の相関
5. 操作（申請、検索、絞り込み、ページ送り など）
6. 業務ルールごと
7. 操作後の結果と画面遷移
8. エラー表示
9. ロールによる違い

書き方の規則（読み手は、実装を知らない学習者やレビュー担当者である）：

- **利用者に見える言葉で書く。** HTTP ステータス、エラーコード、テーブル名・カラム名、内部の列挙値を観点の文に入れない。画面に表示される語（例：ステータスバッジの表示）はそのまま使ってよい。
- **何をしたら、どうなれば正しいかを言い切る。** 「必須チェック」のような体言止めにせず、「リソースを選ばずに申請すると、申請できないこと」のように、条件と見える結果を書く。
- **期待結果は仕様の言葉の範囲で書く。** 仕様が「申請不可」としか書いていなければ、「エラーが表示される」「メッセージが出る」のような表示を足さない。表示の有無や文言が試験に要るなら、仕様確認事項に書く。
- **1 観点に 1 つの振る舞い。** 期待結果が2つあれば分ける。
- **画面から観察できる形にする。** 内部の状態（DB の行ができる等）は、それが画面のどこに現れるかで書く（例：「承認が必要なリソースで申請すると、マイ予約一覧で承認待ちと表示されること」）。画面に現れない場合は、観点に残したうえで、何を見れば確かめられるかを備考に書く。
- **存在確認だけの観点を並べない。** 各入力欄が表示されることを1欄ずつ観点にしない。他の観点を実行すれば必ず触れるからである。初期表示は「何が、どの状態で表示されるか」を少数の観点にまとめる。
- **境界は両側と一致点を分ける。** 仕様が数値・日時・範囲の条件を式や不等号で示している場合、境界の内側・一致点・外側をそれぞれ別の観点にする。時間帯の重なりのような2区間の関係は、「完全に前／端が接する／一部重なる／内包する／内包される／完全に後」を区別する。接するだけの場合を重なりとみなすかは、仕様の不等号で決める。
- **画面アクセス権限は、ロールごとに1件ずつ観点にする。** 仕様の権限表で許可されているロールは「開ける」、拒否されているロールは「開けない」の観点を、ロールごとに書く。全ロールが許可されていても、除外に回さない（認可を破ると影響が大きく、後からロールを増減したときに確かめる手がかりになるため）。
- **それ以外のロールの違いは、仕様に違いが書かれている所だけ観点にする。**

**仕様の食い違いの回答に期待結果が左右される観点は、観点一覧に入れず保留する。** 回答によって期待結果が逆になる観点を確定のように書くと、レビューする人が回答前の案を正しい観点と読み違えるためである。保留した観点は、Step 6 で仕様の食い違いの「影響する観点」列に、回答ごとの観点案として完全な文で書く（例：「A なら『ADMIN で開くと、リソース選択の選択肢に無効なリソースが含まれないこと』／B なら『ADMIN で開くと、リソース選択の選択肢に無効なリソースも含まれること』」）。学習者がダッシュボードで回答を選ぶと、ワークフローの案内スキル（`e2e-workflow`）が選ばれた案を観点一覧へ移す。

**仕様に書かれていない振る舞いは、観点にしない。** 期待結果を仕様から決められないためである。Step 6 で「仕様に書かれていない点」に並べるだけにする。

### Step 5: 確認しない観点を併記する

仕様上は確認できるが、この画面の結合テストでは意図して外すものは、消さずに理由付きで一覧の後に書く。レビューする人が「漏れたのか、意図して外したのか」を区別できるようにするためである。理由は次の5つから1つを選び、**表記を変えずにそのまま書く**（語を縮めたり言い換えたりすると、理由ごとに数えたり絞り込んだりできなくなる）。なぜその理由になるかは補足の列に書く。

| 理由（この表記で書く） | 使う場面 |
|---|---|
| 取るに足らない | 他の観点を実行すれば必ず確かめられる、または外しても利用者への影響がない |
| 上流のテストで担保済み | 単体テストや API のテストで確かめる方が適切で、画面を通す意味が薄い |
| 手動確認に隔離 | 見た目の判断など、人の目で確かめる必要がある |
| この画面の対象範囲外 | 他の画面が主役の振る舞い（この画面への入り口となる他画面のボタン、遷移先の画面の詳細な表示など） |
| 共通の観点で担保 | 全画面で共通の振る舞い（共通レイアウト、全画面に共通の認証の扱いなど） |

### Step 6: 仕様確認事項を書く

Step 3 で「矛盾」「記載なし」に振り分けたものを、次の2つに分けて書く。

| 区分 | 何を書くか | 書き方 |
|---|---|---|
| 仕様の食い違い（要回答） | 「矛盾」に振り分けたもの | 閉じた質問と回答の選択肢の案を書き、影響する観点の ID か、保留した観点の案を添える。学習者がダッシュボードで回答を選ぶ |
| 仕様に書かれていない点（回答不要） | 「記載なし」に振り分けたもの | ID を振らず、1項目1行の箇条書きで、何が書かれていないかと見た箇所を短く書く。観点にはせず、テストもしない |

仕様の食い違いは、読んだ人が**その場で回答できる形**にする。回答しづらい書き方だとレビューが止まるためである。

- 質問文は1つの問いだけにする。「〜か、また〜か」と2つ詰めない。
- 質問の形は「〜するか」か「A と B のどちらにするか」に限る。「どう振る舞うか」「どう扱うか」のような開いた問いにしない。答える人が選ぶだけで済むようにするためである。
- 回答の選択肢は、食い違う両側の記述に合わせたものを2〜3個、「A. <案>／B. <案>」の形で書く（例：「A. 含めない（画面仕様書の記述に合わせる）／B. 含める（要件定義書の記述に合わせる）」）。ダッシュボードはこの形を読み取って選択肢を表示する。

仕様に書かれていない点を回答不要にするのは、このチュートリアルでは仕様書を変えないためである。実際の開発なら仕様を決める人に確認に出すものだが、学習者が仮の回答をしても正解がない。学習者がテストに必要だと考えた点は、差し戻しの理由に書いてもらう。

次のような項目は、仕様書に明記がない限り確定の観点にせず、仕様に書かれていない点に書く。

- 過去日時の入力可否、期間の最長・最短、営業時間などの日時制約
- 数値の最小値・最大値、0 や負数の扱い、定員との関係
- 文字数制限（データ型の上限しか書かれていない場合を含む）、空白の扱い、文字種
- 片方だけ入力した場合など、組み合わせの不備の画面上の扱い
- エラーメッセージの文言と表示位置（文言が仕様にない場合）
- 二重送信の防止、通信失敗・タイムアウト時の画面の動き
- タイムゾーン、日時の入力単位
- 不正なクエリパラメータ（存在しない ID 等）を受けたときの扱い

### Step 7: ID を付ける

画面を表す大文字の略号を決め（例：`/reservations/new` なら `RSV-NEW`、`/resources` なら `RES-LIST`）、観点は `<略号>-VP-001`、仕様の食い違いは `<略号>-Q-001`、確認しない観点は `<略号>-EX-001` とする。並び順を確定してから、欠番なしで通し番号を振る。`Docs/test/*/perspectives.md` に同じ略号を使う既存の観点一覧があれば、別の略号にする。

観点に優先度は付けない。観点一覧に載せた観点はすべてテストするためである。

### Step 8: 自己点検してから保存する

次をすべて確かめ、満たさない点は直してから保存する。

- すべての観点に、文書名と節（要件 ID があれば ID も）の根拠がある。その節は実在する。
- 「矛盾」として挙げた項目は、食い違う両側の記載元を読み直し、それぞれが本当にその側の内容を書いているかを確かめた。
- 「」で囲んだ仕様の文言は、仕様書の原文どおりである。仕様にない挙動を、確定の観点や「根拠にした仕様」の確定の行に書いていない。
- 観点の文に、HTTP ステータス、エラーコード、テーブル名・カラム名、実装のファイル名が入っていない。
- 同じ条件・同じ操作・同じ期待結果の観点が重複していない。
- Step 3 で「矛盾」にしたものがすべて仕様の食い違いに、「記載なし」にしたものがすべて仕様に書かれていない点に載っている。仕様の食い違いには、閉じた質問と「A. …／B. …」の形の回答の選択肢がある。
- 仕様に書かれていない点を、観点にしていない。
- 確認しない観点に、すべて上の語彙の理由が付いている。
- ID に重複と欠番がない（新規作成なので欠番も作らない。差し戻しの修正で生じる欠番は、e2e-workflow の決まりで認めている）。集計の数が表の行数と一致している。

## 出力

保存先は `Docs/test/<スラッグ>/perspectives.md` とする。この成果物は学習者の作業ブランチにコミットしてよいが、main にはマージしない。スラッグは画面パスの先頭の `/` を除き、`/` を `-` に、`{id}` を `id` に置き換え、英小文字にしたもの（例：`/reservations/new` は `reservations-new`、`/resources` は `resources`）。このスラッグの決め方は、ワークフローの案内スキル（`e2e-workflow`）と状態ファイル（`Docs/test/<スラッグ>/state.json`）でも使う。

同じパスのファイルが既にあれば、上書きせずに止めて利用者に知らせる。このスキルは新規作成専用で、既存の観点の更新は扱わないためである。

ファイルの様式は [`references/output-template.md`](references/output-template.md) に従う。

保存したら、結合テストのワークフローの状態ファイルを更新する。状態ファイルがなければ作り、試験観点の段階を「レビュー待ち」にする。直接このスキルを呼ばれた場合も、ワークフローの案内スキル（`e2e-workflow`）から呼ばれた場合も、同じ状態になるようにするためである。状態ファイルは直接編集せず、必ず次のコマンドを使う。

```bash
node scripts/e2e-workflow/state.mjs init <スラッグ> <画面パス>
node scripts/e2e-workflow/state.mjs ai-output <スラッグ> perspectives "観点のたたき台を出力"
```

保存と状態の更新が済んだら、チャットには次だけを返す（一覧の全文は貼らない）。

- 保存先のパス
- 分類ごとの観点数、仕様の食い違いの数、確認しない観点の数、仕様に書かれていない点の数
- レビューが済んだら、ワークフローのダッシュボード（`http://localhost:3130/screen/<スラッグ>`）で、仕様の食い違いに回答し、確定か差し戻しを選ぶこと
