# 出力様式（code.md）

`<...>` を埋めて使う。節の順番と表の列は変えない。列の見出しの文字も変えない（ダッシュボードが見出しの文字で列の役割を見分けるため）。該当する行がない表は、表の代わりに「該当なし」と書く。

ケースとテストの対応表は作らない。ダッシュボードが、テスト名の先頭のケース ID から数える。

````markdown
# <画面名>（`<画面パス>`）テストコードの説明

| 項目 | 内容 |
|---|---|
| 対象画面 | <画面名>（`<画面パス>`） |
| テストコード | `frontend/tests/e2e/workflow/<スラッグ>.spec.ts` |
| 元にした試験ケース | `Docs/test/<スラッグ>/cases.md` |
| 作成日 | <YYYY-MM-DD> |

この説明は、生成したテストコードをレビューするための資料である。学習者の判断が要るところだけを書く。テストコードの全文は上のファイルにある。

## 1. テストデータの用意

| データ ID | 条件 | 用意のしかた | 注意 |
|---|---|---|---|
| <略号>-D-01 | <試験仕様書 1.2 の条件> | <初期データから条件で選ぶ／API で作る、と使う関数> | <データベースに残る、など。なければ空欄> |

## 2. 仕様と実装で名前が違うところ

| 仕様書の名前 | 実装の名前 | 使うケース |
|---|---|---|
| <試験ケースや仕様書に書かれた名前> | <テストコードで指定した名前> | <ケース ID> |

## 3. ケースどおりに書けなかったところ

| ケース ID | ケースの記述 | テストコードでの書き方 | 結果への影響 |
|---|---|---|---|
| <略号>-TC-0nn | <ケースの記述> | <近い書き方> | <この書き方で、結果や見つけられる不具合がどう変わりうるか> |

## 4. テストコードにできなかったケース

| ケース ID | 書けなかった理由 |
|---|---|
| <略号>-TC-0nn | <理由を1文で> |

## 5. 集計

| 区分 | 件数 |
|---|---|
| 試験ケース | <n> |
| テスト | <n> |
| テストコードにできなかったケース | <n> |
| 仕様と実装で名前が違うところ | <n> |
| ケースどおりに書けなかったところ | <n> |
````
