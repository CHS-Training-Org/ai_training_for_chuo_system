# テストコード生成（新規作成）

## このスキルの位置づけ

結合テストは、試験観点、試験ケース、テストコードと実行の3つの段階で進める。このスキルは3つ目の段階の前半を担い、学習者が確定させた試験ケースを、Playwright のテストコードに変換する。テストを流して証拠を集め、フェイルしたケースに見立てを書くのは、案内スキル（e2e-workflow）が続けて行う。何を確かめるか（期待結果）は試験ケースで決まっている。このスキルが決めるのは、それを画面のどの要素を操作して、どう書けば確かめられるかだけである。

この段階からは、実装コードを読んでよい。ボタンや入力欄を指定するには、実装の画面に付いている名前やラベルが要るからである。ただし、**期待結果は試験ケースからだけ取る**。実装を読んで「この画面ではこう表示されるはずだ」と期待結果を作り直すと、仕様とずれた実装をそのまま正解として固定してしまう。実装が試験ケースの期待結果を満たしていないように見えても、`expect` を弱めたり外したりせず、試験ケースのとおりに書く。実際にどうなるかは、このあと流した結果で確かめる。

生成したテストコードは学習者の成果物で、main にはマージしない。置き場所は `frontend/tests/e2e/workflow/` に決めてあり、普段の `pnpm test:e2e` には含まれない。

## 作らないもの

- 試験ケースにない `test`、試験ケースと異なる期待結果
- 共通の機構（`frontend/tests/e2e/helpers/`、`playwright.config.ts`、`auth.setup.ts`、`cleanup.setup.ts`）の変更。足りない機能があれば、そのケースを「テストコードにできなかったケース」に書く
- 実装コード、仕様書、観点一覧、試験ケース一覧の修正
- テストの実行と、失敗に合わせた修正（案内スキルが流し、直すかどうかは証拠を見た学習者が決める）

## 手順

### Step 1: 対象画面を決め、入力がそろっているかを確かめる

スラッグの決め方は `.claude/skills/generate-test-perspectives/SKILL.md` の「出力」の節と同じ。次のコマンドで状態を確かめ、試験ケースの段階が「確定」でなければ作らずに止める。

```bash
node scripts/e2e-workflow/state.mjs show <スラッグ>
```

`frontend/tests/e2e/workflow/<スラッグ>.spec.ts` か `Docs/test/<スラッグ>/code.md` が既にあれば、上書きせずに止めて知らせる。

### Step 2: 読むもの

| 読むもの | 使い道 |
|---|---|
| `Docs/test/<スラッグ>/cases.md`（試験ケース一覧） | 変換するケース、テストデータの条件、基本の入力、AI が仮に決めた値。期待結果の出どころはここだけ |
| `Docs/test/<スラッグ>/perspectives.md`（観点一覧） | ケースの意図が読み取りにくいときの手がかり |
| `frontend/src/app/`、`frontend/src/components/` の対象画面の実装 | ボタン、入力欄、見出し、表の名前やラベル。要素の指定にだけ使う |
| `frontend/tests/e2e/helpers/workflow-test.ts` | 生成したテストが使う `test`。テストごとに、結合テスト専用のデータベースを初期データだけの状態に戻す |
| `frontend/tests/e2e/helpers/reservations.ts`、`helpers/setup-data.ts`、`helpers/evidence.ts` | 時間帯の割り当て、テスト用の利用目的、前提データの用意、実行の証拠（見る場所の画面、使った値）を残す関数 |
| `frontend/tests/e2e/reservation-request.spec.ts` | 書き方の手本（要素の指定、時間帯）。普段のテストなので後片付けがあるが、生成したテストには書かない |
| `scripts/seed.sql`（初期データ） | テストデータの条件に合うデータがあるか |
| `docs-next/docs/spec/api-spec.md` | 前提データを API で用意するときの形 |

### Step 3: テストデータを対応づける

試験ケース一覧の 1.2「テストデータ」の各行について、条件に合うデータをどう用意するかを決め、`code.md` の1章に書く。

- 初期データに条件に合うものがあれば、`findActiveResource` に**条件**と、エラーのときに出す条件の説明を渡して選ぶ（例：`findActiveResource((r) => r.requiresApproval, "承認が必要な有効なリソース")`）。名前や ID をテストコードに直接書かない。画面で選ぶときは、取得したリソースの名前を使う。
- 初期データにない場合は、`helpers/setup-data.ts` の関数で作る。無効なリソースは `findOrCreateInactiveResource` を使う。
- 既存の予約が要るケースは、`createReservationAs` で作る。利用目的は `existingPurposeFor(testInfo)` にする。印（`[e2e]`）の直後に「既存」が入るので、テスト自身の利用目的（`purposeFor(testInfo)`）と先頭が一致せず、証拠の画面でも見分けられる。既存の予約を2件以上作るときは、`existingPurposeFor(testInfo, "既存1")` のように語を変える。`purposeFor(testInfo)` の後ろに語を足した文字列は使わない（テスト自身の利用目的と前方一致する）。承認と却下は `decideAsAdmin` で行う。
- 用意できない場合は、そのケースを4章「テストコードにできなかったケース」に書く。

### Step 4: 試験ケースをテストコードに変換する

テストファイルは、`test` と `expect` を `@playwright/test` からではなく `../helpers/workflow-test` から取る（`import { test, expect } from "../helpers/workflow-test";`）。この `test` は、テストごとに結合テスト専用のデータベースを初期データ（`scripts/seed.sql`）だけの状態に戻してから動かす。そのため、前のテストが作ったデータは残っておらず、後片付けは要らない。前提のデータ（既存の予約、無効なリソース）は、そのテストの中で作る。

1つの試験ケースを1つの `test` にする。テスト名は**ケース ID で始める**（例：`test("RSV-NEW-TC-001 MEMBER でサインインして開くと、予約申請フォームが表示される", ...)`）。ダッシュボードは、テスト名の先頭のケース ID でケースとの対応を数える。分類（試験ケース一覧の 2.1、2.2 …）ごとに `test.describe` でまとめる。

テストは学習者が1件ずつ試験ケースと突き合わせて読む。そのため次のように書く。

- **1つのケースは1つの `test(...)` で、テスト名を文字列のまま書く。** 配列とループでテストを作らない。ループで作ると、テスト名がコードに直接現れず、ダッシュボードがケースとの対応を数えられないうえ、学習者がケースごとにコードを読めない。似たケースが続く場合は、共通の手順を関数にまとめ、各 `test` ではその関数に渡す値（日時、期待結果）を書く。
- **各 `test` の中で、何を入力し、何を確かめるかが読み取れるようにする。** 共通の関数に入れてよいのは、操作の手順（フォームへの入力、一覧の読み取り）だけで、`expect` は各 `test` の中に書く。

| 試験ケースの記述 | テストコードでの書き方 |
|---|---|
| 「MEMBER でサインイン済み」 | 何もしない（標準のセッションが MEMBER） |
| 「APPROVER でサインイン済み」「ADMIN でサインイン済み」 | その `describe` で `test.use({ storageState: "playwright/.auth/approver.json" })` |
| 「サインインしていない」 | `test.use({ storageState: { cookies: [], origins: [] } })` |
| テストの途中で別のロールに切り替える | `browser.newContext({ storageState: "playwright/.auth/approver.json" })` で別のページを開く |
| 割り当て枠からの相対の日時 | `slotFor(testInfo)` の開始に分を足して作り、入力欄には `toDatetimeLocal` で入れる |
| 「テスト用の利用目的」 | `purposeFor(testInfo)` |
| 文字数を指定した利用目的 | `purposeFor(testInfo)` に文字を足して指定の文字数にした文字列 |
| 基本の入力 | 試験ケース一覧の 1.3 の値 |

要素の指定と待ち方は次のとおりにする。

- 要素は `getByRole`、`getByLabel`、`getByText` で、実装に付いている名前やラベルで指定する。`data-testid`、CSS セレクタ、XPath は使わない。
- 試験ケース（仕様書）の名前と、実装の名前が違う場合は、実装の名前で指定し、`code.md` の2章に書く（例：仕様書は「申請する」、実装は「予約を申請する」）。名前の違いが不具合かどうかは学習者が判断する。
- `page.waitForTimeout` で固定時間を待たない。`expect` が要素の出現を待つ。
- 操作のあと、処理が終わるのを待つときは、画面の変化（ボタンの表示が「申請中...」から戻る、画面が移る、メッセージが出る）を待つ。通信の完了（`waitForRequest`、`waitForResponse`、`request.response()`、`response.finished()`）では待たない。画面がエラーになると、ブラウザが応答の受け取りを途中で打ち切ることがあり、そのとき通信の完了を待つ処理は終わらず、テストが制限時間（30秒）まで止まるためである。
- `waitFor` などで明示的に待つときは、`timeout` を10秒以下にする。期待結果の要素（メッセージなど）が出るのを待つ場合は、待ち切れなくても `.catch(() => undefined)` で先へ進め、`evidence` で撮ってから `expect` でフェイルさせる。期限なしで待つと、期待結果と違ったケースが「途中で止まった」に分類され、見る場所の画面も残らない。
- 期待結果は、試験ケースの「期待結果」を、「見る場所」に書かれた場所で、そのとおりに `expect` で書く。「申請できないこと」は、見る場所（マイ予約一覧など）に、このテストの利用目的の予約がないことで確かめる。表示されたことだけでなく、文言や件数まで確かめる。
- 期待結果を確かめる `expect` が1つの `test` に2つ以上あるとき（見る場所が2つあるケースや、メッセージと件数を両方確かめるケース）は、最後の1つを除いて `expect.soft` にする。1つ目の期待結果と違っても、テストが先へ進み、残りの見る場所の画面と確かめた結果が残るようにするためである（例：重複のメッセージが出なくても、マイ予約一覧を開いて撮り、予約がないことを確かめる）。手順の途中の確認（画面が開いたことの確認など）は `expect.soft` にしない。そこでフェイルしたら、その先の手順は意味がないためである。

実行の証拠は、次の2つを残す（`helpers/evidence.ts`）。学習者はテストコードを読まず、この2つを試験ケースの「期待結果」「見る場所」と並べて見て、期待結果が成り立っていたかを判断する。

見る場所の画面：

- 各 `test` で、試験ケースの「見る場所」（マイ予約一覧、予約申請フォームのメッセージ欄、承認待ち一覧など）を開いたら、期待結果を確かめる `expect` の直前に `await evidence(page, "<場所の名前>")` を呼ぶ。`page` は、その場所を開いているページにする。別のページで一覧を開いて確かめる場合は、そのページを渡す。
- `<場所の名前>` は、試験ケースの「見る場所」の言葉で書く（例：「マイ予約一覧」「予約申請フォームのメッセージ欄」）。
- 見る場所が2つあるケース（メッセージ欄と一覧など）は、それぞれで撮る。
- 確かめる行が画面の外になる場合でも、画面全体を撮るので位置を合わせる必要はない。

このテストで使った値：

画面には「テスト用の利用目的」や「RSV-NEW-D-01」ではなく、実際の文字列、リソースの名前、日時が出る。学習者が見る場所の画面でどの行を見ればよいかを分かるように、テストが実際に使った値を `await usedValue("<何の値か>", <値>)` で残す。

- 残す値は次の3種類。値が決まった直後（入力や選択の前、または API でデータを作った直後）に呼ぶ。
  - 手順と入力で、入れた値と選んだ値のすべて。利用目的は `purposeFor(testInfo)` などで作った実際の文字列を渡す。空欄のまま押す項目は `null` を渡す（「（空欄）」と残る）
  - テストの前に API で作ったデータのうち、見る場所の画面に写りうるもの（既存の予約のリソースの名前、日時、状態など）
  - 見る場所で行を見分けるのに使う値（利用目的が空欄のケースで、代わりに見分けるのに使うリソースと日時など）
- `<何の値か>` は試験ケースの言葉で書く。テストデータは ID を添えて、学習者が試験ケースの ID と画面の名前を結び付けられるようにする（例：「利用目的」「リソース（RSV-NEW-D-01）」「開始日時」「既存予約（RSV-NEW-D-02）の日時」）。
- 日時は `Date` のまま渡す。画面と同じ形式（`toLocaleString("ja-JP")`）で残る。文字列に直して渡さない。
- 予約の状態のような値は、API の値（`APPROVED`）ではなく、画面の表示（「承認済み」）で渡す。
- 長い値（255文字の利用目的など）も、省略せずにそのまま渡す。

後片付け（`cancelE2EReservations`、`test.afterEach`）は書かない。次のテストの前に、データベースが初期データに戻るためである。

### Step 5: ケースどおりに書けないところを書き出す

試験ケースの記述を、そのままではテストコードにできないことがある。その場合は、近い書き方で書いたうえで `code.md` の3章に書く。載せるのは、書き方によってテストの結果か、見つけられる不具合が変わるものだけである。要素の指定方法のように、どう書いても結果が変わらないものは載せない。

例：「画面が移る前にもう一度押す」を、1回目のクリックの直後に2回目のクリックを送る書き方にした。画面がすぐに移ると2回目が押せず、二重送信の防止を確かめられないことがある。

テストコードにできないケースは、`test` を作らずに4章に理由とともに書く。`test.skip` や `test.fixme` で残さない。外すかどうかを決めるのは学習者である。

### Step 6: 書いたテストが読み込めるかを確かめる

次のコマンドで、テストが読み込めて、`[workflow]` の行が試験ケースの数だけ（4章に書いたケースを除く）一覧に出ることを確かめる。一覧には、先に動く準備のテスト（`[setup]` と `[pre-clean]` の行）も出て、最後の `Total` に含まれるが、これは数えない。テストは実行しない。

```bash
cd frontend && E2E_WORKFLOW=1 pnpm exec playwright test --project=workflow --list tests/e2e/workflow/<スラッグ>.spec.ts
```

エラーが出たら直してから保存する。

### Step 7: 自己点検してから保存する

- 試験ケース一覧の2章のすべてのケース ID が、いずれかのテスト名の先頭か、`code.md` の4章のどちらかにある。
- `expect` が、試験ケースの期待結果より弱くなっていない。見る場所で確かめている。実装に合わせて変えていない。
- `data-testid`、CSS セレクタ、XPath、`waitForTimeout`、`test.only`、`test.skip`、`test.fixme`、日付の文字列（`2027-01-01` など）がない。
- 通信の完了（`waitForRequest`、`waitForResponse`、`request.response()`、`response.finished()`）で待っていない。明示的な待ちには、10秒以下の `timeout` がある。
- `test` と `expect` を `../helpers/workflow-test` から取っている。後片付けを書いていない。
- リソースの名前や ID をテストコードに直接書いていない。
- テストを配列とループで作っていない。`expect` が各 `test` の中にある。
- すべての `test` で、見る場所を開いたあと、期待結果の `expect` の前に `evidence` を呼んでいる。
- 期待結果の `expect` が2つ以上ある `test` では、最後の1つを除いて `expect.soft` にしている。
- すべての `test` で、手順と入力で入れた値と選んだ値、見る場所に写る前提データの値を `usedValue` で残している。日時は `Date` のまま渡している。
- `code.md` の集計の数が表の行数と一致している。

## 出力

テストコードは `frontend/tests/e2e/workflow/<スラッグ>.spec.ts`、レビュー用の説明は `Docs/test/<スラッグ>/code.md` に保存する。`code.md` の様式は [`references/output-template.md`](references/output-template.md) に従う。

状態ファイルは変えない。テストコードと実行の段階を「レビュー待ち」にするのは、テストを流してフェイルしたケースに見立てを書いたあとで、案内スキル（e2e-workflow）が行う（`state.mjs` も、流した結果がそろうまでは受け付けない）。

チャットには次だけを返す（コードの全文は貼らない）。

- 保存したファイルのパス
- テストの数、テストコードにできなかったケースの数、仕様と実装で名前が違うところの数、ケースどおりに書けなかったところの数
- レビューで最初に見てほしい点を最大3つ
- このあと、案内スキルがテストを流して証拠を集めること
