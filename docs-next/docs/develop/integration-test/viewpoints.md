# 試験観点を作る

このチュートリアルでは、予約申請画面を題材に、結合テストの試験観点を確定させるまでを体験します。**試験観点**とは、その画面で「何が正しく動けばよいか」を、テストに落とす前の言葉で書き出したものです。

このページは、[結合テストのワークフロー](./workflow.md)の最初の段階にあたります。観点のたたき台は AI が出力します。学習者は、すべての観点を仕様書と突き合わせてレビューし、観点を確定させます。AI の出力には、仕様にない期待結果や引用の取り違えが混ざることがあり、どの行に混ざるかは前もって分からないためです。

## 学習目標

このチュートリアルを終えると、次ができるようになります。

- AI に試験観点のたたき台を出力させ、レビューで何を確かめるかを説明できる
- 仕様書を根拠に、AI が出した観点の誤り、漏れ、余計な指摘を見つけて、AI に直させられる
- 観点を外すかどうかを、理由を付けて決められる

## ゴール

仕様書に根拠がある観点の一覧を確定させます。仕様の食い違いへの回答も、一覧に反映された状態にします。

---

## AI と学習者の役割分担 {#roles}

### AI が出力するもの

試験観点のたたき台は、[`generate-test-perspectives`](../../reference/claude-code/agent-config.md) スキルが1つのファイル（以下「観点一覧」。予約申請画面なら `Docs/test/reservations-new/perspectives.md`）に出力します。スキルは仕様書（`docs-next/docs/spec/`）だけを根拠にし、実装コードは読みません。動いている画面や実装から期待結果を作ると、仕様とずれた実装をそのまま正解として固定してしまうためです。以下で「4.1」のように書いているのは、この観点一覧の章と節の番号です。

| 観点一覧の章 | AI が書く内容 |
|---|---|
| 1章 根拠にした仕様 | 仕様書から拾った仕様と記載元。確定しているものと、文書どうしで食い違うものに分ける |
| 2章 試験観点 | 仕様を根拠にした観点 |
| 3章 確認しない観点 | 意図して外す観点と、その理由 |
| 4.1 仕様の食い違い | 文書どうしで食い違う点を、選択肢（A、B など）から選んで答えられる質問にしたもの。回答で期待結果が逆になる観点は、回答ごとの観点案として保留する |
| 4.2 仕様に書かれていない点 | 仕様書に書かれていないため、期待結果を決められず、観点にしなかった点 |
| 5章 集計 | 件数 |

学習者が差し戻すと、AI は指摘と回答に沿って観点一覧を直します。

### 学習者が決めること

| 学習者がやること | 対象の章 | 手順 |
|---|---|---|
| AI の出力を見る前に、壊れたら困ることを3つ書き出す | （スキル実行前） | 手順1 |
| すべての観点の根拠を、仕様書で確かめる | 1章、2章 | 手順3-1 |
| 食い違いを確認する | 4.1 | 手順3-2 |
| 除外に賛成するか反対するかを決める | 3章 | 手順3-3 |
| 壊れたら困ることと照らし合わせる | 2章、4.2 | 手順3-4 |
| 食い違いに回答し、差し戻すか確定するかを決める | 4.1、全体 | 手順4 |

レビューで見つけた問題は、差し戻しの理由に書きます。問題のない行に印を付けていく記録は作りません。実際の現場のレビューでも、残すのは指摘です。指摘、回答、確定の操作は、日時付きでダッシュボードの記録に残ります。

学習者が確かめないものもあります。ID の連番、件数の集計、章の構成と表の形式です。これらは AI が毎回安定して正しく出力しており、人が読み直しても得るものがほとんどありません。

### この分担にする理由 {#why}

分担は、スキルを繰り返し実行して見えた AI の特性から決めています。運営者が同じスキルを予約申請画面、リソース一覧、マイ予約一覧、承認待ち一覧で実行し、出力を仕様書と照らし合わせました。各画面の実行は数回ずつなので、次の表は確立した事実ではなく、この計測で見えた傾向です。

| 見えた傾向 | 実際に起きたこと | 対応するレビュー |
|---|---|---|
| 実行するたびに、拾う観点や指摘が変わる | 同じ画面でも、観点の数が回によって変わった（スキルの初期の版では、18 件から 24 件まで変わった）。ある回に拾った食い違いを、次の回に見落とすこともあった | すべての観点を仕様書と突き合わせる（手順3-1）。壊れたら困ることと照らし合わせる（手順3-4） |
| 食い違いの見落としと、挙げすぎの両方が起きる | 本物の食い違いを見落とす回があった。逆に、要件が詳細を省略して書いているだけの箇所を食い違いとして挙げ、確定できる観点を保留にした回もあった | 食い違いを確認する（手順3-2） |
| 引用の取り違えや、仕様にない表示の書き足しが起きる | 別の側の記述を食い違いの根拠に数えた回があった。仕様が「申請不可」としか書いていないのに、「エラーが表示される」を期待結果に足した回もあった | すべての観点の根拠を確かめる（手順3-1） |
| 仕様書にない暗黙の期待は拾えない | 仕様書に書かれていないことは、観点にならない | 壊れたら困ることを先に書き、照らし合わせる（手順1、手順3-4） |

根拠の確認を抜き取りにしないのは、誤りがどの行に出るかが実行のたびに変わるためです。抜き取った行に誤りがなくても、残りの行に誤りがないとは言えません。

観点を減らす判断を人が担うのは、観点を増やす誤りよりも減らす誤りの方が気づきにくいためです。AI が余計な観点を出しても、レビューで外せば済みます。一方、必要な観点を AI が外してしまうと、外したことに誰も気づかないまま、テストの検出力が落ちます。除外（3章）への賛否と、食い違い（4.1）への回答を学習者が決め、仕様に書かれていない点（4.2）を学習者が見直すのはこのためです。[^nakano]

[^nakano]: この考え方は、JaSST'26 Niigata の講演「[AI に任せた品質は、誰が見立てるのか](https://speakerdeck.com/nakanao/ai-ni-makaseta-hinshitsu-ha-dare-ga-mitateru-no-ka-ai-jidai-no-tesuto-manejimento)」（中野直樹氏）から採っています。同講演は、テストを増やす判断は AI に案を出させて人が間引けばよいが、減らす判断は人が根拠を残して決めるべきだとしています。

AI の判定を学習者がそのまま承認するだけでは、判定する力が身につきにくいことも知られています。[^anthropic] 手順1で AI の出力を見る前に自分の見立てを書くのは、このためです。

[^anthropic]: Anthropic の研究「[How AI assistance impacts the formation of coding skills](https://www.anthropic.com/research/AI-assistance-coding-skills)」（2026年1月）は、AI に作業を丸ごと任せたり、デバッグを繰り返し任せたりした参加者ほど、理解度テストの点が低かったと報告しています。

## 対象画面

予約申請画面（`/reservations/new`）を対象とします。利用者がリソース（施設や備品）を選び、日時と目的を入力して予約を申請する画面です。仕様は[画面仕様書](../../spec/screen-spec.md)の予約申請画面の節にあります。

---

## 手順1 壊れたら困ることを書く {#step1}

AI の出力を見る前に、対象画面を開き、画面仕様書の予約申請画面の節を読みます。そのうえで、この画面で壊れたら利用者や業務が困ることを3つ、手元のメモに書きます。

仕様書の要約やメモを作る必要はありません。仕様書そのものが根拠なので、読むことに時間を使います。

:::note[先に書く理由]

AI の一覧を先に見ると、それに引きずられて自分の見立てを持てなくなります。先に書いた3つが一覧に入っているかを手順3-4で照らし合わせると、AI が拾えなかった暗黙の期待に気づけます。

:::

---

## 手順2 スキルで観点のたたき台を作る {#step2}

Claude Code に次のように依頼します。

```text
/e2e-workflow 予約申請画面（/reservations/new）の結合テストを進めたい
```

ワークフローの案内スキル（`e2e-workflow`）が、画面ごとの状態ファイルを作り、観点のたたき台を作るスキル（`generate-test-perspectives`）を呼び出します。観点一覧は `Docs/test/reservations-new/perspectives.md` に保存され、試験観点の段階は「レビュー待ち」になります。ワークフロー全体の進め方は[結合テストのワークフロー](./workflow.md#where-am-i)にあります。

`/e2e-workflow` は、スラッシュを付けてそのまま打ってください。セッションが Sonnet でも、このコマンドで始めたときだけ、観点のたたき台を作り終えるまで Opus で動きます。「結合テストを進めたい」のようにスラッシュを付けずに頼むと、案内スキルは起動しても Sonnet のまま動きます。組織の設定で Opus が許可されていない場合も、Sonnet のまま動きます。所要時間は、Opus で10分前後です。

チャットには、保存先と件数が表示されます。一覧の全文はチャットには出ないので、ダッシュボードかファイルで読みます。

保存した一覧は作業ブランチにコミットしてかまいませんが、main にはマージしません（[ADR-032 の追記](../../reference/adr/ADR-032-integration-test-tutorial-adoption.md#addendum-2026-09-23)）。

---

## 手順3 たたき台をレビューする {#step3}

観点一覧を仕様書と並べて読み、次の4つを確かめます。直してほしい点が見つかったら、観点の ID と一緒に手元に書き留めておき、手順4で差し戻しの理由にまとめます。

### 3-1. すべての観点の根拠を確かめる {#step3-1}

1章「根拠にした仕様」と2章「試験観点」のすべての行について、記載元の節を仕様書で開き、書いてあるとおりかを確かめます。

- 「」で囲まれた文言が、仕様書の原文どおりか
- 観点の期待結果が、記載元の節に書かれていることから決まるか
- 仕様書が「できない」としか書いていないのに、「エラーが表示される」のような表示が足されていないか

記載元が同じ行は、まとめて確かめると早く済みます。誤りがあれば、行の ID と、仕様書に実際に何と書いてあるかを書き留めます。

### 3-2. 食い違いを確認する {#step3-2}

4.1「仕様の食い違い」の各項目について、両側の記載元を読み、本当に異なることが書かれているかを確かめます。たとえば、画面仕様書が「有効なリソースだけ」を選択肢にすると書き、要件定義書が「ADMIN には無効なリソースも」表示すると書いているのは、同じ条件について異なることを書いているので食い違いです。

AI は、食い違いでないものを食い違いとして挙げることがあります。一方の文書が詳細を省いて書いているだけで、詳しく書いている側と矛盾しない場合です。こうした項目を見つけたら、食い違いではないことを書き留めます。差し戻すと、AI が詳しく書いている側に合わせて観点を入れ直します。

食い違いの項目は、手順4-1でどちらに合わせるかを回答します。

:::note[課題シートは仕様の根拠にならない]

エンハンス課題のシートにある「背景」は、現在の実装を説明した文章で、仕様ではありません。課題シートを根拠にした食い違いが挙がっていたら、食い違いではないと書き留めます。

:::

### 3-3. 除外に賛成するか反対するかを決める {#step3-3}

3章「確認しない観点」の各行について、理由に賛成するか反対するかを決めます。理由は次の5つのどれかです。

| 理由 | 使う場面 |
|---|---|
| 取るに足らない | 他の観点を実行すれば必ず確かめられる、または外しても利用者への影響がない |
| 上流のテストで担保済み | 単体テストや API のテストで確かめる方が適切 |
| 手動確認に隔離 | 見た目の判断など、人の目で確かめる必要がある |
| この画面の対象範囲外 | 他の画面が主役の振る舞い |
| 共通の観点で担保 | 全画面で共通の振る舞い（共通レイアウト、未認証時のリダイレクトなど） |

反対する行は、反対の理由と一緒に書き留めます。差し戻すと、AI が観点として2章に戻します。反対せずに確定すると、3章の除外すべてに賛成したことになります。

### 3-4. 壊れたら困ることと照らし合わせる {#step3-4}

手順1で書いた3つが、2章の観点に入っているかを確かめます。入っていないものは、4.2「仕様に書かれていない点」に挙がっていることがあります。仕様書に書かれていないため、AI は期待結果を決められず、観点にしていません。

テストに必要だと考えたものは、期待結果（何をしたら、どうなれば正しいか）を添えて書き留めます。差し戻すと、AI が観点として足します。4.2 のほかの項目も読み、テストに必要なものがあれば同じように扱います。

## 手順4 観点を確定する {#step4}

### 4-1. 仕様の食い違いに回答する {#step4-1}

ダッシュボード（[結合テストのワークフロー](./workflow.md#where-am-i)を参照）で予約申請画面を開き、観点一覧の上にある「仕様の食い違いへの回答」の欄で、4.1 の各質問に回答を選びます。本来の回答者は仕様を決める人ですが、このチュートリアルでは仕様書を変えないため、学習者が仮に決めます。どちらを選んでも誤りではありません。選んだ回答が実装の振る舞いと違えば、3つ目の段階でテストがフェイルします。そのときは、実装の不具合ではなく「仕様の仮回答による」フェイルとして判断します（[フェイルしたケースの原因を判断する](./execution.md#step2)）。

### 4-2. 差し戻すか確定するかを選ぶ {#step4-2}

手順3で書き留めた指摘があるか、4-1で回答を選んだときは、指摘を「指摘」の欄に書いて「差し戻す」を押します。そのあと、もう一度 `/e2e-workflow` を実行すると、AI が指摘と回答に沿って観点一覧を直し、状態が「レビュー待ち」に戻ります。直された箇所について、手順3の確認を繰り返します。

指摘がなく、回答がすべて観点一覧に反映されていれば、「確定する」を押します。回答を選んで AI が反映するまでは、「確定する」は押せません。確定する前に、観点から具体的な試験ケースを思い描けるかも確かめます。思い描けない観点は粗すぎるので、分けるよう指摘します。

手順1から手順4までの所要時間は、先行実施で測ります。今のスキルでは、予約申請画面の観点が40件前後出るため、根拠の確認だけで1時間を超える可能性があります。

## 次のステップ

確定した試験観点の一覧を持って、次は[試験ケースの作成](./cases.md)へ進みます。そのあと、テストコードと実行の段階で、AI がテストコードを作って流し、学習者は実行の証拠で判断します。段階の全体は[結合テストのワークフロー](./workflow.md)にあります。
