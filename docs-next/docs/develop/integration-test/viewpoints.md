# 試験観点を作る

このステップでは、1つの画面を題材に、AI が出力した試験観点を仕様書と突き合わせてレビューし、確定させます。AI に任せた成果物を、仕様書を根拠に自分で確かめて判断できるようになることがねらいです。

このチュートリアルでいう**試験観点**は、その画面で「何が正しく動けばよいか」を、仕様書の記載を根拠に1行ずつ書いたものです。どのロールで何を入れ、どこを見て確かめるかは、まだ決めません。それは次の段階（[試験仕様書を作る](./cases.md)）で決めます。

ここでは、[結合テストのワークフロー](./workflow.md)の3つの段階のうち、最初の段階（試験観点）の手順を説明します。

## 学習目標

このステップでは、次のことができることを目標とします。

- AI に試験観点のたたき台を出力させ、レビューで何を確かめるかを説明できる
- 仕様書を根拠に、AI が出した観点の誤り、漏れ、余計な指摘を見つけて、AI に修正を指示できる
- AI が「確認しない観点」として外した観点に、理由を付けて賛成か反対かを決められる

## このステップの到達点

仕様書に根拠がある観点一覧が確定し、仕様の矛盾への回答も一覧に反映された状態になります。

---

## AI と学習者の役割分担 {#roles}

### AI が出力するもの

試験観点のたたき台は、[`generate-test-perspectives`](../../reference/claude-code/agent-config.md) スキルが1つのファイル（以下「観点一覧」。予約申請画面なら `Docs/test/reservations-new/perspectives.md`）に出力します。

動いている画面や実装から期待結果を作ると、仕様とずれた実装をそのまま正解として固定してしまいます。そのため、スキルは仕様書のみを根拠にし、実装コードは読みません。このチュートリアルでいう**仕様書**は、`docs-next/docs/spec/` にある要件定義書、画面仕様書、API 仕様書、ER 図のすべてを指します。

観点一覧は、次の章で構成されます。このページで「3章」「4.1」のように書いたときは、観点一覧の章と節の番号を指します。

| 観点一覧の章 | AI が書く内容 |
|---|---|
| 1章 根拠にした仕様 | 仕様書から拾った仕様と記載元。確定しているものと、文書どうしで矛盾するものに分ける |
| 2章 試験観点 | 仕様を根拠にした観点 |
| 3章 確認しない観点 | 意図して外す観点と、その理由 |
| 4.1 仕様の矛盾 | 文書どうしで矛盾する点を、選択肢（A、B など）から選んで答えられる質問にしたもの。回答で期待結果が逆になる観点は、回答ごとの観点案として保留する |
| 4.2 仕様に書かれていない点 | 仕様書に書かれていないため、期待結果を決められず、観点にしなかった点 |
| 5章 集計 | 件数 |

学習者が差し戻すと、AI は指摘と回答に沿って観点一覧を直します。

### 学習者が決めること

| 学習者がやること | 対象の章 | 手順 |
|---|---|---|
| すべての観点の根拠を、仕様書で確かめる | 1章、2章 | 手順2-1 |
| 矛盾を確認する | 4.1 | 手順2-2 |
| 除外に賛成するか反対するかを決める | 3章 | 手順2-3 |
| 抜けがないかを確かめる | 2章、4.2 | 手順2-4 |
| 矛盾に回答し、差し戻すか確定するかを決める | 4.1、全体 | 手順3 |

レビューで見つけた問題は、差し戻しの理由に書きます。指摘、回答、確定の操作は、日時付きでダッシュボードの記録に残ります。

### この分担にする理由 {#why}

分担は、スキルを複数の画面で繰り返し実行して見えた AI の特性から決めています。各画面の実行は数回ずつなので、次の表は確立した事実ではなく、そこで見えた傾向です。

| 見えた傾向 | 実際に起きたこと | 対応するレビュー |
|---|---|---|
| 実行するたびに、拾う観点や指摘が変わる | 同じ画面でも、観点の数が回によって変わった（スキルの初期の版では、18 件から 24 件まで変わった）。ある回に拾った矛盾を、次の回に見落とすこともあった | すべての観点を仕様書と突き合わせる（手順2-1）。抜けがないかを確かめる（手順2-4） |
| 矛盾の見落としと、挙げすぎの両方が起きる | 本物の矛盾を見落とす回があった。逆に、要件が詳細を省略して書いているだけの箇所を矛盾として挙げ、確定できる観点を保留にした回もあった | 矛盾を確認する（手順2-2） |
| 引用の取り違えや、仕様にない表示の書き足しが起きる | 別の側の記述を矛盾の根拠に数えた回があった。仕様が「申請不可」としか書いていないのに、「エラーが表示される」を期待結果に足した回もあった | すべての観点の根拠を確かめる（手順2-1） |
| 仕様書にない暗黙の期待は拾えない | 仕様書に書かれていないことは、観点にならない | 抜けがないかを確かめる（手順2-4） |

AI が観点を外しても、外したことには気づきにくく、そのままテストの抜けになります。そのため、観点を外す判断は学習者が担います（3章の除外への賛否と、4.2 の見直し）。[^nakano]

[^nakano]: この考え方は、JaSST'26 Niigata の講演「[AI に任せた品質は、誰が見立てるのか](https://speakerdeck.com/nakanao/ai-ni-makaseta-hinshitsu-ha-dare-ga-mitateru-no-ka-ai-jidai-no-tesuto-manejimento)」（中野直樹氏）から採っています。同講演は、テストを増やす判断は AI に案を出させて人が間引けばよいが、減らす判断は人が根拠を残して決めるべきだとしています。

## 対象画面

対象画面は、[画面仕様書](../../spec/screen-spec.md)の画面一覧から1つ選びます。予約申請画面以外を選ぶときの始め方と注意点は、[題材の画面を選ぶ](./workflow.md#other-screens)にあります。

このページの手順と例は、予約申請画面（`/reservations/new`）で説明します。利用者がリソース（施設や備品）を選び、日時と目的を入力して予約を申請する画面です。

---

## 手順1 スキルで観点のたたき台を作る {#step1}

[作業ブランチ](./workflow.md#branch)を切ってから、Claude Code に次のように依頼します。

```text
/e2e-workflow 予約申請画面（/reservations/new）の結合テストを進めたい
```

ワークフローの案内スキル（`e2e-workflow`）が、画面ごとの状態ファイルを作り、観点のたたき台を作るスキル（`generate-test-perspectives`）を呼び出します。観点一覧は `Docs/test/reservations-new/perspectives.md` に保存され、試験観点の段階は「レビュー待ち」になります。

:::info[スラッシュを付けて打つ]

`/e2e-workflow` のようにスラッシュを付けて打つと、案内スキル（`e2e-workflow`）が起動します。スラッシュを付けてそのまま打ってください。セッションが Sonnet でも、このコマンドで始めたときだけ、観点のたたき台を作り終えるまで Opus で動きます。「結合テストを進めたい」のようにスラッシュを付けずに頼むと、案内スキルは起動しても Sonnet のまま動きます。組織の設定で Opus が許可されていない場合も、Sonnet のまま動きます。

:::

たたき台ができるまで、Opus で10分前後かかります。チャットには、保存先と件数が表示されます。一覧の全文はチャットには出ないので、ダッシュボードかファイルで読みます。

---

## 手順2 たたき台をレビューする {#step2}

観点一覧を仕様書と並べて読み、次の4つを確かめます。直してほしい点が見つかったら、観点の ID と一緒に手元に書き留めておき、手順3で差し戻しの理由にまとめます。

### 2-1. すべての観点の根拠を確かめる {#step2-1}

1章「根拠にした仕様」と2章「試験観点」のすべての行について、記載元の節（1章は「記載元」、2章は「仕様根拠」の列）を仕様書で開き、行の内容が仕様書の記載と合っているかを確かめます。

- 「」で囲まれた文言が、仕様書の原文どおりか
- 観点の期待結果が、記載元の節に書かれていることから決まるか
- 仕様書が「できない」としか書いていないのに、「エラーが表示される」のような表示が足されていないか

### 2-2. 矛盾を確認する {#step2-2}

4.1「仕様の矛盾」の各項目について、両側の記載元（「見た箇所」の列）を読み、本当に異なることが書かれているかを確かめます。たとえば、予約申請画面のリソースの選択肢について、画面仕様書は「有効なリソースだけを出す」と書き、要件定義書は「ADMIN には無効なリソースも出す」と書いています。同じ選択肢について2つの文書の内容が違うので、これは矛盾です。

AI は、一方の文書が詳細を省いているだけの箇所を、矛盾として挙げることがあります。見つけたら「矛盾ではない」と書き留めて差し戻すと、AI が詳しく書いている側に合わせて観点を作り直します。

矛盾の項目は、手順3-1でどちらに合わせるかを回答します。

:::note[課題シートは仕様の根拠にならない]

エンハンス課題のシートにある「背景」は、現在の実装を説明した文章で、仕様ではありません。課題シートを根拠にした矛盾が挙がっていたら、矛盾ではないと書き留めます。

:::

### 2-3. 除外に賛成するか反対するかを決める {#step2-3}

3章「確認しない観点」の各行について、理由に賛成するか反対するかを決めます。AI は、次の5つの理由のどれかを付けています。賛成するかは、「使う場面」を目安に、その観点に当てはまるかで判断します。

| 理由 | 使う場面 |
|---|---|
| 確認の必要性が低い | 他の観点を実行すれば必ず確かめられる、または外しても利用者への影響がない |
| 上流のテストで担保済み | 単体テストや API のテストで確かめる方が適切 |
| 手動確認に隔離 | 見た目の判断など、人の目で確かめる必要がある |
| この画面の対象範囲外 | 他の画面が主役の振る舞い |
| 共通の観点で担保 | 全画面で共通の振る舞い（共通レイアウト、未認証時のリダイレクトなど） |

反対する行は、反対の理由と一緒に書き留めます。差し戻すと、AI が観点として2章に戻します。反対せずに確定すると、3章の除外すべてに賛成したことになります。

### 2-4. 抜けがないかを確かめる {#step2-4}

一覧を読み終えたら、利用者の使い方や業務のルールに照らして確かめるべき振る舞いが、2章の観点から抜けていないかを見ます。仕様書に書かれていない期待は、AI が期待結果を決められないので、観点にせず 4.2「仕様に書かれていない点」に挙げています。4.2 の各項目も、抜けを探す手がかりとして読みます。

テストに必要だと考えたものは、期待結果（何をしたら、どうなれば正しいか）を添えて書き留めます。差し戻すと、AI が観点として足します。

## 手順3 観点を確定する {#step3}

### 3-1. 仕様の矛盾に回答する {#step3-1}

ダッシュボード（開き方は[進み具合を確かめる](./workflow.md#where-am-i)を参照）で対象画面を開き、観点一覧の上にある「仕様の矛盾への回答」の欄で、4.1 の各質問に回答を選びます。本来の回答者は仕様を決める人ですが、このチュートリアルでは仕様書を変えないため、学習者が仮に決めます。どちらを選んでも誤りではありません。

選んだ回答が実装の振る舞いと違えば、3つ目の段階でテストがフェイルします。そのときは、3つ目の段階のレビューで、実装の不具合ではなく「仕様の仮回答による」フェイルとして判断します。

### 3-2. 差し戻すか確定するかを選ぶ {#step3-2}

3-1で選んだ回答は、AI が観点一覧に反映するまで確定できません。そのため、手順2で書き留めた指摘があるとき、または3-1で矛盾に回答したときは、指摘を「指摘」の欄に書いて（回答だけのときは空欄のまま）「差し戻す」を押します。

そのあと、もう一度 `/e2e-workflow` を実行すると、AI が指摘と回答に沿って観点一覧を直し、状態が「レビュー待ち」に戻ります。直された箇所について、手順2の確認を繰り返します。

指摘がなく、回答がすべて観点一覧に反映されていれば、「確定する」を押します。回答を選んで AI が反映するまでは、「確定する」は押せません。確定する前に、観点から具体的な試験ケースを思い描けるかも確かめます。思い描けない観点は粗すぎるので、分けるよう指摘します。

:::info[所要時間の目安]

予約申請画面では観点が40件前後出たので、根拠の確認だけで1時間を超える見込みです。

:::
