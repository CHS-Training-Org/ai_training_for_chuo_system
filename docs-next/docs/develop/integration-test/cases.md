# 試験ケースに展開する

[試験観点を作る](./viewpoints.md)で確定した試験観点は、「何が正しく動けばよいか」を書いたものです。まだ、どのロールで、何を入れて、どこを見れば確かめられるかは決まっていません。このページでは、観点の一つひとつを、前提条件、手順と入力、期待結果、見る場所を持つ**試験ケース**に展開します。試験ケースの一覧は、従来のテスト仕様書に当たります。

このページは、[結合テストのワークフロー](./workflow.md)の2つ目の段階にあたります。展開は AI が行い、学習者はすべてのケースを観点と突き合わせてレビューし、確定させます。何を確かめるかは試験観点の段階で決め終えているので、ここで確かめるのは、観点が正しく具体化されたかです。

## 学習目標

このページを終えると、次ができるようになります。

- 試験観点から試験ケースへの展開を AI に任せ、何をレビューすればよいかを説明できる
- 試験ケースが展開元の観点と食い違っていないか、観点の条件を本当に満たす入力になっているかを見分けられる
- AI が展開のために選んだ値と、試験ケースにできなかった観点を、理由を付けて判断できる

## ゴール

確定した試験観点のすべてが、試験ケースか「試験ケースにできなかった観点」のどちらかに載っている試験ケースの一覧を確定させます。

---

## AI と学習者の役割分担 {#roles}

### AI が出力するもの

試験ケースは、[`generate-test-cases`](../../reference/claude-code/agent-config.md) スキルが1つのファイル（以下「試験ケース一覧」。予約申請画面なら `Docs/test/reservations-new/cases.md`）に出力します。スキルが読むのは、確定した観点一覧と仕様書だけです。試験観点の段階と同じく実装コードは読まないので、期待結果が実装に引きずられることはありません。

| 試験ケース一覧の章 | AI が書く内容 |
|---|---|
| 1章 テストの前提 | テスト環境の前提と、ケースが使うテストデータの条件 |
| 2章 試験ケース | 観点ごとの試験ケース。分類は観点一覧の2章と同じ |
| 3章 AI が仮に決めた値 | 仕様書に値がなく AI が選んだ値のうち、別の値にするとテストの結果か見つけられる不具合が変わるもの |
| 4章 試験ケースにできなかった観点 | 前提を作れないなどの理由で、ケースにできなかった観点 |
| 5章 集計 | 件数 |

観点一覧の3章「確認しない観点」と、4.2「仕様に書かれていない点」は展開しません。どちらも、試験観点の段階で学習者が扱いを決めています。

### 学習者が決めること

| 学習者がやること | 対象の章 | 手順 |
|---|---|---|
| すべての試験ケースを、展開元の観点と突き合わせる | 2章 | 手順2-1 |
| AI が仮に決めた値が妥当かを判断する | 3章 | 手順2-2 |
| 試験ケースにできなかった観点を外してよいかを判断する | 4章 | 手順2-3 |
| 差し戻すか確定するかを決める | 全体 | 手順3 |

観点とケースの数の対応は、学習者が数えなくてよいようにしています。ダッシュボードが、観点一覧の2章のすべての観点 ID が試験ケース一覧のどこかに載っているかを照らし合わせ、漏れがあれば確定できないようにしています。AI に数えさせた結果を信じるのではなく、機械的に数えた結果で確かめるためです。

## テストの前提

試験ケースは、次のテスト環境で動く前提で書かれています。仕組みの詳細は [Playwright とは](../playwright-guide.md#reservation-fixture)にあります。

- **ロール**：MEMBER、APPROVER、ADMIN の3つのロールごとに、サインイン済みの状態が用意されています。ケースの手順には、サインインの操作が入りません。
- **日時**：テストごとに、他のテストと重ならない1時間の時間帯（以下「割り当て枠」）が割り当てられます。ケースの日時は「枠の開始」「枠の開始の1時間後」のように、割り当て枠からの相対で書かれます。
- **データの初期化**：各テストの前に、結合テスト専用のデータベースが初期データだけの状態に戻ります。前のテストのデータは残りません。
- **利用目的**：画面でそのテストの予約を見分けられるように、テストごとに、印（`[e2e]`）で始まる専用の文字列が用意されます。ケースの利用目的は「テスト用の利用目的」と書かれ、具体的な文字列は書かれません。
- **テストデータ**：「承認が必要な有効なリソース」のような条件だけが書かれ、具体的なリソースの名前は書かれません。条件に合うデータを選ぶのは、次のテストコードの段階です。
- **基本のロール**：観点がロールを指定していなければ、MEMBER で確かめます。作った予約があるかどうかは、テスト用の利用目的と割り当て枠で見分けます。
- **見る場所**：期待結果が成り立っているかを、どの画面のどの部分を見て判断するかが、「マイ予約一覧」「予約申請フォームのメッセージ欄」のように、場所の名前だけで書かれます。何が成り立てばよいかは期待結果の列に書かれています。画面のどの行を見ればよいかは、テストを流したあとで、テストが実際に使った値（利用目的の文字列、リソースの名前、日時）として表示されます。
- **基本の入力**：観点が対象にしない入力項目（「他の項目は正しく入れる」の項目）の値は、1.3「基本の入力」に一度だけ書かれ、ケースからはそれを参照します。

## 手順1 AI に試験ケースを展開させる {#step1}

試験観点の段階を確定させたあと、Claude Code に次のように依頼します。

```text
/e2e-workflow 予約申請画面（/reservations/new）の結合テストを進めたい
```

案内スキル（`e2e-workflow`）が、試験ケースの段階が未着手であることを確かめ、`generate-test-cases` スキルを呼び出します。試験ケース一覧は `Docs/test/reservations-new/cases.md` に保存され、試験ケースの段階は「レビュー待ち」になります。スラッシュを付けて打つ理由は、[試験観点を作る](./viewpoints.md#step2)と同じです。

チャットには、件数と、レビューで最初に見てほしい「AI が仮に決めた値」が表示されます。一覧はダッシュボードで読みます。

---

## 手順2 試験ケースをレビューする {#step2}

試験ケース一覧を観点一覧と並べて読み、次の3つを確かめます。ダッシュボードでは、試験ケースの段階を開くと試験ケース一覧が表示されます。確定済みの観点一覧は、段階表示の「試験観点」を押すと開けます。直してほしい点が見つかったら、試験ケースの ID と一緒に書き留めておき、手順3で差し戻しの理由にまとめます。

### 2-1. すべての試験ケースを、展開元の観点と突き合わせる {#step2-1}

2章の各ケースについて、「展開元」に書かれた観点を観点一覧で開き、次を確かめます。

- 期待結果が、観点の期待結果と同じか（観点にない表示や文言が足されていないか）
- 手順と入力が、観点の条件を本当に満たしているか（境界の観点なら、入力がちょうど境界の値になっているか）
- 前提条件が、観点の「備考」に書かれた前提データを満たしているか
- 見る場所で、期待結果を画面から観察できるか

観点を抜き取りで確かめないのは、試験観点の段階と同じ理由です。誤りがどのケースに出るかは、実行のたびに変わります。

### 2-2. AI が仮に決めた値が妥当かを判断する {#step2-2}

3章「AI が仮に決めた値」には、仕様書に値が書かれていないため AI が選んだ値のうち、別の値にするとテストの結果か見つけられる不具合が変わるものだけが並んでいます。たとえば、日時の入力単位が仕様書にないときに「入力できる最小の差」を何分にしたか、です。入力欄が5分刻みなら、1分の差は入力できず、そのケースは成り立ちません。

各行の「別の値にするとどうなるか」を読み、選んだ値でその観点を確かめられるかを判断します。どの値を選んでも結果が変わらない細かな選択（重複予約の時間帯を割り当て枠のどこに置くか、など）は、3章には載らず、ケースの手順と入力に書かれています。それらは手順2-1 で確かめます。値を変えてほしい場合は、変えたい値と理由を書き留めます。差し戻すと、AI がその値を使うすべてのケースを直します。

### 2-3. 試験ケースにできなかった観点を判断する {#step2-3}

4章「試験ケースにできなかった観点」の各行について、理由に納得できるかを判断します。

- 納得できる場合は、そのまま確定します。確定すると、その観点はテストしないことになります。
- 展開してほしい場合は、どうすれば展開できるか（用意するデータ、観察する場所）を書き留めます。差し戻すと、AI が展開を試みます。

観点を外す判断を学習者が担うのは、試験観点の段階と同じ理由です。必要な観点が外されると、外したことに誰も気づかないまま、テストの検出力が落ちます。

:::note[観点そのものの誤りに気づいたとき]

レビューの途中で、試験観点そのものの誤りや漏れに気づくことがあります。その場合、試験ケース一覧を直すだけでは解決しません。AI も、確定した観点一覧は書き換えません。関門2 で差し戻し、指摘の欄に「前の段階の誤り：観点の ID」と、何が誤りかを書いて、運営者に相談します。運営者が誤りを認めると、観点の段階を確定から差し戻しに戻し、そこから直して進め直します。詳しくは[前の段階の誤りを見つけたとき](./execution.md#upstream)を参照してください。

:::

## 手順3 差し戻すか確定するかを選ぶ {#step3}

ダッシュボード（[結合テストのワークフロー](./workflow.md#where-am-i)を参照）で、「関門2 ケースの確定」の欄を使います。

手順2で書き留めた指摘があれば、「指摘」の欄に書いて「差し戻す」を押します。そのあと、もう一度 `/e2e-workflow` を実行すると、AI が指摘に沿って試験ケース一覧を直し、状態が「レビュー待ち」に戻ります。直された箇所について、手順2の確認を繰り返します。

指摘がなければ「確定する」を押します。観点一覧の2章の観点のうち、どの試験ケースにも、「試験ケースにできなかった観点」にも載っていないものがあると、「確定する」は押せません。関門の欄の「観点との対応」に、その数が表示されます。
