# 試験仕様書を作る

[試験観点を作る](./viewpoints.md)で確定した試験観点は、「何が正しく動けばよいか」を書いたものです。まだ、どのロールで、何を入れて、どこを見れば確かめられるかは決まっていません。このステップでは、観点を1つずつ、前提条件、手順と入力、期待結果、確認箇所を持つ**試験ケース**に展開し、試験ケースを集めた**試験仕様書**を作ります。

ここでは、[結合テストのワークフロー](./workflow.md)の3つの段階のうち、2つ目の段階（試験仕様書）の手順を説明します。展開は AI が行い、学習者はすべてのケースを観点と突き合わせてレビューし、確定させます。何を確かめるかは試験観点の段階で決め終えているので、ここで確かめるのは、観点が正しく具体化されたかです。

## 学習目標

このステップでは、次のことができることを目標とします。

- 試験観点から試験ケースへの展開を AI に任せ、何をレビューすればよいかを説明できる
- 試験ケースが展開元の観点と食い違っていないか、観点の条件を本当に満たす入力になっているかを見分けられる
- 仕様書に値がなく AI が仮に決めた値が妥当か、試験ケースにできなかった観点を外してよいかを、理由を付けて判断できる

## このステップの到達点

試験仕様書が確定した状態になります。確定した試験観点は、すべて試験ケースか「試験ケースにできなかった観点」のどちらかに載っています。

---

## AI と学習者の役割分担 {#roles}

### AI が出力するもの

試験ケースは、[`generate-test-cases`](../../reference/claude-code/agent-config.md) スキルが1つのファイル（以下「試験仕様書」。予約申請画面なら `Docs/test/reservations-new/cases.md`）に出力します。スキルが読むのは、確定した観点一覧と仕様書だけです。試験観点の段階と同じく実装コードは読まないので、期待結果が実装に引きずられることはありません。

| 試験仕様書の章 | AI が書く内容 |
|---|---|
| 1章 テストの前提 | テスト環境の前提と、ケースが使うテストデータの条件 |
| 2章 試験ケース | 観点ごとの試験ケース。分類は観点一覧の2章と同じ |
| 3章 AI が仮に決めた値 | 仕様書に値がなく AI が選んだ値のうち、別の値を選ぶと、テストの結果や、見つけられる不具合が変わるもの |
| 4章 試験ケースにできなかった観点 | 前提を作れないなどの理由で、ケースにできなかった観点 |
| 5章 集計 | 件数 |

観点一覧の3章「確認しない観点」と、4.2「仕様に書かれていない点」に残っているものは、試験観点の段階でテストしないと決めたものなので、AI は試験ケースに展開しません。

AI は、観点一覧の2章のすべての観点が、試験ケースか「試験ケースにできなかった観点」のどちらかに載っていることを機械的に確かめてから、試験仕様書を渡します。

### 学習者が決めること

| 学習者がやること | 対象の章 | 手順 |
|---|---|---|
| すべての試験ケースを、展開元の観点と突き合わせる | 2章 | 手順2-1 |
| AI が仮に決めた値が妥当かを判断する | 3章 | 手順2-2 |
| 試験ケースにできなかった観点を外してよいかを判断する | 4章 | 手順2-3 |
| 差し戻すか確定するかを決める | 全体 | 手順3 |

## テストの前提

試験ケースは、テスト環境が下の箇条書きのように用意されている前提で書かれています。仕組みの詳細は [Playwright とは](../playwright-guide.md#reservation-fixture)にあります。

- **ロール**：MEMBER、APPROVER、ADMIN の3つのロールごとに、サインイン済みの状態が用意されています。ケースの手順には、サインインの操作が入りません。
- **日時**：テストごとに、他のテストと重ならない1時間の時間帯（以下「割り当て枠」）が割り当てられます。ケースの日時は「枠の開始」「枠の開始の1時間後」のように、割り当て枠からの相対で書かれます。
- **データの初期化**：各テストの前に、結合テスト専用のデータベースが初期データだけの状態に戻ります。前のテストのデータは残りません。
- **利用目的**：画面でそのテストの予約を見分けられるように、テストごとに、印（`[e2e]`）で始まる専用の文字列が用意されます。ケースの利用目的は「テスト用の利用目的」と書かれ、具体的な文字列は書かれません。
- **テストデータ**：「承認が必要な有効なリソース」のような条件だけが書かれ、具体的なリソースの名前は書かれません。条件に合うデータを選ぶのは、次のテストコードの段階です。
- **基本のロール**：観点がロールを指定していなければ、MEMBER で確かめます。作った予約があるかどうかは、テスト用の利用目的と割り当て枠で見分けます。
- **確認箇所**：期待結果が成り立っているかを、どの画面のどの部分を見て判断するかが、「マイ予約一覧」「予約申請フォームのメッセージ欄」のように、場所の名前だけで書かれます。何が成り立てばよいかは期待結果の列に書かれています。画面のどの箇所を見ればよいかは、テストを流したあとで、テストが実際に使った値（利用目的の文字列、リソースの名前、日時）として表示されます。
- **基本の入力**：観点が対象にしない入力項目（「他の項目は正しく入れる」の項目）の値は、1.3「基本の入力」に一度だけ書かれ、ケースからはそれを参照します。

## 手順1 AI に試験ケースを展開させる {#step1}

観点一覧を確定させたあと、Claude Code に次のように依頼します。

```text
/e2e-workflow 予約申請画面（/reservations/new）の結合テストを進めたい
```

案内スキル（`e2e-workflow`）が、試験仕様書がまだ作られていないことを確かめ、`generate-test-cases` スキルを呼び出します。試験仕様書は `Docs/test/reservations-new/cases.md` に保存され、試験仕様書の段階は「レビュー待ち」になります。スラッシュを付けて打つと、試験ケースを作り終えるまで Opus で動きます（[試験観点を作る](./viewpoints.md#step1)を参照）。

チャットには、件数と、レビューで最初に見てほしい「AI が仮に決めた値」が表示されます。一覧はダッシュボードで読みます。

---

## 手順2 試験ケースをレビューする {#step2}

試験仕様書を観点一覧と並べて読み、次の3つを確かめます。ダッシュボードで対象の画面を選ぶと、試験仕様書が表示されます。確定済みの観点一覧は、画面上部に並ぶ段階のうち「試験観点」を押すと表示されます。直してほしい点が見つかったら、試験ケースの ID と一緒に書き留めておき、手順3で差し戻しの理由にまとめます。

### 2-1. すべての試験ケースを、展開元の観点と突き合わせる {#step2-1}

2章の各ケースについて、「展開元」の列にある観点 ID を観点一覧で探し、その観点と照らして次を確かめます。

- 期待結果が、観点の期待結果と同じか（観点にない表示や文言が足されていないか）
- 手順と入力が、観点の条件を本当に満たしているか（境界の観点なら、入力がちょうど境界の値になっているか）
- 前提条件が、観点の「備考」に書かれた前提データを満たしているか
- 確認箇所で、期待結果を画面から観察できるか

AI の誤りがどのケースに入るかは前もって分からず、見落としたケースの誤りはそのままテストコードに引き継がれます。そのため、抜き取りにせず、すべてのケースを確かめます。

### 2-2. AI が仮に決めた値が妥当かを判断する {#step2-2}

3章「AI が仮に決めた値」には、仕様書に値がないため AI が自分で決めた値が載っています。載るのは、どの値に決めるかでテストの結果が変わるものだけです。

たとえば、仕様書に日時の入力単位が書かれていないと、AI は開始と終了の最小の差を、仮に1分と決めることがあります。しかし入力欄が5分刻みなら、1分の差は入力できないので、そのケースはテストできません。

各行の「別の値にするとどうなるか」を読み、選んだ値でその観点を確かめられるかを判断します。どの値を選んでも結果が変わらない細かな選択（重複予約の時間帯を割り当て枠のどこに置くか、など）は、3章には載らず、ケースの手順と入力に書かれています。それらは手順2-1 で確かめます。値を変えてほしい場合は、変えたい値と理由を書き留めます。差し戻すと、AI がその値を使うすべてのケースを直します。

### 2-3. 試験ケースにできなかった観点を判断する {#step2-3}

4章「試験ケースにできなかった観点」の各行について、AI が試験ケースにできなかった理由が妥当かを判断します。

- 妥当であれば指摘は不要です。
- 展開してほしい場合は、どうすれば展開できるか（用意するデータ、観察する場所）を書き留めます。差し戻すと、AI が展開を試みます。

観点を外すのはテストを減らす判断なので、AI に任せず学習者が決めます。

:::note[観点そのものの誤りに気づいたとき]

レビューの途中で試験観点そのものの誤りや漏れに気づいたときは、確定した観点一覧を差し戻しの状態に戻して直します。

関門2 で差し戻し、指摘の欄に「前の段階の誤り：観点の ID」と、何が誤りかを書きます。`/e2e-workflow` を実行すると、AI が誤りを確かめた結果を示し、観点一覧を戻すかどうかを尋ねます。戻すと答えると、観点一覧は「差し戻し」に、試験仕様書は「未着手」に戻ります。AI が観点一覧を直したら、観点一覧の確定からやり直します。詳しくは[前の段階の誤りを見つけたとき](./execution.md#upstream)を参照してください。

:::

## 手順3 差し戻すか確定するかを選ぶ {#step3}

ダッシュボード（開き方は[進み具合を確かめる](./workflow.md#where-am-i)を参照）の「関門2 試験仕様書の確定」で、差し戻すか確定するかを選びます。

手順2で書き留めた指摘があれば、「指摘」の欄に書いて「差し戻す」を押します。そのあと、もう一度 `/e2e-workflow` を実行すると、AI が指摘に沿って試験仕様書を直し、状態が「レビュー待ち」に戻ります。直された箇所について、手順2の確認を繰り返します。

指摘がなければ「確定する」を押します。
