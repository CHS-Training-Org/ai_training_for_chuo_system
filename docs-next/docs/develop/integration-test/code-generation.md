# Playwright コードを生成する

[試験ケースに展開する](./cases.md)で確定した試験ケースは、何を入れて、どこを見ればよいかまで決まっています。このページでは、それを Playwright のテストコードに変換します。

このページと次の[テストを実行する](./execution.md)は、[結合テストのワークフロー](./workflow.md)の3つ目の段階（テストコードと実行）にあたります。AI は、テストコードを作ったあと、続けてテストを流し、実行の証拠を集めるところまで行います。学習者はテストコードを読みません。このページでは、テストコードの説明のうち、テストコードを見なくても決められること（仕様と実装の名前の違いなど）を判断します。テストの確かめ方が期待結果に足りているかは、次のページで、テストコードから抜き出した「このテストが確かめたこと」と実行の証拠を見て判断し、関門3 で確定か差し戻しを選びます。

## 学習目標

このページを終えると、次ができるようになります。

- 試験ケースからテストコードへの変換を AI に任せ、何をレビューすればよいかを説明できる
- 仕様と実装の名前の違いや、ケースどおりに書けなかったところが、テストで見つけられる不具合をどう変えるかを判断できる
- テストコードを読まずに、AI に任せたところと人が決めるところを分けて進められる

## ゴール

テストコードの説明の2〜4章を判断し、直してほしい点を書き留めます。確定するのは、次のページで実行の証拠を見たあとです。

---

## AI と学習者の役割分担 {#roles}

### AI が出力するもの

テストコードは、[`generate-test-code`](../../reference/claude-code/agent-config.md) スキルが出力します。出力は2つのファイルです。

| ファイル | 中身 |
|---|---|
| `frontend/tests/e2e/workflow/<画面>.spec.ts`（テストコード） | 試験ケース1件につき1つのテスト。テスト名はケースの ID で始まる |
| `Docs/test/<画面>/code.md`（テストコードの説明） | 学習者の判断が要るところだけを書いた説明 |

テストコードを書くときから、AI は画面の実装を読みます。ボタンや入力欄を指定するには、実装に付いている名前やラベルが要るためです。ただし、期待結果は試験ケースからだけ取ります。実装が試験ケースの期待結果を満たしていないように見えても、AI はテストを弱めず、試験ケースのとおりに書きます。実際にどうなるかは、流した結果で分かります。

テストコードの説明（`code.md`）の章は次のとおりです。

| 章 | AI が書く内容 |
|---|---|
| 1章 テストデータの用意 | 試験ケースのテストデータ（「承認が必要な有効なリソース」など）を、初期データから選ぶか、API で作るか |
| 2章 仕様と実装で名前が違うところ | 試験ケースの名前と、テストコードで指定した実装の名前が違うところ |
| 3章 ケースどおりに書けなかったところ | 近い書き方にしたところと、それで結果がどう変わりうるか |
| 4章 テストコードにできなかったケース | テストにできなかったケースと、その理由 |
| 5章 集計 | 件数 |

### 学習者が決めること

| 学習者がやること | 対象 | 手順 |
|---|---|---|
| 仕様と実装で名前が違うところを判断する | 説明の2章 | 手順2-1 |
| ケースどおりに書けなかったところを判断する | 説明の3章 | 手順2-2 |
| テストコードにできなかったケースを外してよいかを判断する | 説明の4章 | 手順2-3 |

差し戻すか確定するかは、実行の証拠も見たうえで、[テストを実行する](./execution.md)の関門3 で決めます。

### 学習者が確かめなくてよいもの

テストコードは読みません。次のものは、人がコードを読まなくても確かめられるためです。

| 確かめなくてよいもの | 代わりに確かめる仕組み |
|---|---|
| ケースとテストの対応 | ダッシュボードが、テスト名の先頭のケース ID を数える。漏れや重複があれば確定できない。`test.skip` や `test.describe.skip` で止めたテストは数えない |
| 要素の指定方法、固定時間の待機、テストごとの初期化 | ダッシュボードが、決まりから外れた書き方を見つけて注意を出す。テストごとに初期データへ戻す仕組みを使っていないテストは、実行できない |
| 要素の名前や入力の値の誤り | 誤っていれば、流したときにテストがフェイルして分かる |
| テストデータの用意（説明の1章） | データベースに何が残るかは運営者が扱う。学習者は参考として読めばよい |
| テストの確かめ方が、期待結果に足りているか | 次のページで、「このテストが確かめたこと」と、見る場所の画面とテストで使った値（実行の証拠）を期待結果と並べて見て判断する |

確かめ方が足りないテストは、実行するとたいていパスしてしまいます。それを見つけるのに、コードを読む必要はありません。AI は、確かめ（`expect`）ごとに何を確かめるかの説明を添え、試験ケースの「見る場所」を開いたところで画面を撮り、テストで実際に使った値（利用目的の文字列、リソースの名前、日時）を残すテストを書きます。ダッシュボードは、確かめの説明と照合の種類をテストコードから機械的に抜き出して、期待結果の横に出します。画面と値だけでは、今回の実行の様子しか分かりません。確かめが足りているかは、抜き出した確かめで判断します。

:::note[テストコードの置き場所]

`frontend/tests/e2e/workflow/` に置いたテストは学習者の成果物で、普段の `pnpm test:e2e` には含まれません。ワークフローでは、AI が `node scripts/e2e-workflow/run.mjs` で流し、証拠を集めます。`pnpm test:e2e:workflow` でも流せますが、証拠は集まらず、ダッシュボードにも出ません。手元で試すときだけ使います（[BookFlow での実行](../playwright-guide.md#run)）。テストコードは作業ブランチにコミットしてかまいませんが、main には入れません（[ADR-032 の追記](../../reference/adr/ADR-032-integration-test-tutorial-adoption.md#addendum-2026-09-23)）。

:::

## 手順1 AI にテストコードを書かせる {#step1}

試験ケースの段階を確定させたあと、Claude Code に次のように依頼します。

```text
/e2e-workflow 予約申請画面（/reservations/new）の結合テストを進めたい
```

案内スキル（`e2e-workflow`）が `generate-test-code` スキルを呼び出し、テストコードとその説明を保存します。続けて、案内スキルが結合テスト専用のデータベースとバックエンドを用意してテストを流し、フェイルしたケースに見立てを書きます。すべて終わると、テストコードと実行の段階は「レビュー待ち」になります。流すのに数分かかります。

開発用のバックエンドが動いているときは、止めて結合テスト用に起動し直してよいかを、案内スキルが確かめます。結合テスト用のバックエンドは、流したあとも動いたままになります。開発に戻るときの止め方は、案内スキルの最後の返答にあります。

## 手順2 テストコードをレビューする {#step2}

ダッシュボードでテストコードと実行の段階を開くと、上にテストコードの説明（`code.md`）、その下に実行の証拠が表示されます。テストコードの全文も、押すと開けますが、読む必要はありません。直してほしい点が見つかったら、ケースの ID と一緒に書き留めておき、関門3 で差し戻しの理由にまとめます。

### 2-1. 仕様と実装で名前が違うところを判断する {#step2-1}

説明の2章には、試験ケース（仕様書）の名前と、実装の名前が違うところが並んでいます。たとえば、仕様書は「申請する」ボタン、実装は「予約を申請する」ボタン、のような違いです。

テストコードは実装の名前で要素を指定しているので、このままでもテストは動きます。学習者は、その違いが表記の揺れか、仕様と実装が食い違っている不具合かを判断します。不具合だと考えた場合は、そのことを書き留めておき、関門3 で確定するときに指摘の欄に書いて記録に残します。

### 2-2. ケースどおりに書けなかったところを判断する {#step2-2}

説明の3章には、試験ケースの記述をそのままではテストコードにできず、近い書き方にしたところが並んでいます。「結果への影響」を読み、その書き方で、試験ケースが見つけたかった不具合を見つけられるかを判断します。

### 2-3. テストコードにできなかったケースを判断する {#step2-3}

説明の4章の各行について、理由に納得できるかを判断します。納得できる場合は、そのまま確定します。テストにしてほしい場合は、どうすれば書けるかを書き留めて差し戻します。
