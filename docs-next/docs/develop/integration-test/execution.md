# テストを実行する

このページは、[Playwright コードを生成する](./code-generation.md)に続く、[結合テストのワークフロー](./workflow.md)の3つ目の段階（テストコードと実行）の後半です。AI は、テストコードを作ったあと、続けてテストを流し、実行の証拠を集めて、フェイルしたケースに見立てを書いています。学習者は、その証拠を試験ケースの期待結果と照らし、テストが期待結果を本当に確かめたか、フェイルの原因は何かを判断して、関門3 で確定か差し戻しを選びます。

:::note[このチュートリアルの位置づけ]

[ADR-032](../../reference/adr/ADR-032-integration-test-tutorial-adoption.md)は、テストの実行と失敗の切り分けを学習者の作業と定めています。このページは、実行を AI に任せ、学習者は実行の証拠で判断する設計を試すもので、ADR-032 にはまだ反映していません。提案は [ADR-033 の追記](../../reference/adr/ADR-033-e2e-workflow-mechanism.md#addendum-2026-10-03-run)にあります。

:::

## 学習目標

このページを終えると、次ができるようになります。

- 実行の証拠（見る場所の画面と、テストで使った値）を期待結果と照らし、テストが期待結果を本当に確かめたかを判断できる
- フェイルしたケースが実装の不具合かテストの誤りかを、AI の見立てを手がかりに、証拠と仕様で判断できる
- 関門3 で確定か差し戻しを選び、実装の不具合だと判断したケースを記録に残せる

## ゴール

テストコードと実行の段階を確定させます。

---

## AI と学習者の役割分担 {#roles}

### AI がやること

テストを流す作業は、案内スキル（`e2e-workflow`）が行います。

| AI がやること | 中身 |
|---|---|
| 環境を整える | 結合テスト専用のデータベース（`bookflow_e2e`）を用意し、バックエンドをそこにつないで起動する。開発用のバックエンドが動いていれば、止めてよいかを学習者に確かめる |
| テストを流す | `node scripts/e2e-workflow/run.mjs` で流し、結果と証拠を集める。環境が原因で流れなかったものは、環境を直して流し直す。テストの誤りに見えるものは、ここでは直さない |
| 見立てを書く | フェイルしたケースごとに、実装の不具合の候補か、テストの誤りの候補かなどの見立てと、その根拠を `Docs/test/<画面>/triage.md` に書く |

テストの誤りに見えても AI が直さずに渡すのは、直すかどうかを証拠で決めるのが学習者だからです。AI が自分の判断でテストを直して流し直すと、期待結果に合わせてテストを弱めたことに、学習者が気づけなくなります。

### 学習者がやること

| 学習者がやること | 手順 |
|---|---|
| 実行の証拠を見て、期待結果が成り立っているかを確かめる | 手順1 |
| フェイルしたケースが、実装の不具合かテストの誤りかを判断する | 手順2 |
| 前のページで書き留めた指摘と合わせて、確定か差し戻しを選ぶ | 手順3 |

---

## 手順1 実行の証拠を見る {#evidence}

テストの結果は、最後まで期待結果どおりだった「パス」と、それ以外の「フェイル」で表します。フェイルには、期待結果と違ったものだけでなく、手順の途中で止まったものや、環境が整っていなかったものも含みます（下の区分の表）。テストが一度も動かなかったケースは「実行されていない」と表示し、このケースがあるうちは確定できません。

パスかどうかだけでは、テストが期待結果を本当に確かめたかは分かりません。確かめ方が足りないテストは、画面の振る舞いが間違っていてもパスするためです。そこで学習者は、テストコードを読む代わりに、実行の証拠を見て判断します。

生成したテストは、試験ケースの「見る場所」（マイ予約一覧、予約申請フォームのメッセージ欄など）を開いたところで画面を撮ります。あわせて、テストが実際に使った値（利用目的の文字列、選んだリソースの名前、日時など）を残します。試験ケースには「テスト用の利用目的」「枠の開始」のように書かれていますが、画面には実際の文字列や日時が出るためです。

テストは、1件ごとに、結合テスト専用のデータベースを初期データだけの状態に戻してから動きます。そのため、証拠の画面には初期データと、そのテストが作ったデータだけが写ります。ほかのテストや過去の実行のデータは写りません。

ダッシュボードでテストコードと実行の段階を開き、テストコードの説明の下にある「実行の証拠」まで進むと、ケースごとに「期待結果、見る場所、このテストで使った値」「結果」「証拠の画面」が並びます。結果、画面、使った値は、実行から機械的に集めたものです。AI が書いたものは、フェイルしたケースの「AI の見立て」だけです。各ケースについて、次を確かめます。

- 証拠の画面に、見る場所が写っているか
- 使った値で行を探し、その画面で期待結果が成り立っているか（たとえば「申請できないこと」なら、マイ予約一覧に、使った値の利用目的の予約がないこと）
- 使った値が、試験ケースの手順と入力どおりか（たとえば「リソースを選ばないと申請できない」なら、リソースが「（空欄）」になっていること）

パスしたケースも見ます。パスしたテストは誰も疑わないので、確かめ方が足りないことに気づけるのはここだけです。証拠の画面や使った値がないケースや、見る場所と違う場所が写っているケースは、差し戻しの理由に書きます。

フェイルしたケースは、テストがどこで止まったかによって、次の区分に機械的に分けて表示します。表の上のボタンで、区分ごとに絞り込めます。

| 区分 | 意味 | 見るところ |
|---|---|---|
| 期待結果と違った | 見る場所までたどり着き、期待結果を確かめたところでフェイルした | 見る場所の画面で、期待結果と何が違うか |
| 途中で止まった | 見る場所にたどり着く前に、手順の途中でフェイルした（画面の要素が見つからない、画面が移らない、時間切れなど） | フェイルした時点の画面で、どこで止まったか |
| 前提データを用意できなかった | テストの前提になるデータ（既存の予約など）を API で作れなかった | エラーの内容 |
| 環境が整っていない | バックエンドやデータベースにつながらなかった | AI が環境を直して流し直すので、通常は残らない |

見る場所が2つあるケース（メッセージ欄とマイ予約一覧など）では、1つ目の期待結果と違っても、テストは2つ目の見る場所まで進んで画面を撮り、期待結果を確かめます。この場合、エラーは起きた順に並びます。区分は、最後のエラーで決めます。

区分は、実装の不具合か、テストの誤りかまでは決めません。それは手順2で判断します。

テストコードを流したあとで変えると、証拠は古いものとしてダッシュボードに表示され、流し直すまで確定できません。

## 手順2 フェイルしたケースを判断する {#step2}

フェイルしたケースには、AI の見立てが付いています。見立ては次の4つのどれかです。

| 見立て | AI がそう書くとき |
|---|---|
| 実装の不具合の候補 | 証拠の画面や応答が、試験ケースの期待結果と違う振る舞いを示している |
| テストの誤りの候補 | テストの操作や確かめ方が、試験ケースの手順や見る場所と合っていない |
| 環境の問題 | 流し直しても直らなかった、環境が原因と考えられるもの |
| 判断できない | 証拠から、どちらとも言えない |

見立ての根拠に書かれた証拠を、自分で見て確かめます。そのうえで、ケースごとに次のどれかに決めます。

- **実装の不具合**：展開元の試験観点に立ち返り、期待している振る舞いが仕様に照らして正しいことを確かめます。正しければ、実装の不具合として、手順3で確定するときに指摘の欄へケースの ID と理由を書きます。このチュートリアルの範囲では、記録に残すところまでとします。
- **テストの誤り**：直してほしい点を書き留め、手順3で差し戻します。
- **試験ケースか試験観点の誤り**：入力値や期待結果のほうが誤っていた場合です。確定した前の段階へ戻す操作は、まだダッシュボードにありません。差し戻しの理由に書いて、運営者に相談します。

:::warning[AI の見立てをうのみにしない]

AI が「実装の不具合の候補」とした見立てが、実際には試験ケースの入力値や期待結果の誤りであることもあります。見立ては候補です。根拠の証拠と、仕様書を自分で確かめてから決めてください。

:::

## 手順3 差し戻すか確定するかを選ぶ {#step3}

ダッシュボードの「関門3 テストの確定」の欄で、選びます。

- **差し戻す**：前のページ（テストコードの説明の判断）と手順2で書き留めた指摘があれば、指摘の欄にケースの ID を添えて書き、「差し戻す」を押します。もう一度 `/e2e-workflow` を実行すると、AI が指摘に沿ってテストコードを直し、流し直して見立てを書き直し、状態が「レビュー待ち」に戻ります。直った証拠を、もう一度手順1から確かめます。
- **確定する**：指摘がなければ「確定する」を押します。実装の不具合だと判断したケースがあれば、指摘の欄に書いてから押します。フェイルしたケースが残っていても、原因が実装の不具合だと判断できていれば確定してかまいません。

次のどれかに当たると、「確定する」は押せません。関門の欄に理由が表示されます。

- 試験ケースのうち、どのテストにも「テストコードにできなかったケース」にも載っていないものがある
- 同じケース ID のテストが2本以上ある
- 流した結果がない、テストコードが流したあとで変わっている、実行されていないケースがある

結合テスト用のバックエンドは、流したあとも動いたままです。開発に戻るときは、`node scripts/e2e-workflow/env.mjs down` で止め、`cd backend && ./gradlew bootRun` で開発用のバックエンドを起動し直します。

## ここまでの流れ

このチュートリアルで、次の3つの段階を体験しました。

1. 試験観点：何を確かめるかを、仕様書を根拠に決める
2. 試験ケース：観点を、前提、手順と入力、期待結果、見る場所に展開する
3. テストコードと実行：AI がテストコードを作って流し、学習者が実行の証拠で判断する

どの段階でも、AI が成果物を出し、学習者が関門で確定させます。学習者はテストコードを読みませんが、何を確かめるか（観点と期待結果）と、本当に確かめられたか（実行の証拠）は、自分で判断します。どこかの段階でつまずいたときは、[試験観点を作る](./viewpoints.md)から読み直してください。
