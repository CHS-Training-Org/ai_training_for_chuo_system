# ADR-035 — ドキュメントの図：draw.io の元ファイルだけを持ち、ブラウザで描画する

## Status

Accepted（2026-11-07）

## Context

ドキュメントサイトの図は、Mermaid では表現しきれない構成図やフロー図を描くために draw.io を使っている。20 枚の図は、いずれも元ファイル（`.drawio`）と、そこから書き出した画像（`.drawio.svg`）の2つで持っていた。ページが参照するのは画像だけである。

この持ち方で、2つの問題が出た（Issue #178）。

1つは、元ファイルと画像がずれることである。20 組を比べたところ、STEP-03 用の「計画→実装のループ」の図（`guide/no-aidlc-workflow-plan-implement`）は、元ファイルのラベルが新しく、公開中の画像は古いままだった。2つのファイルは同じコミットで作られており、最初から書き出し直されていなかった。元ファイルを直しても画像を書き出し忘れると、誰も気づかないまま古い図が公開される。

もう1つは、ビルドの警告である。Docusaurus は Markdown の画像の大きさを image-size で読むが、image-size はファイルの先頭 1000 バイトの中で `<svg>` の開始タグが閉じていないと SVG と判定しない。draw.io の SVG は編集用のデータを開始タグの属性に埋め込むため、20 枚すべてが判定に通らず、キャッシュの無いビルドで警告が並んでいた。上流（Docusaurus の issue #9715、image-size 2.1.0）でも直っていない。

運営者の条件は、ずれが起きないこと（元ファイルが1つ）、画質がベクターであること、ビルドを重くしないこと（図のためだけに Docker や draw.io デスクトップ版を動かさない）の3つである。

検討した候補：

| 候補 | ずれ | 画質 | ビルドの重さ | 評価 |
|---|---|---|---|---|
| 現状のまま、警告を無視する | 起きる | ベクター | 変わらない | ずれが解決しない |
| `.drawio.svg` だけを持ち、警告は独自の remark プラグインで消す | 拡張機能で保存し直すまで起きる | ベクター | 軽い | AI（drawio-skill）は XML を直接書き換えるので、見た目の SVG が描き直されない |
| `.drawio.png` だけを持つ | 起きない | ラスター | 軽い | 拡大すると文字がぼやける |
| ビルドで `.drawio` から SVG を書き出す（draw.io デスクトップ版のヘッドレス Docker イメージ） | 起きない | ベクター | 重い | Electron を含む大きなイメージを CI とローカルで動かす |
| ビルドで `.drawio` から SVG を書き出す（Playwright の Chromium と閲覧用 JS） | 起きない | ベクター | 中 | CI と docs コンテナに Chromium が要る |
| Mermaid、PlantUML 等のテキストの図に乗り換える | 起きない | ベクター | 軽い〜中 | 自由な配置ができず、構成図やフロー図の表現力が下がる。20 枚の描き直しが要る |
| **元ファイルだけを持ち、閲覧者のブラウザで描画する** | **起きない** | **ベクター** | **軽い** | 閲覧用 JS（約 5MB、gzip で約 1.1MB）を図のあるページで読み込む |

draw.io の図を正確に描くには、文字の幅を測るためにブラウザのエンジンが要る。そのため、ビルドで書き出す方式はどれもブラウザかそれに相当するものを動かすことになる。閲覧者のブラウザで描画すれば、ビルドには何も足さずに済む。

## Decision

**draw.io の図は元ファイル（`.drawio`）だけを `static/diagrams/` に置き、同梱した draw.io の閲覧用 JS で閲覧者のブラウザに描画する。** 書き出した画像は置かない。

- **Markdown の書き方**：これまでの画像と同じく `![説明](/diagrams/<分類>/<名前>.drawio)` と書く。図だけの段落にする。ビルド時に `plugins/remark-drawio.js` がこれを `<DrawioDiagram>` に置き換える。ファイルが無い、段落の途中にある、図として読めない場合はビルドを失敗させる。
- **描画**：`src/components/DrawioDiagram.tsx` が、図のあるページで初めて閲覧用 JS を読み込み、`.drawio` を取得して描画する。図をクリックするとページの中で拡大表示を開く（Mermaid の図の拡大縮小に相当する手段として）。
- **レイアウトのずれ**：描画の前に、元ファイルの図形の位置から求めた大きさで場所を確保する。文字のはみ出しなどは計算に入らないため、多くの図で ±10px 程度、線が図形の外を回り込む図では 100px 余りずれる。
- **ダークモード**：図は常にライトの配色で描き、ダークモードでは白背景のカードに載せる。
- **閲覧用 JS の同梱**：CDN（`viewer.diagrams.net`）から読み込まず、`static/js/drawio-viewer/` に版を固定して置く。CDN の URL には版が含まれず更新が予告なく反映されること、社内のネットワークで外部への通信が遮られると図だけ表示されなくなること、閲覧者の情報を外部に送らないことのためである。版、取得元、ライセンス（Apache-2.0）、更新の手順は同ディレクトリの README.md に書く。
- **外部への通信**：同梱した閲覧用 JS は、組み込み済みの図形だけを使う図では外部に何も取りに行かない。外部の画像、stencil、Web フォント、数式は使わない（drawio-skill の「ドキュメントサイトに載せる図」）。

## Consequences

**良い点**

- 元ファイルが1つになり、書き出しの手順がなくなるので、公開中の図が元ファイルとずれることが構造上なくなる。ずれていた「計画→実装のループ」の図は、元ファイルの新しいラベルで公開される。
- 画像として SVG を読まなくなるので、image-size の警告が出なくなる。
- ビルドに Docker やブラウザを足さずに済む。drawio-skill は `.drawio` を作って Markdown から参照するところで終わる。
- 図の中の文字は、これまでも検索の索引に入っていなかった。代わりに説明文が本文として索引に入る。

**悪い点・残る課題**

- 図のあるページを初めて開くときに、閲覧用 JS（gzip で約 1.1MB）を読み込む。描画まで少し待つ。JS が動かない環境では、図の代わりに説明文だけが表示される。
- 描画前に確保する大きさは目安なので、描画の後に本文が少しずれる図がある。
- 閲覧用 JS の更新は手作業である。更新のたびに git の履歴が約 1.1MB（圧縮後）増える。
- 開発サーバーで `.drawio` を直したときは、ページを再読み込みしないと反映されない。
- 受講者のトランクは `main` を取り込まないため、既存の受講者の環境（PR プレビューを含む）は `.drawio.svg` の方式のままである。

**この方式で問題が出たときの退路**

閲覧用 JS の読み込みの重さや描画のずれが許容できなくなった場合は、同じ閲覧用 JS を Playwright の Chromium で動かし、ビルド時に SVG を書き出す方式に移る。元ファイルは `.drawio` のままでよい。構成図以外の図（シーケンス図、状態遷移図）を Mermaid に寄せることも、将来の選択肢として残す。
