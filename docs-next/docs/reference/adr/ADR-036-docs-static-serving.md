# ADR-036 — ローカルのドキュメントサイトを静的ファイルで配信する

## Status

Accepted（2026-11-15）

## Context

受講者と同じ構成の devcontainer の消費メモリを、運営者の PC（物理 RAM 16GB、WSL2 の VM の上限 7.43GiB）で計測した（Issue #192）。VS Code の接続、`pnpm dev`、`./gradlew bootRun` を同時に動かすと、VM の上限とスワップ 2GB を使い切った。受講者の PC も物理 RAM 16GB 以上で統一しているので、同じ状況が起こりうる。

docs コンテナは、[ADR-027](./ADR-027-docusaurus-migration.md) の移行以来、Docusaurus の開発サーバー（`docusaurus start`）を常に動かしていた。開発サーバーは静的ファイルを配るのではなく、サイト全体を Rspack でバンドルし、その結果と依存関係の情報をメモリに置き続ける。編集をすぐ画面に反映するためである。計測では、常に 0.9〜1.1GB を使っていた。Mermaid の描画をやめた（[ADR-035](./ADR-035-drawio-browser-rendering.md) の追記）あとも、713MB（ピーク 871MB）が残った。内訳の大半は JavaScript のヒープではなく Rspack のネイティブメモリなので、ヒープの上限を絞ってもほとんど減らない。

一方、ビルド済みの静的ファイルを `docusaurus serve` で配るだけなら、約 125MB で済む。ビルドには 8〜15 秒かかり、その間は一時的に 1.2〜1.75GB を使う。

受講者は、チュートリアルの途中で仕様書を更新する（Spec-first）。更新した仕様書をその場で確認できる必要がある。STEP-06 では、ダッシュボードから `http://localhost:8000` の仕様書を開いて観点の根拠を確かめる。受講者のトランクには STEP-03〜05 で変えた仕様が入っているため、`main` を公開している GitHub Pages では代わりにならない。

検討した候補：

| 候補 | 常に使うメモリ | 受講者が手元の仕様書を見られるか | 評価 |
|---|---|---|---|
| 現状のまま開発サーバーを常に動かす | 約 0.7〜0.9GB | いつでも、編集もすぐ反映 | 削減にならない |
| 開発サーバーを必要なときだけ起動する | ほぼ 0 | 起動したときだけ | 受講者が起動の手順を覚えておく必要がある。STEP-06 などで止まっていると仕様書を開けない |
| **起動時にビルドし、静的ファイルを配る** | **約 125MB** | **いつでも。更新は再ビルドで反映** | 採用 |
| 静的ファイルを nginx などで配る | 数 MB | 同上 | サービスと設定ファイルが増える。baseUrl や 404 ページの扱いを GitHub Pages と合わせる手間がかかる |

## Decision

**docs コンテナは、起動のたびに依存を入れてビルドし、`docs-next/build/` を `docusaurus serve` でポート 8000 から配る。開発サーバーは、運営者が `scripts/docs-dev.sh` で必要なときだけポート 8001 に起動する。**

- **起動時のビルド**：ブランチを切り替えてから devcontainer を起動したときも、そのブランチの内容が表示されるよう、毎回ビルドする。ビルドが失敗しても（リンク切れなど）コンテナは止めずに配信を始める。止めると `restart: on-failure` で起動を繰り返すためである。
- **更新の反映**：起動後にドキュメントを直したときは `scripts/build-docs.sh` でビルドする。出力先が配信している `docs-next/build/` と同じなので、サーバーを起動し直さず、ページの再読み込みで反映される。`/update-spec` は最後にこのビルドを実行するので、仕様書の更新後は自動で表示が新しくなる。
- **開発サーバー**：`scripts/docs-dev.sh` は docs コンテナの中で開発サーバーを前面で起動し、Ctrl+C で止める。編集の即時反映と、ページに直接コメントを残す機能（`plugins/review-comments.js`）は開発サーバーでしか動かないため、運営者が文書を書くときに使う。
- **ポート 8001 の転送**：8001 は compose の `ports` でホストに公開し、`devcontainer.json` の `forwardPorts` には入れない。`forwardPorts` は作業用コンテナ（frontend）の localhost を転送するためである。さらに `portsAttributes` で 8001 の自動転送を止める。VS Code がターミナルに出た URL を見て作業用コンテナの 8001 を転送すると、Windows の `localhost:8001` を VS Code が先に使い、ブラウザが docs コンテナに届かなくなることを運営者の PC で確かめた。
- **ビルドの時期**：Java の言語サーバーの初期化（VS Code の接続後に始まる）とビルドが重ならないよう、ビルドを後にずらす案も検討した。docs コンテナから初期化の終わりを確実に知る手段がなく、時間でずらすと PC によって重なったり受講者に空のページが見えたりするため、採らなかった。

## Consequences

**良い点**

- docs コンテナが常に使うメモリが、713MB（ピーク 871MB）から約 125MB に減る。
- ビルドを経るので、開発サーバーでは使えなかったサイト内の検索が手元でも使える。
- 受講者が手元で見るドキュメントが、GitHub Pages と同じビルドの結果になる。

**悪い点・残る課題**

- 起動後の変更（編集、ブランチの切り替え）は、再ビルドするまで表示に反映されない。受講者が気づかずに古い表示を読むことがありうるので、トラブルシューティングに対処を載せた。
- 起動時のビルドで、一時的に 1.2〜1.75GB を使う。VS Code の Java の初期化と重なると、VM の上限を超えてスワップを使うことがある。
- ビルドの間（8〜15 秒）は、ページが表示されない。
- 受講者のトランクは `main` を取り込まない（[ADR-030](./ADR-030-personal-trunk-branch-strategy.md)）ため、受講中の受講者の環境には自動では届かない。
- 運営者は、文書を書くときに `scripts/docs-dev.sh` を起動する手間が増える。

[ADR-027](./ADR-027-docusaurus-migration.md) の「DevContainer」の節にある、開発サーバーを起動する構成は、この ADR で置き換える。
