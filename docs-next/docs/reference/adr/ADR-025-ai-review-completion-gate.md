# ADR-025 — AIレビューをタスク完了判定に格上げ

## Status

Accepted（2026-07-27）

## Context

[ADR-024](../ADR-024-ai-first-review-adoption) は `@claude pr-review` によるAIレビューを採用したが、その位置づけを「セルフレビューを補助する参考コメント」とし、マージの条件にはしないと決めた。採用時点ではレビューが実際にどの程度の検出力を持つか未知であり、学習者のマージを止める判断材料にできるとは言えなかったためである。

その後の実運用で、この観点構成が具体的な検出力を持つことを確認した。実際のエンハンス課題のPRに対して、テストが存在するにもかかわらず新規ロジックを検証していない状態（モックがクエリパラメータを無視するため、追加した転送処理を削除してもテストがpassする）を検出している。これはCIのlintやテストでは検出できない種類の欠陥であり、メンターの第三者レビューが保証されなくなった[ADR-023](../ADR-023-mentor-gate-removal)以降の運用で埋めたかった穴にあたる。

そこでチュートリアルの運用方針を「3つの観点すべてがOKであれば、実施者はそのタスクを完了とする」に変更した。ただしADR-024の記述は「参考コメント」のままであり、ドキュメントと運用が食い違っていた。

参考コメントから判定機構へ格上げするには、次の4点を決める必要がある。

**判定値の扱い**：「確認する」という指示だけでは判定の粒度が実行ごとにぶれる。同じPRを2回レビューして違う結論が出る状態では、完了の判断材料にできない。

**情報不足の扱い**：ビジネス要求シートが未リンクのPRや、PR本文の動作確認欄が未記入のPRでは、そもそも判定に必要な情報が揃っていない。これをOKともNGとも扱わない第3の値が必要になる。

**理解度チェックの判定方法**：観点3は質問を投げる観点であり、質問を生成できたこと自体は学習者の理解を意味しない。判定するには回答を読む必要がある。

**CI結果の扱い**：[review-criteria.md](../../develop/review-criteria.md) の評価基準はCI greenを完了条件に挙げているが、`claude-review`ジョブは`actions: read`権限を持たずCI結果を参照できなかった。CIが落ちている状態でタスク完了と判定するのは筋が通らない。

## Decision

AIレビューの総合判定OKを、チュートリアル実施者のタスク完了の条件とする。ADR-024の「非ブロッキング」の項目のみを本ADRで改訂し、他の決定（`@claude pr-review`によるトリガー方式、3観点の構成、GHAS・CodeQL不採用）はそのまま有効とする。

- **判定値**：各観点に`OK`・`NG`・`判定不能`のいずれかを付ける。情報が揃っていない場合は`判定不能`とし、OKもNGも選ばない。「たぶん満たしている」で`OK`を出さないための枠組みである。
- **総合判定**：3つの観点すべてが`OK`で、かつ前提条件のCI greenが`OK`のとき「完了」とする。1つでも`NG`・`判定不能`があれば「未完了」とする。
- **理解度チェックは2ラウンド方式**：1回目のレビューは質問を提示して観点3を`判定不能（未回答）`とする。学習者がPRコメントで回答し、再度`@claude pr-review`すると、過去のコメント履歴から回答を読み取って観点3を判定する。
- **CI greenを前提条件として判定する**：`claude-review`ジョブに`actions: read`権限と`gh pr checks`の実行許可を追加する。3観点という語彙を保つため、CI greenは4つめの観点ではなく前提条件として別枠で扱う。
- **出力は観点ごとに1件、最後にサマリを1件**の計4件のコメントとする。1件にまとめない。サマリを最後に投稿するのは、GitHubがコメントを古い順に表示するため、最後のコメントが最下部（PRを開いた学習者が最初に目にする位置）に来るからである。ラウンド2以降も4件すべてを投稿し、各ラウンドを完全なスナップショットとして残す。

:::note 観点3に関わる項目は ADR-026 で改訂済み
    上記のうち **総合判定**・**判定値**・**理解度チェックは2ラウンド方式**・**4件投稿**の各項目は、観点3（理解度チェック）に関わる部分が [ADR-026](../ADR-026-comprehension-check-quiz-format) で改訂されました。現在は次のとおり運用しています。

    - 観点3 は3〜5問の4択＋理由一文で出題し、回答があった実行で正誤にかかわらず全問を解説します
    - 観点3 は `OK`・`NG`・`判定不能` の3値ではなく状態（未出題・出題済み・確定）を持ち、動作はラウンド番号ではなく状態で決まります
    - 総合判定は `観点1 OK ∧ 観点2 OK ∧ CI green OK ∧ 観点3が確定` です。**観点3の誤答は完了を妨げません**
    - 観点3 が確定している実行では観点3のコメントを投稿せず3件とします

    観点1・観点2・CI green の判定値と扱い、required status check を導入しない方針は本ADRのまま有効です。
:::
- **required status checkは導入しない**。総合判定はタスク完了の条件だが、技術的にマージをブロックする仕組みは設けない。マージは学習者自身が行い、ADR-023のセルフ完結運用を維持する。

判定基準・出力様式の定義本体は`.github/workflows/references/pr-review-rubric/`配下に置く（前提と判定の枠組み、観点ごとの3ファイル、出力の様式の計5ファイル）。ワークフローの`prompt`はこれらを読む指示のみとし、基準の改訂をYAMLの変更から分離する。

## Consequences

**ポジティブ**：

- 判定が観測可能な事実（差分に存在するか）に寄るため、同じPRに対する判定の再現性が上がる。
- `判定不能`を独立した値として持つことで、情報不足のPRが暗黙にOK扱いされなくなる。ビジネス要求シートのリンクやPR本文の記入が、完了判定を通すうえで実質的に必要になる。
- 2ラウンド方式により、理解度チェックが質問の投げ捨てで終わらず、回答まで含めた検証になる。[ai-tools-guide.md](../../ai-tools-guide.md)の「生成コードの責任はマージした開発者が負う」という方針を、外部からの問いで検証可能にする。
- 観点ごとにコメントが分かれるため、学習者はどの観点が未達でどう直すかを追いやすい。

**留意点**：

- 学習者は最低2ラウンドのやり取りを要する。1回のレビューでタスク完了にはならない。
- 1ラウンドあたり4件のコメントが投稿されるため、PRのコメント欄は長くなる。
- タスク完了の条件でありながらマージをブロックしないため、判定が未完了のままマージすることは技術的に可能である。ADR-023同様、学習者の自発性に依存する。
- CI greenの判定は`gh pr checks`の出力に依存する。チェックが1件も報告されないPR（ドキュメントのみの変更など）では`判定不能`となり、総合判定が「未完了」になる。この扱いが実運用で厳しすぎる場合は、対象外の条件を別途定める必要がある。
